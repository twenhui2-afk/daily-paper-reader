Abstract —Static call graph construction tools cannot soundly model every dynamic language feature, yet they rarely reveal when, where, or why their results are unsound. Users cannot judge whether a call graph is complete for their program, and developers lack the precise root cause and code location needed to tell an implementation bug from an intended soundness/precision tradeoff. We present CG Rizz , an agentic framework addressing both needs in two phases. In a training phase, CG Rizz compares a benchmark of programs’ static and dynamic call graphs to find boundary edges —calls observed at runtime but missing from the static graph—and, for each, an LLM agent suggests a root cause: the program pattern the analysis failed to model and the responsible location in the tool. Because such a suggestion may be wrong, CG Rizz accepts it only when three independent pieces of evidence agree: runtime instrumentation that detects the pattern, a test case that reproduces the missed edge, and a warning inserted at the implicated tool location. The validated reports, test cases, and code locations serve developers; the warnings accumulate into a warning-instrumented build that, in a deployment phase, flags unsoundness on new programs for users, with no dynamic analysis required. We evaluate CG Rizz 

with three state-of-the-art tools, WALA, OPAL, and Soot, on three complementary benchmark suites. Of the 1459 boundary edges CG Rizz encounters, it reasons about 10.3% directly, all confirmed by a manual audit, and resolves a further 84.1% by grouping them with these validated root causes. Tool maintainers confirmed several reported limitations as genuine, and some have been fixed. The generated warnings generalize, flagging 74%– 92% of the unsoundness in held-out programs. Finally, guided by CG Rizz ’s reports, a coding agent refactored programs to remove 64% of the targeted root-cause patterns while preserving functionality, making them more amenable to static analysis. 

Index Terms —call graphs, root cause analysis, agent reasoning. 

I. I NTRODUCTION 

A static call graph models the potential calling relationships between methods in a program. Such a graph has traditionally served as the foundation of a wide range of program anal-ysis applications, including vulnerability detection, program comprehension, optimization, and software maintenance [1]– [3]. Today, call graphs also provide useful code context to large language models (LLMs), enabling them to reason about software behavior, answer developer queries, and perform complex software engineering tasks [4], [5]. Ideally, static call graph construction tools are sound , mean-ing that they capture all possible calling relationships that may occur during any execution of the target program. In practice, achieving soundness for all possible programs is rarely possible [6]. This limitation often stems from dynamic language features such as reflection, native code, and other behaviors that are difficult—or in some cases impossible—to analyze statically [6]–[9]. Tools that consume unsound call graphs may produce wrong answers. For example, a taint analysis tool [10] that does not see a call to a particular method may miss an illicit flow (leading to a false negative), or an exonerating input validation (leading to a false positive). Especially in the former case, users (including LLM coding agents) may be overconfident that their program is free of certain classes of vulnerabilities. Unsound analysis tools leave two groups of people missing useful information. A user , who runs a tool on their own program, has no way to tell whether, where, and why the resulting call graph is unsound for that program: documen-tation offers only aggregate statistics, and the tool itself issues no warning when it gives up on a construct. A developer ,who maintains the tool, lacks the precise root cause and code location needed to tell a genuine implementation bug from an intended soundness/precision tradeoff—and, when it is a bug, to reproduce and fix it. We developed CG Rizz to address these unmet needs. It operates in two phases. In a training phase, CG Rizz compares a benchmark of programs’ static and dynamic call graphs to find 

boundary edges —calls observed during execution but absent from the static graph—and, for each, an LLM agent suggests 

a root cause: the program pattern the analysis failed to model and the responsible location in the tool’s code. Because the suggestion can be wrong, CG Rizz accepts it only when three independent pieces of evidence agree: runtime instrumentation that catches the pattern as the program executes, a test case that reproduces the missed edge, and a warning inserted at the implicated tool location. The resulting report, reproducing test case, and code location are what a developer needs to confirm, fix, or knowingly accept a limitation. The inserted warnings accumulate into a single warning-instrumented build; in a deployment phase, this build is run by a user on a new program and warns where and why that program’s call graph may be missing edges, giving a user a view of whether to trust the analysis or adjust the program. We evaluate CG Rizz on three widely used static call graph construction frameworks—WALA, OPAL, and Soot—using arXiv:2611.29745v1 [cs.SE] 22 Nov 2026 three complementary benchmarks, asking whether CG Rizz 

produces trustworthy artifacts and whether those artifacts serve the two stakeholders. First, of the 1459 boundary edges the training phase encounters, an agent reasons about and validates 151 directly, and a manual audit confirms the reported root cause in every one of them; grouping resolves a further 1227 by matching them to an already-validated root cause, and re-analyzing a stratified sample shows that 86% of grouped edges share their group’s root cause. Second, the resulting artifacts are actionable for tool developers: of the reports we shared with the maintainers of each tool, several were confirmed as genuine limitations, and some have been fixed. Third, the warnings learned during training generalize to previously unseen programs: in a cross-validation study they surface 74%–92% of the unsoundness in held-out programs, and running the warning-instrumented tools directly on eight new programs flags 75%–83% of their root causes, giving a user a soundness signal for their own code with no dynamic analysis required. Finally, a user can act on these reports to reduce unsoundness: guided by CG Rizz ’s reports, a coding agent refactored programs to remove root-cause patterns while preserving their functionality, resolving 30 of 47 boundaries (64%). Overall, this paper offers the following contributions:  

> •

We present CG Rizz , the first agentic framework that reasons about, validates, and localizes the root causes of unsoundness in static call graph construction. Prior work characterizes a tool’s unsoundness only in aggregate— by comparing static and dynamic call graphs [6], [8], [11] or constructing synthetic benchmarks [12]—without pinpointing, reproducing, or localizing the cause of each individual missed edge.  

> •

We improve the transparency of static analysis tools by surfacing unsoundness during execution, so users can judge the reliability of a generated call graph and respond.  

> •

We show that the same reports give coding agents a new form of guidance—beyond functional correctness— toward software that is more amenable to static analysis. II. M OTIVATING EXAMPLE

Now consider the same missed edge from an OPAL de-veloper’s perspective. Its source could be a deliberate design decision, an implementation bug, or an unrealized opportunity to improve soundness—but the tool offers no signal that tells these apart: it neither flags the omission nor indicates where, in its own implementation, the edge was dropped. Suppose instead the developer were handed exactly the information needed to act on it. Existing work stops short: a report in the style of Sui et al. [6] would attribute the missing edge to a reflective API on the execution path, such as 

Class.newInstance() (line 5)—symptom-level attribution that points to the right neighborhood but is neither precise enough to localize the limitation nor specific enough to repro-duce it reliably. Three further pieces of information would close this gap: the precise condition that triggers the unsoundness, the responsible code location, and a reproducing test case. Inspecting OPAL’s implementation (Listing 2) 1 reveals the condition: the true cause lies earlier in the execu-tion chain than Class.newInstance() —the argument to 

Class.forName() is a non-constant variable. At line 17, OPAL pattern-matches the argument against StringConst 

and returns None for any non-constant argument, so the reflective target, and every edge depending on it, is never resolved. Reflection itself is not the problem; reflection with a non-constant class name is. For the test case, Listing 1 is exactly such a case, with the virtual call at line 6 the expected edge against which both the bug and any fix can be confirmed. Without such support, a developer must hypothesize the cause, build a reproducing test case, and localize the code by hand—demanding substantial expertise in both the framework and the language feature. This motivates our second goal, (G2) Developer localization: for each missed edge, automatically explain the precise root cause, the responsible tool implemen-tation location, and a reproducing test case with its expected edge, so that the developer can confirm, fix, or knowingly accept the limitation. III. CG Rizz APPROACH 

This section presents CG Rizz , an agentic framework for finding the root causes of unsoundness in call graph construc-tion tools. CG Rizz ’s training phase is given a benchmark of target programs, and for each follows the workflow detailed in Figure 1, which is divided into six stages. The first stage, data generation (Section III-A), collects boundary edges —calls observed when the program runs but missing from its static call graph—by building the program’s static and dynamic call graphs, taking their difference, and discarding non application-level edges. Next, for each boundary edge, the reporting agent (report generation , Section III-B) inspects the program and the tool’s source to suggest why the edge was missed—which pattern in the program the analysis failed to model, and where

in the tool’s implementation that failure occurs—producing an unsoundness report with a root cause, the implicated tool location, and a test-case description. Next, CG Rizz collects evidence to validate this report, in three independent forms. The test-case agent ( test-case generation , Section III-C) turns the report’s description into a test case that reproduces the missing edge. The instrumentation agent ( instrumentation and validation , Section III-D) writes runtime instrumentation that detects the suggested pattern as the program executes; CG Rizz 

checks that it flags the original boundary edge and that the test case reproduces the same pattern, producing a witness . The warning agent ( tool warning and trace check , Section III-E) inserts a warning at the implicated code location in the tool that fires when the tool processes the pattern. When the three agree, CG Rizz emits a validated report; when a check fails, it returns targeted feedback to the responsible agent and retries, setting the boundary aside after a bounded number of attempts. A final stage, grouping and filtering (Section III-F), reuses the instrumentation to dequeue and group other boundary edges sharing the same root cause. These three pieces of evidence are the artifacts the two goals of Section II call for. The test case, its expected edge, and the localized tool location serve the developer ( G2 ), while in deployment the validated in-tool warnings fire on the same patterns in future programs to serve the user ( G1 ). 

A. Data Generation 

For each target program we construct two call graphs: the static call graph, built by the target tool under the configuration we are studying, and a dynamic call graph, obtained by executing the program on representative inputs. We build both with the Judge framework [8], [12], which provides infrastructure for call-graph extraction and for comparing static and dynamic call graphs. The dynamic call graph is recorded by Judge’s own execution machinery, which is unrelated to the instrumentation CG Rizz later generates to validate a root cause (Section III-D). Comparing the two graphs yields the boundary edges : edges that appear in the dynamic call graph but not the static one, and whose caller appears in both. Each boundary edge seeds the rest of the pipeline. Both goals G1 and G2 concern unsoundness at the application 

level—patterns a user writes (G1) and a developer can re-produce as an application-level test case (G2)—so we keep only application-level boundary edges and exclude two other kinds. The first is edges whose caller is a JDK library method (e.g., in java.* ): these lie within library infras-tructure that users do not modify and a developer cannot readily isolate as a test. The second is edges whose callee is a JVM runtime method—one the JVM invokes implicitly (e.g., ClassLoader.loadClass() , <clinit> , or the hidden classes generated for lambdas) rather than through a call site written in the program. Boundaries are processed one at a time from the queue. The first stage, report generation , is carried out by the reporting agent , an LLM agent whose task is to suggest the root cause of the missed edge. It has access to three inputs: (1) the source code of the static analysis tool, (2) the source and byte code of the target program for the current boundary, and (3) the boundary information from Section III-A. The reporting agent starts from the boundary information. It uses the caller and callee signatures to locate the call site in the program and the recorded execution paths to gather the surrounding context, and from these it suggests the program pattern responsible for the missed edge—the specific construct, and the condition under which the analysis fails to model it. In the motivating example, it identifies the pattern as a reflective call through Class.forName() whose class-name argument is non-constant (line 4); reflection alone is not the pattern, reflection with a non-constant argument is. C. Test Case Generation 

From the unsoundness report, the test-case agent constructs a small standalone program intended to reproduce the missed edge. It extracts the test-case description from the report, generates a corresponding program, and then builds and runs it, refining until it compiles and executes successfully. At this stage the goal is only a working, self-contained reproduction at the application level; whether the program actually exhibits the missed edge is established by the validation in Section III-D. If the agent cannot produce a compilable, runnable test case, CG Rizz sets the boundary aside and moves to the next one in the queue. 

D. Instrumentation and Validation 

The reporting agent has only suggested a root cause; CG Rizz 

now gathers evidence for it. Two things must hold: that the suggested pattern accounts for the real missed edge (the boundary edge on the original target program), and that the generated test case reproduces that same pattern, making it a faithful, minimal stand-in. CG Rizz establishes both by building 

instrumentation that detects the pattern as the program runs. The instrumentation agent constructs this instrumentation from the report. To make the pattern precise enough to detect at runtime, we describe it with three elements, which the agent extracts from the report: 

a) Root cause location: The program location where the unsoundness originates; the instrumentation must flag the cor-responding instruction under the relevant runtime conditions. In the motivating example this is the Class.forName() call at line 4, where the argument is a variable rather than a constant. 

b) Symptoms: The observable consequences of the root cause—for call graphs, the missed edges. In the motivating example the symptom is the virtual call at line 6 whose receiver originates from the reflective instantiation. 

c) Relation: The link between root cause and symptom, typically a data-flow dependency. In the motivating example it is the flow from the object ( cls ) created by the reflective call at line 4 to the receiver of the virtual call at line 6. Running the instrumented program produces a witness : a JSON record listing each detected root cause together with the symptoms it produced. Each root-cause entry names the enclosing method and program counter of the root-cause instruction; each symptom entry names the caller, callee, and program counter of a missed edge. For the motivating example, the witness (Listing 4) records a single root cause— the Class.forName() call in ReflectVar.main() —and a single symptom, the missed edge from ReflectVar.main() 

to Target.hello() .The instrumentation agent works iteratively, generating a candidate and then building and running it until it compiles and runs without error. If the second check fails, CG Rizz returns directly to the reporting agent to revise the root cause. Once both checks pass, the workflow proceeds to the next phase. 

E. Tool Warning and Trace Check 

The warning agent inserts a warning into the source of the static analysis tool at the implicated location—a print statement that, during call graph construction, emits a message whenever the tool reaches that location under the conditions of the root-cause pattern. Once inserted, the same warning fires on any future program that exercises the pattern, which is how CG Rizz surfaces unsoundness to users (Section II). Because the report from Section III-B already names the files and locations responsible, the agent edits only those. Each warning records the description of the unsoundness, the enclosing method in the tool where the pattern is handled, and the line of that location. This information is usually available from variables in scope at the insertion point; when it is not, we instruct the agent to thread the needed variables into scope so the warning can report them. The warning agent is given the unsoundness report and write access to the tool’s source. The added (green) lines in Listing 2 show the warning for the motivating example, inserted directly into OPAL’s implementation. When handleAllocations 

calls getString , the latter returns None for a non-constant argument, so the second case branch runs and triggers the inserted warning. During call graph construction, the message is emitted whenever the pattern is encountered. With the warning in place, CG Rizz runs the warning-instrumented tool on the test case and records its execution trace. The check passes if the trace contains the inserted warning and, further, the root-cause locations recorded in the test case’s witness that are reachable in the static analysis all appear in the trace. This confirms that the implicated location is the one actually responsible for the missed edge. The check can fail in two ways: the trace contains no warning at all, meaning execution never reaches that region of the tool; or it contains warnings but not the root causes the witness expects. In either case CG Rizz re-invokes the warning agent up to k = 3 times with feedback identifying the failure mode and the warnings already tried. As in the previous phase, if the check still fails, CG Rizz returns to report generation, because a warning that cannot be made to fire at the implicated location is itself evidence that the report’s localization is wrong; a boundary that survives neither the warning retries nor a report revision is set aside. When the check passes, CG Rizz 

records the inserted location in the report and proceeds. After every boundary in the queue has been processed, CG Rizz merges all inserted warnings, using Git, into a single warning-instrumented build of the tool. This build can be run on fresh programs to alert users where their generated call graphs may be missing edges, realizing G1. 

F. Grouping and Filtering 

Once a boundary edge has been fully validated, the in-strumentation built for it (Section III-D) can recognize the same pattern cheaply in other benchmark programs, which is what keeps the pipeline affordable: rather than a full agent analysis of every remaining boundary, CG Rizz reruns that instrumentation on the programs whose boundaries are still in the queue. This works because the boundary edges come from executions we can rerun, so the instrumentation observes directly which queued boundaries exhibit the pattern it was built to detect. If a queued boundary appears among its symptoms, it very likely shares the same root cause, so CG Rizz 

groups it with the analyzed boundary and removes it from the queue. This is a heuristic—a shared symptom is strong evidence but not proof of an identical cause—so a grouped boundary can still be analyzed on its own if later evidence warrants. IV. E VALUATION 

Our evaluation asks whether CG Rizz meets the two needs set out in Section II: user transparency ( G1 ) and developer localization ( G2 ). Both depend on the training phase first producing artifacts that can be trusted, so we begin there and then take each persona in turn. 

RQ1 (Training phase). Does CG Rizz produce correct, validated root-cause artifacts, and at what scale and cost? This establishes whether the engine that serves both personas is sound. 

RQ2 (Developers, G2). Do CG Rizz ’s reports, test cases, and localizations help tool developers diagnose, confirm, and fix unsoundness? 

RQ3 (Users, G1). Do the warnings learned during training generalize to previously unseen programs, giving a user a reliable signal of where their own call graph may be unsound? 

RQ4 (Users, G1). Can a user act on CG Rizz ’s reports— here, through a coding agent—to refactor a program so that it is more amenable to static analysis? 

A. Experimental Setup 

This subsection covers what is common to all four RQs; details specific to a single RQ appear in its subsection. 

a) Tools: We apply CG Rizz to three state-of-the-art call graph construction frameworks: OPAL [15] (v5.0.1), WALA [16] (v1.5.7), and Soot [17] (v4.4.1), all used exten-sively in recent studies [7], [8]. 2 For each we use the default context-insensitive algorithm with all available soundness-enhancing options enabled. The three frameworks differ con-siderably in the size and structure of their call graph construc-tion code—2666, 1997, 3804 files and roughly 300, 309, 705 KLoC for OPAL, WALA, and Soot—which bears on how hard it is for an agent to locate a root cause within each, a point we return to in RQ1. 

b) Benchmarks: We use three complementary bench-marks. Cats [12] is a suite of 112 small, manually written programs, each exercising a specific dynamic language feature known to challenge call graph construction; it lets us test CG Rizz on isolated, well-understood patterns. NJR [18] and 

XCorpus [19] are real-world applications that exercise the intertwined sources of unsoundness arising in practice: for NJR we use the 141-program subset from prior static-analysis studies [20], [21], and for XCorpus the subset gathered by Sui et al. [6]—the only programs with at least one built-in test case, which we use to generate the dynamic call graphs. A program enters our evaluation only if it has at least one boundary edge surviving the filtering of Section III-A, since otherwise CG Rizz has nothing to analyze. The two kinds of benchmarks are then sampled differently. Because each Cats program targets a distinct pattern, we evaluate every tool on all of its own qualifying Cats programs—15 for WALA, 19 for OPAL, and 21 for Soot—so each tool is exercised on every pattern it exposes. For NJR and XCorpus we instead keep only the programs common to all three tools—25 NJR and 8 XCorpus—so the tools are compared on an identical set. From the 8 XCorpus programs we study three spanning a range of domains and unsoundness sources: javacc5.0 , a parser generator; fitjava-1.1 , an acceptance-testing framework; and nekohtml-1.9.14 , an HTML parser.

B. RQ1: Validity, Yield, and Cost of the training Phase 

RQ1 asks whether the training phase can be trusted: whether the root causes it reports are valid , how many of the boundary edges it manages to resolve—its yield —and at what cost. We keep validity and yield separate because a high yield means little unless the resolved cases are also correct. 

a) Yield: Table I (columns 3-10) reports, for each bench-mark and tool, the total number of boundary edges and how CG Rizz handled them. The total is itself a coarse measure of a tool’s unsoundness: for a given program the dynamic call graph is the same across tools, so the boundary count reflects how much of it the tool’s static graph missed—and, as the table shows, the tools differ here. In all, CG Rizz en-countered 1459 boundary edges. We call a boundary resolved 

when either an agent reasoned about it directly and passed all three validation checks of Section III (151, 10.3%), or the grouping stage (Section III-F) matched it to an already-validated pattern (1227, 84.1%). Grouping accounts for most resolved boundaries, which is what lets the training phase scale past a thousand edges without a separate agent analysis of each. Grouping is highly concentrated: across all three tools the largest group alone covers 22–34% of grouped edges and the top three cover almost half, while the rest tail off to a median group size of 2–4, so 25–35% of reasoned boundaries account for 80% of all grouping. Yield tracks program complexity. The small, single-feature Cats programs were resolved completely for all three tools, because their unsoundness is localized and an agent needs little surrounding context to reason about it. The real-world NJR and XCorpus programs were harder: there a root cause often spans several classes, packages, or third-party libraries, so the agent must reason over long-range dependencies, and both root-cause identification and artifact generation become more error-prone. 

b) Failed cases: The pipeline is sequential—report, then test case, then instrumentation with the pattern and boundary 

checks, then warning with the trace check—so a boundary that fails an early stage never reaches the later ones, and we categorize each failure by the last stage it reached (columns 6–9 of Table I). Most failures were pattern- or boundary-check failures: the generated instrumentation did not explain the real missed edge, or the generated test case did not reproduce it. Both concentrate on the larger programs and more elaborate patterns, where two known weaknesses of LLM agents compound—writing instrumentation that runs correctly on real-world code, and reasoning over long-range dependencies. A few cases failed earlier still, when an agent could not produce a required artifact at all. 

c) Validity: A boundary passing all three checks shows only that its report, test case, instrumentation, and warning are mutually consistent—not that the reported root cause is the true one. To test correctness directly, we manually audited the 151 reasoned boundaries—those an agent analyzed directly— confirming for each whether the reported pattern is the actual reason the edge was missed and whether the inserted warning fires at the responsible location. The root cause was correct in 100% of audited cases. However, we found two problems: (1) The generated in-strumentation is sometimes overly specific to the program on which it was built and does not fire on others. Grouping is therefore occasionally imperfect: a single root-cause pattern can be split across boundaries and reasoned about more than once. Only 30/44, 39/69, and 30/38 reasoned boundaries correspond to unique root causes for OPAL, Soot, and WALA, respectively. Because grouping is only a scalability heuristic (Section III-F), this does not affect resolved cases; it merely makes the grouped count underestimate reuse. These counts also approximate the number of fixes needed to address the identified unsoundness patterns. (2) Some warnings are in-serted at locations that are too general. For example, warnings associated with unmodeled native methods may be triggered whenever a receiver has an empty points-to set, even when the reported root cause is unrelated to the actual unsoundness. While these warnings still alert users to potential incomplete-ness, the explanation may be less actionable when attempting to eliminate the underlying root cause (Section IV-E). To mitigate this issue, we instruct the agent to guard warnings with lightweight control-flow conditions when possible, re-ducing false alarms from frequently executed but unrelated code locations. Neither problem affects the 100% correctness above: each reported root cause is still a genuine limitation of the tool that explains its missed edge; the problems only limit how broadly the instrumentation and warnings apply. 

d) Grouping accuracy: In addition to the problems above, we validated whether grouping is too general: whether grouped edges actually share the root cause of the validated boundary that grouped them (the group’s representative ). We used a stratified random sample of 100 of the 1227 grouped edges. We stratified first by tool and then by group: every group with at least 12 members forms its own stratum, the remaining small groups of each tool are pooled into one stratum, and samples are allocated in proportion to stratum size (WALA 20, OPAL 36, Soot 44). Each sampled edge was then re-analyzed from scratch by CG Rizz with grouping disabled, and we compared the root cause it confirmed with the representative’s. Overall, 86 of the 100 sampled edges share their representative’s root cause (WALA 17/20, OPAL 31/36, Soot 38/44). The 14 mismatches are not spread evenly: they fall in 6 of the 109 total groups, mostly mid-sized and large ones, where the representative’s instrumentation was too general and accepted edges outside its root cause. C. RQ2: Tool Developer Support 

RQ2 asks whether CG Rizz ’s artifacts—the report, the re-producing test case, and the implicated tool location—give a developer enough to act on an unsoundness. We assess this by sharing them with the maintainers of the three analyzed tools. Through manual inspection, we identified 7, 9, and 9 distinct root-cause groups for WALA, OPAL, and Soot, respectively. From these groups, we selected five from WALA, two from OPAL, and five from Soot and sent our artifact to the respective maintainers. For each report we record whether the maintainer confirmed it and, if so, whether they treated it as a bug to fix or as an intentional tradeoff. Every confirmed limitation was judged actionable, and several led to concrete outcomes. Soot maintainers were the most responsive. They confirmed four of our five reports and fixed three of them: missing handling of implicit exceptions, dynamic proxies ( Proxy.newProxyInstance ), and reflective field access ( Class.getDeclaredFields ). The fourth, re-flective calls with non-constant parameters, was scheduled to be addressed in a commercial version of the tool, and the fifth had not been discussed yet. The WALA maintainers confirmed two—reflective field access (e.g., Class.getDeclaredField ) and reflective proxy methods (e.g., Proxy.newProxyInstance )—and classified a third, implicit exceptions, as an intentional design tradeoff that they noted should be documented more clearly. That last case is evidence our artifacts are sufficient to distinguish a bug from a deliberate tradeoff, part of Goal G2. We did not receive a response for the other two reports. The OPAL maintainers confirmed one limitation, missing 

System.out edges when the JRE is in scope, which they had already fixed in a newer release. They did not respond to our remaining report. Even in cases developers did not respond, our artifacts let us carry out that diagnosis ourselves. The reports let us reason about a limitation the way a maintainer would, without their involvement. For example, as shown in Listing 5, OPAL’s own code notes that implicit NullPointerException calls should not be ignored, yet our report for a boundary involving such a call shows the limitation is unresolved—and that the location OPAL would handle it at is never reached for the affected cases. Because of imprecision in OPAL’s handling of interface-typed receivers, the condition that would introduce the exception edge does not fire, so the expected edge to

D. RQ3: Generalizability to User Programs 

We run three experiments to answer RQ3. The first two measure whether warnings learned from some programs fire on the unsoundness of other, unseen programs; the third asks whether microbenchmarks alone suffice to build those warnings. 

a) First experiment: coverage of held-out programs: 

We pool the programs from all three benchmarks and split them randomly into training and testing sets in an 80–20 ratio: the training programs drive the training phase that produces the warnings, and the testing programs stand in for the deployment phase—future applications run through the warning-instrumented tool. To reduce the effect of how the split falls, we use five-fold cross-validation and report the average coverage and standard deviation across folds. Re-running the warning-instrumented tool for every fold would be costly, so we use the equivalence groups from Section III-F as a proxy. Recall that each group bundles boundary edges that the analysis confirmed share a single root-cause pattern. We say a group’s warning is available if at least one of its edges originates in a training program—i.e., analyzing that program would have produced the warning— and we count a testing-program edge as covered if it belongs to an available group, since the same warning applies to every edge in the group. Coverage is the fraction of testing-program boundary edges that are covered. Under five-fold cross-validation, the warnings cover 74.0% 

± 30.0 (WALA), 82.2% ± 10.2 (Soot), and 92.3% ± 5.1 (OPAL) of the boundary edges in held-out programs. This is the fraction of an unseen program’s unsoundness that the warning-instrumented build would surface to its user with no dynamic analysis on the user’s part ( G1 ): a sufficiently diverse training subset captures most common causes and flags them even in programs that contributed nothing to the warnings. 

b) Second experiment: running the warning-instrumented tools: To validate the proxy and evaluate the instrumented tools directly, we selected eight NJR programs that were not part of our evaluation benchmark and that contain boundaries for all three tools after initial filtering. We first ran CG Rizz on each program to establish ground truth, finding 6 root causes for WALA, 12 for Soot, and 11 for OPAL. We then ran the final warning-instrumented tools on the same programs and compared the emitted warnings against these root causes. The warnings cover 5 of 6 (83%) root causes for WALA, 9 of 12 (75%) for Soot, and 9 of 11 (82%) for OPAL. These results are in line with the cross-validation estimates and confirm that the instrumented tools surface most of the unsoundness in programs they have never seen ( G1 ). 

c) Third experiment: microbenchmarks are not enough: 

This experiment again uses the grouping proxy. Taking the root causes discovered in Cats as the only training set and the real-world NJR and XCorpus programs as the testing set, only 2.9% of real-world boundaries match a Cats pattern. The rest come from patterns absent in the microbenchmark—typically inter-actions among application code, libraries, and frameworks—so a deployment built only from Cats would miss almost all of it. Diverse, real-world programs are thus essential to building the warnings future users rely on. We discuss remaining threats of the proxy methodology in Section V.

a) Construct validity: Our ground truth for unsoundness is the gap between a static and a dynamic call graph, and the dynamic graph is only a lower bound on real behavior: it contains the edges some execution exercised, not every feasi-ble edge. A boundary edge is therefore genuine unsoundness, but the absence of one does not certify soundness, and richer inputs would surface more. For the same reason, we do not report the precision of the warnings. A warning raised where no boundary edge was observed may still flag a real missed edge that no execution happened to exercise, so counting it as a false alarm would be unreliable; prior work shows that treating unobserved edges as infeasible leads to substantially wrong labels [23]. Relatedly, CG Rizz attributes each missed edge to a single root-cause pattern; one can in principle arise from several interacting limitations, so a warning may over- or under-approximate the affected locations when causes combine. A single cause accounted for the majority of those we found, and multi-cause patterns would require the agent to add complicated logic to the tool—both supporting this design choice. 

b) Internal validity: The pipeline relies on LLM agents, whose behavior is non-deterministic: a different run may reason differently about the same boundary. The three val-idation checks and the feedback loops guard against this— an unsupported suggestion does not pass—but they cannot rule out a suggestion consistent with all the evidence yet still wrong, which is why we audited all reasoned boundaries by hand (Section IV-B). That audit, and our classification of failures, rest on author judgment; to mitigate this, one author classified and the LLM confirmed the classification by reading the reports. Finally, RQ3 uses grouping as a proxy for running the warning-instrumented tool, and since grouping is an imperfect heuristic (Section IV-B) the reported coverage could be off in either direction. CG Rizz also relies on LLM-generated instrumentation as a witness for the root cause (Section III-D): although we validated it manually and added multiple validation checks, it may still miss the actual pattern or produce evidence only indirectly related to the root cause. 

c) External validity: Our findings come from three tools and three benchmarks and may not carry to others. We chose widely used frameworks and a mix of microbenchmark and real-world programs, and held Soot out during development to check the approach is not tuned to the tools we built it on; even so, other tools, languages, and program styles could exercise patterns we did not see. The RQ2 evidence is further limited to a small set of reports and the maintainers who engaged, and should be read as qualitative. VI. R ELATED WORK 

a) Imprecision and unsoundness root causes in CG anal-ysis: Over the past decade, several studies have investigated techniques for identifying the root causes of imprecision and unsoundness in static analyses and quantifying their impact. Sui et al. [6] proposed an approach for identifying the language constructs responsible for missed call graph edges in Java programs. Their technique combines calling-context trees [24] with runtime tagging of reflective operations to determine which language features contribute to unsoundness. Chakraborty et al. [11] extended this idea to JavaScript, where functions are first-class values, by tracing function data flow to identify the origins of missed call graph edges. Andreasen et al. [25] introduced techniques for isolating soundness and pre-cision issues in the TAJS JavaScript analyzer. Their approach records runtime values during program execution and validates that the corresponding static abstractions account for those values. When unsoundness is detected, delta debugging [26] is used to minimize the program, making manual root-cause analysis significantly easier. Several studies have focused on understanding analysis imprecision rather than soundness. Lhot´ ak [27] compared static and dynamic call graphs to identify sources of im-precision in Java call graph construction. Wei et al. [28] leveraged dynamic execution traces to localize the causes of imprecision in JavaScript analyses and suggested possible fixes. Similarly, Lee et al. [29] constructed tracing graphs by propagating information backwards from imprecise program points, enabling users to identify the dominant causes of analysis imprecision. However, because dynamic call graphs under-approximate program behavior, using them to identify imprecision is challenging [23]. Unlike imprecision, unsoundness can be identified reliably from runtime information: an edge observed at runtime but missing from the static call graph is a definite miss. Beyond this, our work differs in two key respects. First, existing approaches generally require manual inspection, labeling, or interpretation of their results, which limits scalability and the diversity of patterns identified; our framework performs the entire workflow automatically, from identifying boundary edges to generating reports, reproducing test cases, and localiz-ing the implementation limitation. Second, CG Rizz identifies root causes at a much finer granularity. Existing techniques typically attribute a missed edge to a broad language feature or API (e.g., reflection or Method.invoke() ), but modern tools support subsets of these features, so not every use leads to unsoundness. Our approach pinpoints the specific pattern—for example, that the unsoundness arises only when the argument to Class.forName() is not a compile-time constant—yielding more precise explanations and artifacts directly actionable for both developers and users. 

b) Empirical evaluation of call graph analysis: A num-ber of studies have evaluated the soundness and precision of static call graphs [7], [8], [12], [30], [31]. Reif et al. [7], [12] introduced a framework for benchmarking static call graph construction and developed a synthetic benchmark suite consisting of small programs with known sources of soundness and precision issues that are commonly missed by existing static analyses. Since these benchmarks come with known ground truth, they enable precise evaluation of static call graph quality. Helm et al. [8] extended this line of work by applying fuzzing to real-world programs to approximate ground-truth dynamic call graphs. By comparing these dynamic call graphs with statically generated ones, they evaluated the soundness of several static analysis tools on real-world applications. Samhi et al. [9] applied a similar methodology to Android applications, highlighting the challenges posed by reflection and other dynamic language features. Our work also leverages the static–dynamic comparison, using it to identify the boundary edges that start our analysis. We then go beyond measuring or categorizing unsoundness: we automatically reason about the root cause of each missed edge, generate a reproducing test case, localize the implemen-tation limitation, and add a warning that surfaces the pattern in future analyses—providing actionable artifacts for developers and users rather than merely reporting that unsoundness exists. VII. C ONCLUSIONS 

Starting from a set of static and dynamic call graphs produced for a benchmark of target programs, CG Rizz isolates individual missed static edges and suggests a root cause for each with an LLM agent, accepting that suggestion only when runtime instrumentation, a reproducing test case, and an in-tool warning each agree. Its output serves two stakeholders: developers, who get a reproducible, localized account of each limitation; and users, who get a warning-instrumented build that flags the same patterns in their own programs, with no dynamic analysis required. Our evaluation on WALA, OPAL, and Soot shows that this design delivers on both fronts: the root causes CG Rizz reasons about hold up under manual audit and extend through grouping to most remaining boundaries; maintainers confirmed, and in several cases fixed, the limita-tions we reported; the warnings generalize to programs they were not learned from; and the reports guided a coding agent to make programs more amenable to static analysis. While we study call graph construction, the approach is not specific to it. In future work, we plan to apply it to other static analyses, such as security-oriented tools like CodeQL [32], to bring the same transparency to the findings their users rely on.
