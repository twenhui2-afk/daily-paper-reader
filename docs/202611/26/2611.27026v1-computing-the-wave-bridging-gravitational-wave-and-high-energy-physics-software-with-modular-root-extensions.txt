Abstract 

High-Energy Physics (HEP) and Gravitational Wave (GW) astronomy pursue different scientific goals, yet they face strikingly similar computing challenges and can enrich one another through shared software. Building on the prototype presented at ACAT 2024, we report on the consolidation of that work into a single, modular extension of the CERN ROOT data-analysis framework, freely distributed under RIOPlus . The library is now organised as a set of optional, dynamically loadable extensions covering configuration and file-format parsing (including the Gravitational Wave Frame (GWF) format and HDF5), remote and federated data access (OSDF/Pelican, S3, Kafka) with token-based credentials, an enhanced dynamic-display manager, an advanced signal-processing layer built on the KFR library, and a complex-capable tensor layer backed by LibTorch with ONNX interoperability. We summarise the design of each extension, outline the intended application to transient-noise (glitch ) detection and classification, and update the FFT performance benchmark comparing KFR with FFTW. We close with the end-to-end ROOT-centred workflow these extensions enable, its current status, and an outlook toward column-wise RNTuple storage. 

# 1 Introduction 

The timely detection of compact-binary mergers is of central importance to both astrophysics and nuclear physics. The first binary-neutron-star merger, GW170817 together with its elec-tromagnetic counterpart GRB170817A [1], opened the era of multi-messenger astronomy and demonstrated the value of low-latency alerts. Over the last years the main gravitational wave (GW) collaborations have consolidated their computing efforts into a common infrastructure, the International Gravitational-Wave Observatory Network (IGWN) [2], jointly operated by the LIGO [3], Virgo [4] and KAGRA [5] collaborations. IGWN and the large HEP experiments (e.g. ATLAS and CMS at the LHC) share many computing challenges — federated data distribution, heterogeneous pipelines, the integration

High-energy physics (HEP) is dominated by the need to process very large data volumes, whereas the GW community is driven primarily by latency: science data streams are comparatively small (a few calibrated channels), but they must be transported and analysed in near real time to enable rapid sky localisation and follow-up. The goal of the present work, continuing the prototype reported at ACAT 2024 [6], is to get the best of both worlds by bringing the maturity and performance of HEP analysis software — in particular the CERN ROOT framework [7] — to GW data analysis, while keeping the result lightweight, optional and easy to adopt. ROOT has already been used within the GW community, mostly by researchers with a HEP background; a concrete and successful example is the Omicron software [8], which performs the 

Q-transform on top of ROOT; the cWB pipeline [9] likewise uses ROOT alongside the LIGO Algorithm Library Suite (LALSuite) [10], the C package that underpins most GW pipelines. Rather than replacing existing tools, our aim is to extend ROOT so that it covers the features a GW workflow requires. From discussions with pipeline development researchers we distilled six practical requirements useful for both communities: 1. common software distribution for Python, C/C++ and Fortran; 2. a coherent ecosystem and packaging story; 3. remote data access : configuration files, remote storage and the GWF/HDF5 file formats; 4. enhanced dynamic display with generic precomputed layout; 5. advanced signal processing ; and 6. complex-valued tensors with low-maintenance machine-learning support. The immediate motivation is transient-noise characterisation in KAGRA: glitch classification for O3GK was done offline with unsupervised learning [22, 23, 24], and linking glitch families to their instrumental origin needed a separate veto study [21]. The steps involved — reading distributed data, time-frequency analysis, inference with Python-trained models — are spread across tools in different languages and data containers. This proceeding is limited to the software addressing this; scientific results obtained with it are left to dedicated publications. 

# 2 A modular ROOT extension: RIOPlus 

Following ACAT 2024 the prototype libraries were consolidated and made available at https:// git.ligo.org/kagra/libraries-addons/root/root-plus . The code is now organised around a core library, libRIOPlus , complemented by a set of optional extensions that the user loads only when needed (figure 1). Each extension is an independent shared object ( .so ), so a deployment pays only for the features it uses and the additional dependencies they entail. All extensions add high-level helpers with no runtime overhead on top of standard ROOT classes, remaining fully compatible with the rest of the framework.

2.2 Configuration and file-format extensions 

The configuration extension ( libRIOPlus_Config ) exposes a single adapter interface ( TConfig ,with concrete back-ends such as TConfigJSON ) so that JSON, YAML, XML and INI files can be read and written interchangeably. The file-format extension ( libRIOPlus_Format ) adds support for reading and writing HDF5 (the de-facto format for GW open-science data) and the Gravitational Wave Frame (GWF) format [11], the standard low-latency strain format in which one calibrated second of data is stored per frame. Rivet files are also supported, easing interoperability with HEP tooling. 

2.3 Remote data access and credentials extension 

Modern GW analysis is increasingly federated. This extension integrates several remote-storage and streaming back-ends behind ROOT-like directory and file abstractions: the Open Science Data Federation (OSDF) [12], accessed over HTTP through the Pelican protocol ( TDirectoryOSDF ); S3-compatible object storage based on the open-source MinIO client ( TDirectoryS3 ); and Apache Kafka [13] producers and consumers ( TKafka ), with message packing for long payloads. Kafka being payload-agnostic, the chunked GWF messages of the IGWN low-latency data distribution (IGWN-LLDD) could use the same packing layer; this is not exercised here. Access to distributed resources worldwide is handled through JSON Web Token and SciToken credentials (TJWToken /TSciToken ), used together with the TCurl interface. 

2.4 Enhanced dynamic display 

GW publications and dashboards rely on a recurring set of plots (running time-series, ratio plots, confusion matrices, skymap projections). The display helpers, built on the ROOT TExec 

mechanism, handle in-sync axis, tick and label positioning from margin-and-padding information, support shared axes, and keep a fixed or dynamic size on demand so that a canvas remains portable when resized. 

2.5 Advanced signal-processing extension 

The signal-processing extension is the part most specific to GW analysis. It wraps the KFR library [14], a modern, actively maintained C++ DSP framework released under the GPL, behind a TKFR interface that is compatible with ROOT’s TVirtualFFT (while remaining optional). KFR provides N -dimensional DFT/FFT together with a rich set of signal-processing primitives: 3amplitude- and power-spectral densities, the Hilbert transform, FIR and IIR filtering, windowing, decimation, and waveform generation, and analog/digital filter design (Butterworth, Chebyshev, elliptic) through TComplexFilter , TBiquad and TPoleZeroMap . They are exposed through 

TTimeSeries and TFrequencySeries (both derived from the TTensor<Element> introduced below), covering use cases from spectral estimation to matched filtering. The library is portable across architectures and exploits SIMD acceleration through SSE/SSE2/AVX instructions on x86 -64 and NEON on ARM64.

2.6 Complex tensors and machine learning 

The tensor extension provides a TTensor<Element> class for tensor and matrix computations backed by the LibTorch C++ API [16], sharing the same backend as PyTorch and therefore enabling transparent GPU acceleration. Following ROOT conventions (e.g. TH1F /TH1D ), the precision notation is extended to four numerical types: real single/double ( F/D) and com-plex single/double ( C/Z). Tensors are created from existing ROOT buffers without copying (torch::from_blob ). Trained models exported in the Open Neural Network Exchange (ONNX) format [17] can be loaded through a TModel wrapper (an ONNX Runtime session) and applied directly to TTensor data, allowing recent models to be used and shared across Python and C/C++ applications without bespoke maintenance — updating LibTorch through Conda is sufficient. This complements, without additional maintenance burden, the machine-learning capabilities already available in ROOT through TMVA/SOFIE [18], which remains an attractive option for reproducibility. The extension targets deployment, not training: applying a Python-trained model, in the same process, to complex-valued data held in ROOT containers. A MNIST [20] example is shipped with the library. 

# 3 Application: transient-noise detection and classification 

A representative use case that exercises several extensions at once is the handling of glitches 

— short instrumental or environmental transients that mimic or mask astrophysical signals. Detecting them starts from a power-excess search, such as the Q-transform performed by Omicron [8] on top of ROOT. The primitives of section 2.5 are its building blocks, but reproducing Omicron is not the purpose of this work and no such comparison is presented here. 4Once candidates are extracted, classifying their morphology helps diagnose detector be-haviour [21]. The publicly available Gravity Spy catalogue [19] lists tens of recurring glitch classes identified since the first observing run [22, 23, 24]. Using the tensor extension (section 2.6), we explore a workflow in which an unsupervised embedding — Uniform Manifold Approximation and Projection (UMAP) — is first used to find clusters in the space of glitch spectrograms for pre-tagging, after which a convolutional neural network performs the final classification, the architecture used offline in [22, 24], with the trained models exported to ONNX. Performing this online would flag recurrent system failures (e.g. cooling or actuators) as they happen. 

# 4 Distribution: packaging and containers 

Conda has become a de facto standard for software deployment within the GW community, and we use it as a package manager to distribute pre-compiled binaries. Two community efforts are relevant: a lightweight hep-forge conda channel with minimal publication requirements (Linux, AMD64, and optional ARM64), and a broader HEP packaging-coordination initiative targeting multiple architectures and operating systems on conda-forge, both independent of the legacy hepforge.org service. Generic conda binaries target a baseline instruction set, but KFR (like LibTorch and ONNX Runtime) embeds several architecture-specific code paths selected at run time, so the performance-critical layer is not penalised. Reference documentation and tutorials are in preparation for the first tagged release, and external contributors are welcome through the LIGO GitLab instance.
