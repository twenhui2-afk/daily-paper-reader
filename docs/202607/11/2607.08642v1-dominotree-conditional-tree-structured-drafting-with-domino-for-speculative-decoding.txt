# DominoTree: Conditional Tree-Structured Drafting with Domino for Speculative Decoding ∗

Saw S. Lin (Zhiqi Zhang) Jyh-Shing Roger Jang 

Abstract 

Speculative decoding accelerates LLM inference by drafting several tokens and verifying them in parallel. Block-diffusion drafters such as DFlash produce a draft block in one pass but model only per-position marginals; best-first tree methods such as DDTree expand candidate trees from those marginals. The released Domino drafter adds a GRU-based causal correction that makes each draft token’s distribution path-dependent, a structure DDTree’s factorized formulation cannot represent. We introduce DominoTree, a training-free best-first draft tree scored by Domino’s conditional (non-factorized) correction along each root-to-node path, made practical by restricting the per-node correction to a candidate top-M . On Qwen3-4B across eight benchmarks, DominoTree reaches up to 6.6× speedup over autoregressive decoding and the highest mean accept length of any evaluated method (up to 10.7 tokens per round) at every temperature we test. DominoTree constructs its tree with a GPU-native, CUDA-graph builder — bit-identical to a reference Python implementation, so acceptance is unchanged — that keeps per-round tree construction cheap. With this builder as default, DominoTree wins throughput over the released Domino decoder — the very drafter it is built on, run at its own CUDA-graph best — at every temperature ( 9–10% overall on Qwen3-4B, up to +22% on Alpaca), and over DDTree/CaDDTree at every temperature we test (CI-clean paired-bootstrap improvements), not only at greedy decoding. On Qwen3-8B, DominoTree keeps the highest accepted length at every temperature and adds a decisive throughput win at T =0 (+24% over DDTree); at higher temperature that edge over DDTree/CaDDTree narrows to a tie and a small loss, while its Overall (aggregate) wins over DFlash and Domino persist. 

## 1 Introduction 

Every speculative decoding method lives inside the same efficiency identity: end-to-end speedup over autoregressive (AR) decoding is proportional to accepted tokens per round ( τ ) divided by the wall-clock cost of drafting and verifying that round ((1), Section 2.1). Draft quality raises τ ; draft 

cost lowers the denominator — and the two trade off. Autoregressive drafters (e.g. the EAGLE line (Li et al., 2024a,b, 2025)) sit at one extreme: each drafted token conditions on every token drafted before it, but that costs γ strictly sequential forward passes for a length-γ draft. Block-diffusion drafters such as DFlash (Chen et al., 2026) sit at the other extreme: an entire block is proposed in a single parallel forward pass, but every position’s logits are then a marginal over tokens that will actually be realized elsewhere in the block, not a conditional on them, which caps how high τ can climb (Section 2.2). Domino (Huang et al., 2026) closes much of this gap without paying the autoregressive drafter’s full sequential cost: it keeps DFlash’s parallel backbone unchanged and adds a lightweight sequential correction — a GRU tracks which tokens have actually been sampled so far along the current draft

## 2 Background 

2.1 Speculative decoding 

Speculative decoding (Leviathan et al., 2023; Chen et al., 2023) accelerates autoregressive LLM inference by pairing a cheap draft model with the expensive target model. At each decoding round the drafter proposes a sequence (or, in tree-based methods, a small tree) of candidate continuation tokens; the target model then scores every candidate position in a single parallel forward pass and accepts the longest prefix (or root-to-leaf path, for a tree) whose tokens match what the target model itself would have sampled. Because the accepted tokens are guaranteed to come from the target model’s own distribution, speculative decoding is lossless up to floating-point tie-breaking : it changes only the number of target-model forward passes needed to produce a given output, not the output distribution itself. Tree-attention verification (Section 3.5) reorders bf16 reductions relative to token-serial decoding, which could in principle add further divergence; Section 4.5 shows it does not, at the same benign tie-level rate as chain-style verification, which is what substantiates the losslessness claim for trees specifically. 3End-to-end speedup over AR decoding can be written as 

η = τ · Ltarget 

Tdraft + Tverify 

, (1) where τ is the mean number of tokens accepted per round (the acceptance length ), Ltarget is the cost of one target forward pass, and Tdraft , Tverify are the per-round drafting and verification costs. Two independent levers govern η: draft quality (which determines τ ) and draft cost (Tdraft ). A method that raises τ at the expense of a proportionally larger Tdraft need not raise η at all — this tension motivates both Domino’s design (Section 2.3) and the cost-aware tree-budget selection this paper builds on (Section 2.5). An autoregressive drafter conditions token i on all previously drafted tokens 1, . . . , i − 1, exactly the causal structure the target model uses, but each of the γ draft positions in a length-γ draft therefore requires its own sequential forward pass (and, in the worst case, its own full-vocabulary LM-head projection) — Tdraft scales with γ. Parallel (block) drafters trade this away. 

2.2 DFlash: a block-diffusion drafter and why its logits are marginals

Two structural facts. These properties of Domino’s correction matter directly for how a draft tree can be built on top of it. 

Fact A. Domino’s released decoder is chain-only. The published decoding loop samples exactly one token per draft position and advances a single GRU state; there is no branching. Nothing in the architecture prevents branching — multiple candidate tokens could be sampled and corrected at a given position, each carrying forward its own GRU state — but the released implementation does not do this. 

Fact B. Domino is a partial-conditional drafter. The backbone representation Hi is shared and path-independent: it is computed once, in the single parallel pass, identical regardless of which tokens end up being sampled anywhere in the block. A fully conditional (autoregressive) drafter would need to re-run its entire backbone per branch, since every position’s represen-tation depends on the realized prefix; a purely marginal drafter (plain DFlash) never depends on the realized prefix at all, so branching costs nothing beyond a top-k read at each depth. Domino sits in between: branching a tree on top of it requires re-running only the cheap GRU-plus-correction branch per node, never the expensive backbone pass, because the backbone output is shared across every hypothetical branch. This is the structural fact that makes a conditional draft tree on Domino computationally plausible at all, and it is the fact DDTree’s and CaDDTree’s factorized formulation cannot represent. 

2.4 DDTree: a best-first heap over factorized marginals 

DDTree (Ringel and Romano, 2026) builds a draft tree directly on top of a block-diffusion drafter’s per-position marginals. Under a fixed node budget n, DDTree maintains a max-priority queue (heap) keyed by cumulative path log-probability: starting from the root’s children, it repeatedly pops the globally highest-cumulative-log-probability unexpanded leaf, adds it to the tree, and pushes its own children (again scored by the drafter’s per-position marginal at the child’s depth) onto the heap, until the node budget is exhausted. Because DDTree’s per-depth distributions are read directly from 5the drafter’s marginals Lbase  

> i

, this scoring is path-independent : two different candidate ancestors at the same depth would offer the identical menu of children and child scores, since the marginal drafter never conditions on which tokens are actually chosen along the path. The resulting tree is prefix-closed by construction (every node’s parent appears earlier in the pop order) and is verified in a single target-model forward pass using an ancestor-only causal attention mask — the standard tree-attention verification mechanism used by DDTree and SpecInfer (Miao et al., 2024) alike, which we reuse unmodified (Section 3.5). 

2.5 CaDDTree: cost-aware adaptive budget 

DDTree’s node budget n is a fixed hyperparameter, chosen offline per task. CaDDTree (Zhang et al., 2026) observes that expected acceptance length is non-decreasing in n — a bigger tree can never accept fewer tokens in expectation — so acceptance length alone gives no principled stopping rule: it always prefers the largest affordable tree, ignoring that a larger tree also costs more to verify. CaDDTree instead optimizes expected throughput directly. Writing Φ( n) = P 

> s

πs for the cumulative prefix-probability mass captured by the first n nodes (in best-first pop order) and modeling draft cost Cd (fixed) and verification cost Cv(n) (increasing, and assumed convex) as functions of the round, the expected-throughput objective at budget n is 

θ(n) = 1 + Φ( n)

Cd + Cv(n) .

CaDDTree proves that under a convex Cv, θ is unimodal in n, which licenses a cheap greedy stopping rule: grow the tree node by node in best-first order and stop increasing n the first time θ stops improving. This removes the need for an offline per-task budget search, adapting the tree size to each round’s actual difficulty as measured by how quickly Φ( n) saturates. Both the unimodality proof and the greedy stopping rule are stated for the factorized case: Φ( n) is a sum over the same fixed per-position marginals DDTree’s heap uses, computed once per round independent of which path is being explored. Section 3.4 asks what survives when this identity is instead applied to a non-factorized, conditional tree: the throughput identity and the best-first monotonicity step it relies on plausibly extend to the conditional case via the same chain-rule argument CaDDTree’s own proof uses, so factorization by itself is not an obvious blocker — but candidate restriction (Section 3.2) prunes the per-node child set our heap actually searches, which departs from the exhaustive per-position support CaDDTree’s proof assumes. We therefore do not claim a proved optimum for the conditional case; we treat CaDDTree’s stopping rule, carried over to our heap, as a cost-aware heuristic . Separately, and more decisively, we find a purely empirical obstacle that defeats this heuristic whether or not CaDDTree’s optimality proof carries over to the non-factorized conditional case: miscalibration of the corrected drafter’s path-probabilities as target-acceptance estimates makes the resulting adaptive budget ineffective in practice, which we analyze in Section 3.4 and Section 6. 

## 3 Methodology 

We build a draft tree on top of the released Domino checkpoint, without any retraining or mod-ification to Domino’s weights. The construction has five pieces: (i) a best-first heap identical in mechanism to DDTree’s, but scored by Domino’s GRU-corrected conditional log-probabilities in-stead of path-independent marginals (Section 3.1); (ii) a candidate-restriction technique that makes the per-node correction affordable (Section 3.2); (iii) a GPU-native, CUDA-graph implementa-tion of that same per-node correction that removes the per-round Python-driven build overhead, 6verified bit-identical to the Python builder (Section 3.3); (iv) CondAdaptive, a native per-round adaptive-budget rule that extends CaDDTree’s cost-aware stopping criterion to this non-factorized setting (Section 3.4); and (v) tree-attention verification, borrowed unmodified, for which we claim no novelty (Section 3.5). 

3.1 Conditional-scored best-first heap 

The builder itself is DDTree’s algorithm, unmodified: a max-priority queue keyed by cumulative path log-probability, popped one node at a time in strictly non-increasing score order, each popped node contributing its own children back onto the heap, until a node budget n is exhausted or the maximum depth L is reached. What differs between DDTree-on-Domino and our method is entirely contained in one function — the children function — that the heap calls to score and expand a popped node’s children: 

C(state , d ) −→ (tokens , log-probs , child-states ).

Given a path state — the GRU hidden state summarizing the tokens realized from the root to that node — and a target depth, C returns the top-k candidate tokens at that depth, their log-probabilities, and (for the conditional variant) each candidate’s child-state: the GRU state after advancing by that one token, used in turn to score that child’s own children. Because the heap builder is written against this interface alone, the two scoring strategies plug into the identical builder; the comparison between them (Section 4.4) isolates the scoring function as the only variable, holding the tree-construction algorithm, budget, and verification fixed.

3.3 GPU-native tree builder 

Candidate restriction (Section 3.2) removes the dominant FLOP cost, but a residual per-node cost remains: best-first expansion is sequential — each pop reads its node’s corrected tokens and log-probabilities back into the Python heap before the next can be scored — and although the per-node correction is individually cheap, each pop launches fifteen to twenty CUDA kernels from Python, so kernel-launch overhead, not FLOPs, dominates. Batching nodes into one launch, the obvious fix, backfires: best-first exists to grow the tree deep along the single highest-scoring path, whereas a batched depth level spends the fixed node budget on shallow breadth before best-first order can choose what to extend — forfeiting the depth the conditional score depends on (its advantage comes from conditioning on the realized path, which only a deep path exercises). We instead remove the launch overhead the way Domino does for its own chain: capture the fixed-shape per-node correction as a CUDA graph and replay it. Best-first cannot be captured whole — which node pops next is data-dependent control flow a graph cannot express — so the Python heap keeps deciding pop order (Algorithm 1) and only the per-node correction is graphed. Being a line-by-line transcription of the eager math, the graphed builder is bit-identical: at T =0 

on GSM8K and HumanEval its committed tokens and accept length match the Python builder’s row-for-row, so the tree is unchanged (Section 4.5). Only cost changes — at budget 16, M =64 it cuts per-round build time from 3.67 ms to 2.31 ms (Table 3). The three-graph construction and its static-buffer recipe are in Appendix C.

3.5 Tree-attention verification (borrowed, unmodified) 

Verification is not a contribution of this paper: given the tree returned by either children function above, we reuse DDTree/SpecInfer’s tree-attention verification unmodified (Miao et al., 2024) — an ancestor-only causal attention mask lets one target-model forward pass score every tree position 9at once, and we commit the highest-scoring root-to-leaf path along which every edge is accepted (longest-accepted-path). This runs alongside, and does not modify, Domino’s own chain-only ver-ification; its near-flat cost as tree size grows is inherited from DDTree/SpecInfer, not engineered here.

4.3 Python vs. GPU-native builder 

A decoding round is bounded by the target model: verify , the single target forward, is 18 .7 ms/round, dwarfing draft (3.5), build (2.3), and commit (0.7) (Table 3), so the one drafter-side cost a tree method must control is the build stage. DominoTree’s default GPU-native builder and a refer-ence Python builder of the same algorithm (Algorithm 1) produce bit-identical trees (Section 3.3), so comparing them isolates build cost with the tree held fixed: draft , verify , and commit are unchanged, and the GPU-native builder’s entire 1.36 ms/round saving falls in build (Table 3). That cost difference is decisive for whether DominoTree’s accepted-length lead converts into a throughput lead against DDTree/CaDDTree. Table 4 shows what this buys: with the GPU-native builder as DominoTree’s default, Overall throughput vs. DDTree is a CI-clean win at every temperature we test (Table 2); with the identical trees built by the Python reference builder instead, the result degrades from a T =0 win to a T =0 .5 tie to a T =1 .0 loss. Against the Domino chain, both builders win at every temperature, but by a much wider margin under the GPU-native builder. 

The effect amplifies at 8B. Tree construction re-queries the drafter once per expanded node, so build grows with the drafter: on Qwen3-8B (single A6000) the GPU-native builder’s per-round 

build saving rises to 11 .7 ms, roughly 8× its 4B saving, while verify is essentially unchanged — confirming the difference is the builder, not GPU contention. This is decisive: under the Python builder DominoTree’s +10 .4% accepted-length lead over its chain converts to no throughput gain (95% CI [−1.37 , +1 .40] ), and the GPU-native builder is what turns that lead into the 8B throughput win of Table 1.

4.5 Losslessness 

Losslessness here is a property of construction, not of the tree: the target verifier is unchanged, so every committed token is a valid target decode regardless of which candidates the tree proposed, up to the bf16 tie-breaking noted in Section 2.1. Empirically (Appendix A), DominoTree diverges from token-serial greedy decoding at the same rate as the vanilla Domino chain ( 7.44% vs. 6.51% 

of prompts show any divergence, at nearly identical mean first-divergence index), with no bias toward either method diverging earlier. This is expected and benign — the same regime DDTree and SpecInfer already occupy — and does not bear on losslessness, which holds by construction for both. 

## 5 Related Work 

Speculative decoding and tree verification. Speculative decoding was introduced by Leviathan et al. (2023) and Chen et al. (2023). SpecInfer (Miao et al., 2024) generalized single-chain verifica-tion to tree-structured candidates, verifying an entire token tree in one target-model forward pass via an ancestor-only attention mask — the verification mechanism this paper reuses unmodified (Section 3.5). 

Autoregressive tree drafters: EAGLE. The EAGLE line (Li et al., 2024a,b, 2025) builds high-quality draft trees on top of an autoregressive drafter, culminating in EAGLE-3’s (Li et al., 2025) training-time-test procedure. Because an autoregressive drafter’s hidden state at position i genuinely depends on the realized tokens at all earlier positions, branching an EAGLE-style tree requires re-running the (small, but nontrivial) draft model per branch — there is no shared, precomputed representation across branches the way there is for a block-diffusion backbone. Block-diffusion drafting: DFlash. DFlash (Chen et al., 2026) is the parallel drafter backbone Domino, and therefore this paper, builds on (Section 2.2). DFlash itself drafts a single chain per round from its marginal per-position distributions; it does not build trees. 

Marginal draft trees: DDTree. DDTree (Ringel and Romano, 2026) is the direct algorith-mic ancestor of the tree-construction mechanism used in this paper: a best-first heap over a block-diffusion drafter’s per-position marginals, verified with an ancestor-only attention mask (Sec-tion 2.4). Our conditional tree uses the identical heap mechanism; the entire technical contribution of this paper is a node-scoring function — Domino’s GRU-corrected, path-dependent conditional log-probability — that DDTree’s factorized formulation cannot express, because DDTree only ever consults per-position marginals that do not depend on which tokens are realized along a candidate’s own path (Section 3.1). 

Cost-aware budgets: CaDDTree. CaDDTree (Zhang et al., 2026) replaces DDTree’s fixed, offline-tuned node budget with a per-round greedy stopping rule, proved optimal under a convexity assumption on verification cost, for the factorized case (Section 2.5). CondAdaptive (Section 3.4) inlines the same rule into our conditional tree’s pop loop; the optimality framework plausibly carries over, but the corrected drafter’s path-probabilities are miscalibrated as target-acceptance estimates, so the resulting budget gives no gain over a fixed one (Section B.3). 

Closest related work: JetSpec. JetSpec (Hu et al., 2026) is, to our knowledge, the closest published method to our goal: it builds a causal draft tree directly on top of a parallel drafter, combining one-forward-pass drafting efficiency with branch-wise causal conditioning, by training a new causal parallel draft head aligned with the target model’s own factorization. The honest distinction is that JetSpec trains a new draft head end-to-end for tree-structured causal conditioning, whereas our method is training-free: it reuses Domino’s released, off-the-shelf correction head, 15 adding no new parameters and requiring no additional training data or compute. We flag plainly that this is a narrow niche: if a future revision of JetSpec is shown to be training-free as well, or if it adds a per-round adaptive budget we could not get CondAdaptive to deliver (Section B.3), the distinction we claim narrows substantially, since a purpose-trained causal head is a strictly more expressive mechanism than reusing a GRU correction that was not trained with tree branching in mind. 

## 6 Limitations and Future Work 

We state the current scope limits plainly rather than deferring them to a closing paragraph. 

GPU-native builder: scope. DominoTree’s default builder is GPU-resident: heap management is left to Python, but per-node correction executes via CUDA-graph capture/replay rather than a per-node round-trip through eager PyTorch, analogous to Domino’s own CUDA-graphed chain correction (Section 3.3). What remains future work is extending this pattern beyond a single-stream research harness: a multi-request, batched, or serving-integrated (e.g. SGLang/vLLM) version of the same graph-capture idea. 

A6000 and 5080 throughput are not directly comparable. This matters for the Qwen3-8B grid (Table 1), collected on a single RTX A6000 rather than the two RTX 5080s used for the Qwen3-4B grid this paper headlines. Microbenchmarking indicates the A6000’s verification-forward latency in this setup is both higher and noisier than the 5080’s, consistent with clock- or attention-kernel-throttling rather than the 5080’s cleaner memory-bandwidth-bound profile, so absolute tokens-per-second numbers from the two GPUs should not be compared directly. Only same-GPU relative comparisons — a tree method vs. its own chain baseline, or own-AR-normalized speedups — carry across the two grids. If anything, the GPU-native builder matters more at 8B than at 4B: the heavier Domino drafter makes tree construction costlier, so the builder’s per-round saving grows to 11 .52 ms and is what converts DominoTree’s accepted-length lead into its 8B throughput win (Section 4.3). 

T > 0 draft convention. At T > 0 DominoTree drafts deterministically (best-first) and samples the target, accepting a draft token iff it equals the sampled target token, so the committed output is the target’s own temperature-sampled sequence (lossless). We verified from source that the reference DFlash/DDTree/CaDDTree implementation uses this identical convention, so that cross-harness comparison is convention-matched at every temperature; the released Domino baseline samples its own draft, as published. Draft-side sampling is a separate axis, ablated in Table 10. 

Adaptive budgeting remains open. DominoTree ships a fixed node budget. CondAdaptive — our attempt to transfer CaDDTree’s cost-aware adaptive budget to this non-factorized setting — does not improve over it: the corrected drafter’s cumulative path-probabilities over-credit accep-tance, so the adaptive rule saturates at its cap (Sections 3.4, B.3). A calibrated per-round adaptive budget is left to future work. 

Prototype, not a serving system. All results are produced by a single-stream, batch-size-1 research harness built on Hugging Face Transformers, not by an integration into a production serving stack (e.g. SGLang or vLLM). The tree builder is CUDA-graphed by default (Section 3.3), but batching, continuous scheduling, and multi-request serving are not implemented here. Throughput 16 numbers here are real, wall-clock GPU measurements on this research harness, not production-serving throughput.

Because Φ( n) overstates how many of the next nodes will actually be accepted, the marginal throughput gain CaDDTree’s rule computes for adding one more node keeps looking positive well past the point where it should turn negative: the rule keeps expanding the tree instead of stopping. In practice this means the selected budget n∗ runs to the maximum budget cap on nearly every round, rather than settling on a smaller, round-specific value. CondAdaptive therefore degenerates to a fixed budget at the cap, with no throughput gain over simply fixing the budget at 16. We adopt the fixed budget as the DominoTree method and report CondAdaptive as a mechanism-backed negative result: the optimality framework transfers, but calibration, not the tree-construction idea, is what defeats it. 

## C GPU-native builder: capture/replay construction 

Section 3.3 establishes that DominoTree graph-captures only the per-node correction, leaving the Python heap untouched, and that the graphed builder is bit-identical to the eager one. This ap-pendix gives the capture/replay construction in full. 

Three per-node graphs. We capture the per-node correction as three separate CUDA graphs — one for the per-round candidate setup, one for the correction proper below the prefix, and one for the simpler state-only expansion above the prefix — because these three sub-computations recur at different points in a build and cannot share a single capture. capture/replay recipe: static input buffers are allocated once, overwritten in place with copy_ before each replay, the graph is replayed as a single driver call, and results are read from static output buffers and cloned before the next pop’s replay overwrites them. The graphed path differs from the eager children function only in reading from these static buffers via index_select instead of direct Python indexing — same operations, shapes, and dtypes — which is why it is equivalent by construction rather than by post-hoc testing. 

The one synchronization that remains. The read-back of each pop’s winning tokens into the Python heap cannot be graphed away: the heap needs those actual values to decide pop order, so one cuda.synchronize() per pop remains. What the CUDA graph removes is the Python-launch overhead surrounding that unavoidable sync, not the sync itself. Domino’s released 

DraftCorrectionGraphRunner captures its entire k-step chain as one graph precisely because a chain has no such data-dependent read-back between steps; best-first’s per-pop heap decision is what forces the finer-grained, three-graph split here.
