## Abstract 

Modern mobile and edge platforms provide hardware-backed attestation of application and platform integrity at load-time. However, they offer little support once application execution begins. We present ARA, an Application-Runtime Anchor for ARM that extends this load-time chain of trust into exe-cution. ARA bootstraps from the underlying ARM platform Root of Trust (RoT) through a measured loading chain and establishes an attested protected run-time within the appli-cation address space using recently introduced ARM Per-mission Overlay Extensions (POE). The resulting run-time domain can host programmable RoTs for Measurement and Storage (RTM/RTS), enabling application run-time integrity verification, attestation evidence generation, and protected use of secrets while retaining efficient access to application run-time state. As exemplary uses, we instantiate ARA for protected media decryption and application control flow measurement. Our prototype and evaluation show that ARA supports frequent run-time RoT-backed operations at near in-process cost, with roughly 10× and 50× lower overhead than out-of-process equivalents. This offers a practical bridge from layered attestation to application run-time trusted com-puting on ARM. 

## 1 Introduction 

Trusted computing architectures rely on Roots of Trust (RoTs) to establish confidence in system integrity and protect security-critical assets such as cryptographic keys, measurements, and security policies. While modern mobile and edge plat-forms increasingly deploy trusted computing services [2, 24, 28, 44, 66], these mechanisms remain largely confined to layered attestation that ends at application load-time veri-fication, essentially proving to a remote verifier (e.g., a re-mote application server) that the right application binary was launched on top of the right operating system. Once a user-space application begins executing, little trustworthy infrastructure remains available for measuring run-time ap-plication behavior or protecting security-critical state within the application itself. We argue that this limitation stems from a key challenge in establishing an application-centric RoT: how to simultaneously isolate a trusted (in-)application run-time substrate and connect this isolated substrate with the underlying hardware-backed RoT guarantees? 

Conventional attempts to achieve this goal typically rely on separate processes, privileged software (e.g., within the kernel), or Trusted Execution Environments (TEEs) [5, 9, 10, 16, 22, 47]. While some of these approaches provide ade-quate isolation, run-time trusted computing operations must repeatedly cross protection boundaries to observe or pro-cess application state. This requires context switches, inter-process communication (IPC), or privilege level/TEE tran-sitions. The resulting cost, thus, becomes prohibitive for run-time security services that interact with the application at fine granularity, e.g., execution/continuous integrity mon-itoring. On the other hand, software-only techniques can avoid some boundary-crossing costs, but instead rely on ex-tensive software instrumentation, incurring significant run-time overheads to the application itself [36, 53, 56]. These limitations call for run-time trusted computing approaches that both (1) remain rooted in platform hardware anchors and (2) avoid crossing traditional/costly isolation boundaries. We also observe that, for the first time, the required hard-ware support for both hardware-backed layered attestation (currently built upon ARM TrustZone) and application-level isolation co-exist in the same architecture (ARM v8.9), with the recent introduction of ARM’s Permission Overlay Ex-tensions (POE) [7] (details in Sec. 2). In particular, we argue that POE changes the design space for trusted computing on ARM by enabling strong isolation within a single pro-cess without requiring costly process, kernel, enclave, or hypervisor transitions, for application measurement and state-based computation. Building on this observation, we compose POE with layered attestation to design, implement, and evaluate Application Run-time Anchor (ARA). ARA is

hardware-isolated and attested, executes within the appli-cation’s address space (user space), and can be instantiated as run-time trusted computing services for application mea-surement and storage. While in-process memory access control features similar to POE have been explored in x86 architectures, in particular based on Intel MPK [27, 54, 58] (see Section 9), x86 lacks the hardware support for layered attestation, which at present is implemented on ARM devices. We believe the composition of the two features to be a timely direction that enables several potential security applications. Trusted computing services are increasingly deployed to protect user-space applications on ARM-based edge devices (as exemplified by Android Play Integrity and Apple’s App Attest system discussed in Sec-tion 2.2), and POE is a very recent technology that enables a new design space to further secure the application run-times. Our evaluation shows that ARA provides a practical and cost-effective foundation for run-time measurement, verifi-cation, and protection of user-space applications. In more detail, ARA benefits from three properties: (1) POE permis-sions are checked in parallel with Memory Management Unit (MMU) checks, and permissions can be reconfigured with one register write operation in user-space; (2) POE can be leveraged to make ARA code and data inaccessible (ex-ecution is only permitted via controlled invocation points) to application code; and (3) POE can be composed into lay-ered attestation to ensure that the configuration of isolated trusted substrate in user space is verifiable. The asymmetry in in-process memory access control pro-vided by POE allows us to instantiate ARA with RoT func-tions without requiring IPC, kernel mediation, or similar. In other words, ARA is isolated from, but shares the same virtual address space as the application. This makes security-relevant computation, e.g., logging relevant control flow transfers and system calls (syscalls) for attestation/auditing, enforcing execution integrity against control flow graphs, confidentially computing on secrets, and signing attestation reports, as cheap as normal in-process computation. Simulta-neously, ARA’s integration with layered attestation provides hardware-backed remote verifiability. 

Intended Contributions. In sum, our intended contribu-tions are: 

• ARA Architecture: an in-process run-time trust an-chor that extends ARM platform attestation into user-space execution using POE. 

• Secure Construction: a bootstrapping and launch-binding protocol plus controlled invocation/syscall me-diation that preserves the ARA boundary even after the host application is compromised. 

• RTS/RTM Instantiations: we provide concrete RTS and RTM services, demonstrated through protected media decryption and in-process control-flow attesta-tion. 

• Prototype and Evaluation: we provide an open-source ARA prototype implementation and respective evaluation showing roughly an order-of-magnitude performance improvement on the RTS workload and roughly 30–55× improvement over process isolation for the high-frequency RTM workload. 

## 2 Background 

2.1 Roots of Trust (RoTs) 

An RoT is a minimal Trusted Computing Base (TCB) used to establish the security foundation of a computing system. Because higher-level security mechanisms depend on the integrity of it, RoTs are typically designed to be verifiable and isolated from less trusted software layers. Common ex-amples include secure elements, Trusted Platform Modules (TPMs), immutable boot ROMs, and hardware security mod-ules (HSMs). In modern systems, RoTs enable functions such as secure boot, cryptographic key management, and plat-form remote integrity verification (a.k.a., remote attestation). RoTs are generally categorized as RoTs for measurement and storage 1.A Root of Trust for Measurement (RTM) focuses on system integrity by securely measuring software (either stat-ically, i.e., at load-time or run-time/execution properties). Examples of measured properties include load-time code integrity and run-time integrity (e.g., control and data flow). A Root of Trust for Storage (RTS) provides secure protection for sensitive cryptographic material and other security-critical data. Unlike an RTM, which focuses on in-tegrity measurement, the RTS ensures the confidentiality and controlled usage of secrets such as encryption keys, cer-tificates, authentication credentials, and attestation keys. In many architectures, cryptographic operations involving pro-tected keys are performed entirely within the RTS boundary, preventing key material from ever being exposed in plaintext to untrusted software. ARA establishes a run-time RoT within a user-space pro-cess. Section 7 presents two case studies demonstrating how ARA can be instantiated as RTM and RTS for user-space process execution. 

2.2 Layered Attestation and Application Integrity 

Modern mobile platforms (such as iOS and Android) provide hardware-backed RTMs for attestation services that allow application servers to verify the integrity of both application code and aspects of the underlying execution environment at or near load-time. When an application is launched, the platform generates a cryptographic key pair that is bound to the application identity and the device’s hardware. The private key never leaves the trusted hardware boundary and is used to sign attestation statements that can be verified by a remote backend using the corresponding public key and platform-issued certificate chain. During application launch or shortly thereafter, the appli-cation server can request (via a challenge-response protocol) an attestation token that reflects both the integrity of the application code and evidence about the device state. If the attestation passes, the server can treat the client as running in a “known-good” state and engage in sensitive operations. While widely used [66], current integrity attestation plat-forms only provide load-time measurements and leave run-time integrity unchecked. Intuitively (and as shown empiri-cally in Section 7), this limitation stems from the high over-head that run-time application RoT functions would have un-der typical isolation models (e.g., process-based), which must rely on costly context switches and IPC. ARA addresses this gap by establishing an overlayed protected domain within the process itself and connecting it into the layered attesta-tion trust chain. 

2.3 Permission Overlay Extension (POE) 

A recent hardware feature, introduced in the ARMv8.9 ar-chitectures, is Permission Overlay Extension (POE) [7]. It enforces access control policies at runtime with minimal overhead, allowing software to dynamically restrict mem-ory access among domains within the same process without requiring kernel mediation. POE acts as an additional access control layer on top of con-ventional virtual memory protections. Access permissions are enforced at the granularity of virtual memory pages us-ing Page Table Entries (PTEs). POE associates memory pages with overlay identifiers (IDs). These IDs encode logical pro-tection domains. During execution, the processor maintains a permission register – namely, POR_EL0 – that specifies the currently allowed access rights, Read, Write, eXecute (R/W/X), for each overlay domain ID. As depicted in Figure 1, POR_EL0 stores 16 permissions (4 bits for each domain over its 64-bit size). However, with the standard 64-bit page-table entries, the domain ID stored in the PTE is 3 bits wide, allowing only 8 different domain IDs and, therefore, only Perm0 –Perm7 to be used. The remaining entries, Perm8 –Perm15 , are reserved in this configuration [7]. In practice, this means that 8 domain permissions can be configured simultaneously. The position of the bits in the layout of POR_EL0 defines the domain ID for the enforcement of that permission. For example, permissions for the domain of ID 7 ( Perm7 ) are stored in bits 28 to 31. When a memory page is created, its PTE is annotated with the protection domain to which the page belongs. POE encodes this domain using four PTE bits that identify the page’s overlay index. On each memory access, the processor enforces both the regular page-table permissions and the active POR_EL0 configuration for the overlay index encoded in the target page’s PTE. The effective permission is there-fore the intersection of the conventional MMU permission and the POE permission selected by that page’s domain ID. These checks occur in hardware, yielding minimal runtime overhead. This is illustrated in Figure 2. As a result, multiple isolated domains can share the same virtual address space. 

Fast Domain Switching. A key feature of POE is the abil-ity to reconfigure domain permissions through a simple and lightweight register update to POR_EL0 in user-space, rather than requiring kernel mediation. Overwriting POR_EL0 when switching execution contexts within a process redefines the access permissions of each domain in one instruction. The in-struction msr (Move to System Register) must always be used to set POR_EL0 . Therefore, application code can be statically inspected at loading time to ensure that unprivileged exe-cutable domains do not contain instructions with structure such as msr POR_EL0 <X> , that would overwrite POR_EL0 

illegally. Because POR_EL0 updates occur entirely in user-space, domain transitions are significantly faster, enabling otherwise impractical isolation models. Since Linux 6.12, arm64 provides upstream support for the POE with the pkey_* system-call family and assign pagess to a specific domain using pkey_mprotect(addr, len, prot, pkey) . In this model, Linux exposes this func-tionality through the standard pkey abstraction.

3.1 System Model 

We assume that the underlying device system features an ARM architecture equipped POE (see POE details in Sec-tion 2.3). Furthermore, we assume that the system features 3Figure 2. POE Access Check. This model is consistent with typical client-side edge devices running ARM Cortex-A processors, such as mobile phones, laptops, IoT devices, etc. We further assume that the device’s layered attestation (a.k.a. platform integrity) mechanism is properly implemented by the vendor. 

3.2 Adversary (Adv) Model 

We assume a user space Adv capable of compromising appli-cation level components within a process, e.g., via memory corruption to attempt to launch attacks (such as code injec-tion, control, and data flow attacks), while the underlying hardware (including POE enforcement and MMU) is trusted. Once checked by the underlying platform integrity measure-ment system (e.g., Google Play Integrity, Apple App Attest, etc. – recall Section 2.2), the kernel can be trusted. This is not an additional assumption: it is always required by process-based user space isolation, regardless of ARA. The attacker may attempt to read or tamper with sensitive data, escalate privileges within the process (i.e., into ARA), or interfere with security services implemented by ARA, including in-voking illegal instructions, abusing ARA calls/entry points, or attempting to reconfigure domain permissions. However, Adv cannot directly bypass hardware-enforced permission checks. Microarchitectural side-channels [14, 15, 32, 37] are treated as orthogonal since they are mitigated by the under-lying CPU micro-architecture [6]. 

3.3 Goals 

[G1 ] Run-time trust retention. Once the platform in-tegrity mechanism has accepted the expected ARA-enabled application configuration and ARA has completed its trusted initialization, subsequent ARA-generated security outputs must remain attributable to that protected run-time instance despite Adv compromise of the application (App). [G2 ] Integrity of run-time measurements. For an RTM, the run-time evidence produced by ARA must faithfully reflect the run-time state processed by the RTM logic. In particular, Adv controlling App must not be able to tam-per with the measurement logic, corrupt the measurement state, or forge run-time evidence that would be accepted as legitimately produced by ARA. [G3 ] Confidentiality and integrity of ARA data. Sensi-tive data managed by ARA must remain protected from Adv. In particular, Adv must not be able to directly read/write security-critical data protected within ARA. [G4 ] Execution integrity of ARA. ARA must execute only intended functionality. Specifically, Adv may interact with ARA only through valid service calls and must not be able to alter their execution (e.g., via unintended control flows that bypass validation logic or cause ARA to return through an unauthorized exit. 

3.4 Non-Goals 

ARA is designed to establish a run-time anchor within an already load-time attested user space process. Its objective is to enable trusted measurement and security services that are isolated from, yet able to efficiently interact with, an untrusted application. Consequently, the following goals fall outside the scope of this work. 

Protection against an attested yet compromised platform. 

ARA assumes the integrity of the underlying platform, in-cluding the hardware, firmware, boot chain, attested operat-ing system kernel, and the platform attestation mechanism used to bootstrap trust (i.e., attest the kernel and loaded application). This is in line with current platform integrity services discussed in Section 2.2. 

Replacing TEEs. ARA is not intended to replace TEEs such as TrustZone [8] and SGX [29]. TEEs protect applications from a potentially untrusted platform by providing isolated execution environments and hardware-backed confidential-ity guarantees. In contrast, ARA builds upon layered attesta-tion systems (see Section 2.2) commonly found in mobile and edge devices to protect trusted run-time services from a com-promised application while remaining within the applica-tion’s address space. The two approaches are complementary and address different threat models. 

General-purpose compartmentalization. The goal of ARA is not to provide a generic multi-compartment isolation frame-work. Rather, it establishes a small privileged attested appli-cation substrate that functions as a run-time RoT for the host process. While POE could support broader compartmental-ization designs, exploring scalable multi-domain isolation policies is outside the scope of this work.

4.2 POE Access Control at Run-Time 

As mentioned above, POE is also configured by ARA before App can execute. Specifically, the process address space is partitioned into three POE-protected domains: DOM0 for ARA itself (trusted code), DOM1 for controlling ARA invo-cation, and DOM2 for App (untrusted code). Table 1 summarizes the POE configurations performed by ARA. Each row specifies the active POR_EL0 access-control configuration applied when code executes in a given domain (the subject domain), while each column indicates the ac-cess permissions to another domain (the object domain). For example, when App code executes, POR_EL0 is configured ac-cording to the DOM2 row. This configuration prevents App from directly accessing ARA while still allowing execution to enter DOM1, which serves as ARA’s legal entry point. Second, ARA registers a seccomp-BPF filter [57] with the kernel. The idea is similar to that used in [64] but adapted for ARA’s requirements. The filter intercepts syscalls issued by App and redirects potentially dangerous ones to ARA DOM0 for arbitration at run-time. Dangerous syscalls include those modifying memory mappings or indirectly violating POE permissions. We discuss them in more detail in Section 5.3. After completing the setup, ARA switches to the DOM2 transfering control to App’s first instruction (e.g., its main 

function) to start App execution. App executes normally until it issues a syscall or ARA call, shown by transitions (1) and (i) in Figure 3, respectively. A syscall is first checked by the seccomp-BPF filter in-stalled at load time. Inoffensive syscalls proceed through normally; whereas dangerous system calls are redirected to ARA together with their arguments, allowing ARA to per-form additional checks before deciding whether or not to perform this syscall. App may also invoke ARA services at any point during run-time. As App executes under the DOM2 configuration, it cannot directly jump into ARA in DOM0 (per Table 1). The only permitted path into ARA is through the dedicated ARA contolled invocation in DOM1, for which DOM2 has execute permission. 4.3 ARA Instantiations 

Beyond the basic initial configurations, the ARA domain also implement configurable (and load-time attestable) trusted computing services that can be securely called as described in Section 4.2. 

Secret Provisioning 

ARA further supports a provisioning mechanism for re-ceiving secrets from an external trusted party (e.g., an ap-plication server or another process) which we refer to as the Provisioner. This mechanism combines ARA with the underlying hardware-backed integrity attestation platform to let the provisioner verify that the process was initialized with the expected code and system configuration. ARA can obtain platform-integrity evidence for the ini-tialized process and associate this evidence with an ARA-controlled provisioning endpoint. ARA can then forward the evidence to the Provisioner (a.k.a. Verifier), which verifies the evidence against the expected load-time state, including the expected ARA code, App code, and provisioning end-point. Upon successful verification, the Provisioner encrypts a secret to the ARA-controlled in-process endpoint and sends it back to ARA. Recall from Section 2 that integrity attesta-tion platforms can be used to provision a public key to the attested end-point. As a result, the secret is provisioned into ARA in DOM0 and never exposed directly to App in DOM2. We note that the exact mechanism by which the provisioning endpoint is bound to platform-integrity evidence depends on the underlying platform. Details are discussed in Section 5.5. 

RTS Instantiations 

From the provisioning mechanism for delivering secrets into the protected ARA domain discussed above, what re-mains for instantiating ARA as an RTS is to implement the logic for protecting and using these secrets for confidential-ity purposes. In particular, RTS services must ensure that provisioned secrets remain within DOM0 and that outputs returned to App through ARA calls (mediated by DOM1 con-trolled invocation) reveal only the intended result, not the underlying secret or unintended functions of the secret. This allows App to use provisioned secrets indirectly through ARA in-process calls, without directly accessing them. For example, an RTS service may use a provisioned master se-cret to decrypt application-specific secrets or derive session keys, while keeping the master secret inaccessible to App. In Section 7.1, we present a concrete case study in which ARA-based RTS uses a provisioned master secret to support protected decryption for video streaming. 

RTM Instantiations 

Instantiating ARA as an RTM requires defining what run-time state should be measured and how that state is delivered to ARA. This typically requires modifying (e.g, via instru-mentation) App to collect and forward the relevant runtime state to ARA through the ARA calls. Once control reaches ARA, the RTM-specific measurement logic measures/extends the received runtime state and then resumes App execution. In a typical end-to-end flow, the application server first uses the provisioning mechanism at launch to verify the pro-cess’s load-time state and establish a signing key with ARA. For RTM, this verification also confirms that the expected App instrumentation was present at load time (in addition to ARA trusted domain). Later, during process execution, the server can request runtime evidence from ARA. ARA generates a report from the runtime events collected through the deployed instru-mentation, signs it using the provisioned signing key, and sends the signed evidence to the server. We present a con-crete RTM case study in Section 7.2. 

## 5 Design Details 

5.1 Bootstrapping and measuring ARA TCB within a process 

ARA configuration must be securely bootstrapped and mea-sured within the process before App starts and within the same process. An ARA user-space loader is the first to exe-cute on creation of an ARA process. At launch, the standard platform integrity mechanism can be used to measure the loader as part of the initially created process. The loader (which is also measured in the previous step) is preconfig-ured with a known-good hash of the code expected to run within ARA trusted DOM0. Before loading any code, the loader verifies the hash of the code to be loaded against the known-good value. As a result, trust in the measured loader extends to the code loaded within ARA, effectively creating a layered measurement chain for the process, similar to the trust chains used in secure boot architectures [4]. The loader first loads an ARA service library (namely 

libara.so ) and hands control to its constructor. Since libara.so 

has been verified, its constructor is trusted to complete the re-maining initialization. This trusted constructor performs the following: (i) verify the loaded App and the ARA entry point against expected hashes, (ii) scan App’s executable pages and rewrite illegal POR_EL0 instructions (Section 5.2), (iii) install the seccomp-BPF filter (Section 5.3), and map/tag the POE domains for the ARA entry point (DOM1) and App (DOM2). After these steps, ARA transfers control to App. From this 6point on, App execution is unprivileged, and DOM0 is reach-able only through controlled invocation points (Section 5.4) or through fault/exception handling (Section 5.3). The resulting trust chain begins with the platform-integrity mechanism authenticating the expected ARA-enabled appli-cation and platform state. The ARA-aware loader then ver-ifies the ARA run-time components, including libara.so ,the ARA entry point, and App, before untrusted execution begins. In this way, trust established at the platform level is extended to the specific in-process ARA configuration. During provisioning, this chain allows the Provisioner to accept an ARA-controlled endpoint only when it is associated with the expected authenticated application configuration and the ARA components verified during initialization. ARA therefore does not require the underlying platform-integrity service to directly measure individual ARA components or to be modified to support ARA. Instead, component-level verification is performed by the trusted ARA loading chain. 

5.2 Load-Time Binary Analysis of App. 

At load time, ARA statically inspects all executable App code and removes every instruction that can write to POR_EL0 .This approach is necessary because POR_EL0 is writable from userspace (EL0), allowing an untrusted App to modify its own permissions by executing msr POR_EL0, Xn (Xn de-notes an arbitrary source register). Since AArch64 instruc-tions are fixed-width and 4-byte aligned, the ARA construc-tor walks each word-aligned address in every executable region, matches the fixed opcode and system-register encod-ing of msr POR_EL0, Xn while masking the source-register field, and replaces each match with a NOP. This simplifies instruction filtering compared to x86, where instructions are not aligned. To prevent such instructions from being introduced after the initial scan, ARA also mediates all transitions that create or modify executable memory, including side-loaded code and JIT-generated code. Any request from the untrusted App (DOM2) to make memory executable, such as a JIT promoting an RW page to RX , is trapped and serviced only after ARA maps the page read-only, scans it, and patches any prohibited instruction. Thus, no DOM2-executable page can contain an instruction that writes to POR_EL0 .

5.3 Syscall Filtering and Mediation 

The POE domain configuration prevents App from directly accessing ARA’s protected memory, However, App may still invoke kernel interfaces that indirectly violate the isolation boundary. For example, a compromised App could ask the kernel to change page permissions, retag PTEs, or copy data from/to DOM0 memory. ARA adopts the syscall-mediation approach and classification of security-sensitive kernel in-terfaces established by prior work [51, 54, 59, 64]. During initialization, ARA installs a seccomp-BPF filter that intercepts security-sensitive syscalls originating outside ARA’s code region. These include syscalls that can modify address space or protection state, affect POE domain assign-ments, or allow the kernel to access protected DOM0/DOM1 memory on App’s behalf. Intercepted App syscalls are redi-rected to ARA, which validates their arguments before allow-ing or rejecting the operation. Signal delivery and return are similarly mediated, following the general approach of prior MPK-based isolation systems, to prevent App from regaining control with an unauthorized POR_EL0 configuration. To avoid the additional seccomp trap and signal-handling overhead for frequently invoked syscalls, ARA also exposes a syscall service through its controlled invocation interface. App passes the syscall number and arguments directly to ARA, which applies the same validation policy and, if per-mitted, issues the syscall from DOM0 on App’s behalf. Thus, the fast path changes only how the syscall request reaches ARA, it does not weaken the syscall-mediation policy. 

5.4 Controlled Invocation 

All RoT services are implemented inside libara.so and execute in DOM0. However, App cannot invoke these ser-vices directly since DOM2 has no execute permission over DOM0. Instead, App must enter through the ARA entry point, whose code is placed in DOM1. We expose the ARA en-try point through the interface secure_call(FUNCTION_ID fid, void *arg) that can be accessed by App, where fid 

identifies the requested service with input arguments in arg .As shown in Listing 1, the entry point saves the App context, switches POR_EL0 to the DOM0 configuration, and executes a memory/instruction barrier ( isb ) to make the new permissions effective. Afterwards, the control is trans-ferred to the trusted dispatcher, which switches the stack pointer to DOM0 stack, validates the requested service and its arguments, and invokes the corresponding function.

The server validates the attestation object against Apple’s trust chain, checks that the attested key is bound to the expected App ID, and extracts the attested public key 𝑝𝑘 𝐷 0. The server accepts only if the attestation object is valid for the expected App ID. On success, the server encrypts the secret using 𝑝𝑘 𝐷 0.

## 6 Security Analysis 

We first argue that invariants IV1 -IV7 (defined below) hold during process execution. Then, we show them sufficient to achieve security goals G1-G4 defined in Section 3.3. [IV1 ] No POE misconfiguration by App. App-controlled executable pages in DOM2 cannot contain instructions that modify POR_EL0 . This follows from the load-time binary anal-ysis (Section 5.2) and syscall mediation preventing unchecked executable-code injection at run-time (Section 5.3). Writes contained in the fixed DOM1 transition sequence are handled separately by IV3 .[IV2 ] App always resumes with DOM2 privilege. When-ever control is transferred to App, the active POE access configuration corresponds to DOM2. This holds at load time, when ARA installs the DOM2 configuration before starting App, and at run-time, when ARA restores the DOM2 configu-ration before every return from DOM0 (Section 5.4) or when delivering a mediated signal/exception to App (Section 5.3). [IV3 ] No direct App → ARA control transfer. App cannot directly execute DOM0 code. Any successful transfer from App into DOM0 must pass through the DOM1 entry point, and from DOM 1 only the fixed DOM0 entry instruction. Ar-bitrary entry within DOM1 cannot result in App-controlled execution with DOM0 permissions (Section 5.4). [IV4 ] Mediated dangerous syscalls. Any DOM2-issued syscall that could access DOM0 (with R/W/X) or DOM1 (R/W) memory or modify MMU/POE permissions or meta-data is denied by ARA. This is realized using the seccomp-BPF filter described in Section 5.3. [IV5 ] Mediated asynchronous control flows. All user-space signal and exception deliveries are first routed to ARA. ARA validates the event, installs the DOM2 POE configura-tion before exposing it to App, and mediates signal return so App cannot restore a non-DOM2 configuration. This is en-forced by ARA’s signal-delivery and signal-return mediation, as described in Section 5.3. [IV6 ] Trusted service correctness. ARA and RoT service handlers are trusted and assumed to be implemented cor-rectly. In particular, they must be memory-safe, validate App-provided inputs before use, and return only outputs permitted by the service policy. This is a standard trusted computing/RoT assumption (Section 3). [IV7 ] Load-time binding. The platform-integrity mecha-nism authenticates the expected ARA-enabled application and platform configuration. Before untrusted App execu-tion begins, the ARA-aware loading chain verifies the ARA run-time components, including libara.so , the ARA en-try point, and App. Together, these steps bind the provi-sioning/signing endpoint to the expected initialized ARA process. 

6.1 G1: Run-time Trust Retention 

We first establish that the trust established during ARA ini-tialization remains valid after App becomes adversarial. IV7 

ensures that the initialized ARA instance, entry point, and App correspond to the expected load-time configuration. After initialization, IV1–IV5 preserve the ARA boundary. App cannot enable unauthorized POE permissions, execute DOM0 directly, indirectly modify ARA through dangerous kernel interfaces, or use asynchronous control flow to re-sume with elevated permissions. IV6 also requires individual RoT services to protect their own trusted state and validate untrusted input. 

6.2 G2: Integrity of Run-time Measurements 

For an RTM instantiation, the measurement logic and mea-surement state reside in DOM0. IV7 rules out the goal’s violation at load-time, e.g., replacing App, removing instru-mentation, or using an unexpected ARA instance. 8At this point, the remote server knows that the expected App code (with instrumentation, e.g., RoT-relevant calls, see Section 7.2 for examples) is loaded. What remains to be shown is that with instrumentation in place Adv cannot tamper with measurement at run-time. This violation can be done by: (1) directly modifying the RTM state or logic in DOM0; (2) forcing ARA code to execute along an unintended path; (3) leverage syscalls to modify measurement state or permissions; (4) abuse signals/exceptions to deviate control flows bypassing instrumentation; or (5) trick an RoT service into corrupting state or producing forged evidence. Case (1) is blocked by IV1 and IV2 since these two invari-ants together imply that at any point, App only has access to DOM2 configuration and thus cannot directly modify the RTM state/logic in DOM0. We argue how (2) is prevented as part of G4 arguement below. Protection from (3), (4) and (5) directly follow from IV4 , IV5 and IV6 , respectively. There-fore, ARA design satisfies G2 .

6.3 G3: Confidentiality and Integrity of ARA Sensitive Data 

For an RTS instanciation, sensitive data is stored inside DOM0. By compromising App, Adv can attempt to access or modify such data in three ways: (1) directly from App in user space, (2) indirectly through kernel syscalls, or (3) through an authorized ARA service call. (1) is prevented by IV1 and 

IV2 ; without a valid DOM0 configuration, App in DOM2 has no means to access data inside DOM0. (2) is prevented by IV4 , which denies or mediates DOM2 syscalls that could access or modify DOM0 memory. Finally, (3) is limited by the execution integrity of ARA (see below in G4 argument) and by IV6 , where a valid call to ARA services returns only out-puts permitted by their service policy, and therefore do not reveal the underlying protected secrets. Thus, ARA design satisfies G3 .

6.4 G4: Execution Integrity of ARA 

G4 requires that App cannot force ARA to execute along unauthorized paths. At run-time, Adv can attempt this in three ways: (1) directly transferring control from App to DOM0 code; (2) leveraging syscalls to modify code, permis-sions, or execution state in DOM0; or (3) abusing asynchro-nous control flow, such as signals or exceptions. (1) is prevented by IV3 . Any transfer from App to DOM0 must pass through the DOM1 entry point, whose only trans-fer into DOM0 targets the fixed dispatcher ara_secure_call .Thus, App cannot choose an arbitrary DOM0 instruction as the entry target or directly enter the middle of an ARA func-tion. Although App may branch to an arbitrary instruction within the DOM1 entry point, this cannot result in App-controlled execution with DOM0 permissions. Before the 

msr that updates POR_EL0 , the DOM2 configuration remains active. If App enters after the msr , the DOM2 configura-tion likewise remains active, and the subsequent transfer to DOM0 faults because DOM0 is not executable. App may also enter directly at the msr with an attacker-controlled value in the source register. However, after this instruction, the only instructions before entering DOM0 are the isb and a direct branch to the fixed ara_secure_call 

dispatcher. Therefore, if the resulting configuration does not permit DOM0 execution, the transfer faults; if it does, control necessarily switches to the trusted DOM0 dispatcher before any App-controlled instruction can execute. Asynchronous signals or exceptions occurring during this transition are covered by IV5 , which ensures that control is returned to App only under the DOM2 configuration. (2) is prevented by IV4 , which denies or mediates DOM2 syscalls that could tamper with ARA code, permissions, or execution state. (3) is prevented by IV5 , since signals and ex-ceptions are routed to ARA first and are delivered to App only after validation under the DOM2 configuration. Therefore, App cannot hijack the ARA entry point, enter the middle of an ARA function, skip validation logic, or force unauthorized partial execution of ARA code, satisfying G4 .

## 7 Prototype and Evaluation 

Since POE is not yet available in commercial devices, we construct two complementary prototypes: (1) a QEMU in-stance implementing full POE support on a modified ARM Cortex-A76 processor model, and (2) a physical ARM Cortex-A76 processor. In case (2), we replace each msr instruction that writes to POR_EL0 with an msr instruction that writes to NZCV instead, while keeping required memory barriers. Because the written NZCV value is never used during exe-cution, this substitution preserves program behavior while accounting for the cost of the register update on App ↔ARA transitions.

If this component is appropriately isolated (a separate process in Widevine L3 path), this prevents a compromised host application from accessing the cryptographic keys or the media in plaintext. ## 8 Discussion and Limitations 

Multi-Threading. Our prototype assumes serialized ARA execution / single-threaded App execution. To support multi-threaded applications, ARA run-time must be made thread-safe by protecting shared ARA state with appropriate syn-chronization primitives. At the architectural level, POE per-missions are maintained as part of each thread’s state and are automatically saved and restored by the kernel during context switches. As a result, each thread retains its own POE permission state when scheduled. 

Multiple ARA Instances in One Procces. Our discus-sion thus far considers one ARA instance per process. Since POE supports eight simultaneously configurable domains, the remaining domains could host additional mutually dis-trusting domains. For example, an RTS holding cryptographic keys could exist in one domain, and an RTM holding mea-surement state in another, without mutual trust. This would require extending the access-control matrix of Table 1 and allocating services (syscall mediation, secret provisioning, etc.) as appropriate for the particular setting of interest. 

JIT and Dynamic Code. ARA design supports JIT and dynamically loaded code by mediating syscalls that makes memory executable (Section 5.2). Any DOM2 request to pro-mote a page to executable is trapped, after which ARA maps the page read-only, scans and patches any illegal POR_EL0 

writes, and only then retags it as executable DOM2 memory. This preserves invariant IV1 at the cost of one run-time pass on the binary being dynamically loaded. 11 Figure 5. Overheads of RTS case on QEMU. 

## 9 Related Work 

In practice, most current edge systems rely on classic inter-process isolation or TEEs. Regarding research, POE is very re-cent, and we are aware of only one preprint – NanoZone [38] – that focuses on it. NanoZone extends support beyond the eight domains available in POE by re-labeling PTE domain IDs (a limitation noted in Sec. 9), trading off performance for scalability (i.e., increased number of domains). Outside the POE-specific space, our work relates to several domains. 

User-Space Trusted Computing. Current mainstream approaches to verify user-level process properties (notably Linux Integrity Measurement Architecture [13, 21, 50], An-droid’s Play Integrity API [24, 28, 44, 66], and Apple App Attest [2]) are restricted to the static state of the process at loading time (essentially attest that the binary has not been illegally modified) without support for measurement of run-time state. This is largely due to the complexity of measuring run-time state from outside the process. Our work bridges this gap by enabling an in-process RoT for run-time verifi-cation and run-time security services. We emphasize that enclaved execution systems such as Intel SGX [16, 20, 65], SANCTUM [17], Keystone [35], etc., do not fall under our definition of in-process RoTs. They establish confidential and remotely attestable code segments (enclaves) within processes based on hardware RoTs. While they support out-sourced confidential computation, these are not privileged with respect to the process itself and cannot implement the same type of services that integrate with layered system-wide attestation systems such as the abovementioned (thus differing from our goal). 

Software-Based Approaches. Related to isolation, in-process software-based compartmentalization techniques aim to constrain the impact of software vulnerabilities by restricting how different parts of a program interact and by enforcing boundaries during execution. Memory safety approaches [11, 42, 49, 62] attempt to eliminate vulnerabili-ties that could lead to control- or data-flow attacks and data corruption before deployment. This is commonly achieved ei-ther through programming languages that integrate memory safety by design, such as Rust [41], which uses static compile-time analysis, ownership, and borrowing mechanisms to en-sure temporal and spatial safety, or through memory-safe dialects of existing languages, such as Checked C [18], which augments C with safer pointer and array types and intro-duces spatial safety checks during compilation and run-time. A complementary line of work focuses on hardening code against exploits with mechanisms such as CHERI [61] (which requires hardware support and typically recompilation), soft-ware fault isolation [26, 30, 60, 63], memory layout random-ization [52], and control-flow integrity (CFI) [45]. Unlike this work, these techniques focus on strengthening code rather than constructing isolated in-process RoTs. 

User-Space Memory Protection in x86. Intel Mem-ory Protection Keys (MPK) [46] provides in-process access-control mechanisms resembling POE in more complex x86 architectures. ERIM [58], Hodor [27], and Secpoline [54] isolate state in x86 using MPK. Other notable approaches on MPK include extending MPK’s limited domain count us-ing virtualization [25, 46] (similar to NanoZone’s case in POE); enforcing heap metadata [12] and cross-language[31] integrity; and intra-unikernel isolation between trusted and untrusted boundaries [55]. To improve on MPK and similar technologies, approaches such as LatticeBox [19] investigate efficient ways of representing domain IDs to make domain transitions faster and domain ID representations more effi-cient, allowing fewer bits to represent more domains within a PTE. Prior systems used MPK primarily for protecting li-braries or compartments. Further, x86 deployments do not feature platform integrity services, e.g. Google Play Integrity, Apple App Attest (see Section 2.2). This results in an orthog-onal design space and set of goals: (1) establishing in-process RTM and RTS building upon platform/loadtime trusted com-puting, and (2) enabling these services on (predominantly ARM-based) edge/client devices. 

HW/SW Co-Designs for Memory Access Control. CC-TAG [39] proposes integrating multiple disjoint memory safety mechanisms into a unified system. More recently, Lattice-BOX [19] introduced a scheme for representing mem-ory permissions that improves both the expressiveness of memory domains and the efficiency of domain switching by reducing reliance on memory barriers on Intel MPK-like systems. These efforts complement our work but focus on different aspects of execution/metadata storage optimization.

## 10 Conclusion 

We presented ARA, a mechanism for extending trust estab-lished by platform integrity mechanisms into applications. ARA design eliminates the need for costly process, kernel, enclave, or hypervisor transitions traditionally required for application-level trusted computing services, enabling prac-tical run-time roots of trust for measurement and storage on ARM-based edge and mobile devices. Our case studies and evaluation demonstrate that ARA can support security services such as run-time integrity measurement and pro-tected secret handling with substantially lower overhead than conventional isolation approaches. More broadly, our results suggest that memory-permission mechanisms can bridge the long-standing gap between load-time user-space attestation and efficient run-time verification.
