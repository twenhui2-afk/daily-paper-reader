JI WANG, National University of Defense Technology, China Mature numerical libraries can still lose many bits of accuracy on localized ill-conditioned inputs, such as roots, poles, cancellation points, and branch boundaries. Existing repair systems can localize such regions and synthesize patches, but strict error thresholds often force many small pieces, long repair times, or large generated code. This paper presents NPTaylor, a Taylor-approximation-based repair framework for localized high floating-point errors in numerical C routines. Given a high-error input and a localized repair domain, NPTaylor searches over Taylor degree, expansion center, segmentation, and floating-point evaluation strategy. It emits guarded C patches that call the original routine outside the localized domain and accepts a patch only after validating the emitted C code on the recorded repair-domain samples, endpoints, and pre-repair peak input. The generated Taylor evaluator uses coefficient splitting and compensated Horner evaluation to reduce the evaluation error introduced by the patch itself. On a 38-function one-input GSL workload, both NPTaylor and AutoRNP repair all 114 configurations across three accuracy thresholds. NPTaylor is 3.33 × faster by geometric-mean offline repair time and emits 0.162 × as many C bytes. In the strictest setting, the median repair time is 3.74s for NPTaylor and 81.97s for AutoRNP; the largest paired repair-time speedup is 157.1 ×, and the largest strict patch is 47.5KB for NPTaylor versus 5.90MB for AutoRNP. The repaired-code runtime matrix gives NPTaylor an overall geometric-mean speedup of 1.56 ×

over the unpatched implementations, compared with 1.35 × for AutoRNP. NPTaylor also repairs localized multi-input benchmark cases beyond AutoRNP’s implemented one-input workflow, with 15/23 strict and 18/23 looser configurations repaired. These GSL results test the general repair method on library routines with known high-error regions; they are local validation claims over the checked repair domains, not full-domain proofs of the original routines. Additional Key Words and Phrases: floating-point arithmetic, numerical programs, automated repair, GSL, Taylor approximation, compensated evaluation 

1 Introduction 

Numerical libraries are small pieces of code with unusually large responsibility. Their functions sit beneath scientific computing, optimization, simulation, sparse linear algebra, and machine-learning workloads, and their numerical behavior can affect both accuracy and reproducibility [8, 9, 22, 30, 43, 47]. The hardest failures are often not spread uniformly over the input space. A mature routine may be accurate on most inputs but lose many bits near a root, pole, cancellation point, or branch boundary. For users, these localized failures are still library failures: the routine returns

a representable value far from the high-precision oracle-rounded result on inputs that the API accepts. Prior work has made high-error detection and repair increasingly automatic. ATOMU [60] detects high-error inputs using atomic conditions, and FPCC [57] uses chain conditions to find inputs that trigger large floating-point error. AutoRNP [56] repairs high floating-point errors in numerical libraries by localizing suspicious regions and searching for source-level patches. This is the closest baseline for our local-repair setting, and its published artifacts support a matched GSL evaluation, but strict thresholds can make its repair search expensive and its emitted patches large. In our strict repair experiment, AutoRNP repairs gsl_sf_bessel_Y1 only after 9788.39s and emits a 403KB patch for one localized interval; NPTaylor repairs the same row in 139.23s with a 2.1KB patch. This paper presents NPTaylor, an automated framework for repairing localized high floating-point errors in numerical C routines with generated Taylor programs. The input to NPTaylor is a high-error record, an original C routine, a high-precision oracle policy, a localized repair domain, and an error threshold. The output is a guarded C patch: 

if 𝑥 ∈ 𝐷 then 𝐸 𝐷 (𝑥 ) else 𝑃 0 (𝑥 ),

where 𝑃 0 is the original implementation and 𝐸 𝐷 is a generated Taylor evaluator for the localized domain 𝐷 . The repair preserves the original path outside the guard and replaces only the high-error region. NPTaylor accepts the patch only after checking the emitted C program, including coefficient literals, floating-point operation order, guard conditions, and fallback behavior. Taylor approximation is useful here not because it is new, but because it matches the locality of the repair problem. On a small interval or box, a high-precision Taylor expansion around a selected center gives a compact numerical form; the center, degree, and segmentation expose a small search space; the same representation covers one-input intervals and multi-input boxes; and fixed evaluation orders such as Horner and EFT–Horner map directly to compact C. The generated expression is tied to the mathematical semantics of the target function rather than only to a syntactic rewrite of the existing implementation: on the selected domain, NPTaylor approximates the high-precision oracle and then validates the resulting floating-point program against the repair threshold. The key boundary is that NPTaylor is a validation-driven repair system, not a full-domain proof system. Its repaired patches are checked on deterministic local validation sets that include sampled points, guard endpoints, and the pre-repair peak input. A successful repair therefore means that the emitted patch satisfies the stated threshold on the recorded validation set for the localized domain; it does not prove continuity across piece boundaries or a full-domain error bound for the original routine. We evaluate this general repair method on baseline-aligned GSL workloads. On a 38-function one-input repair workload, both NPTaylor and AutoRNP repair all 114 configurations across three accuracy thresholds. NPTaylor is 3.33 × faster by geometric-mean repair time and emits 0.162 × as many C bytes. In the strictest setting, median repair time is 3.74s for NPTaylor versus 81.97s for AutoRNP, the largest paired repair-time speedup is 157.1 ×, and the largest strict patch is 47.5KB for NPTaylor versus 5.90MB for AutoRNP. The repaired-code runtime matrix also favors NPTaylor in aggregate: overall geometric-mean speedup over the unpatched implementations is 1.56 × for NPTaylor and 1.35 × for AutoRNP. NPTaylor also repairs multi-input benchmark cases, a setting outside AutoRNP’s implemented one-input workflow; it directly repairs up to 18/23 evaluated multi-input cases.

2 Background 2.1 Floating-Point Error for Repair 

Floating-point implementations approximate real-valued mathematical functions with finite preci-sion operations [22, 27, 28, 47]. A binary floating-point format F has precision 𝑝 and a bounded exponent range. A finite normalized value has the form

where 𝑠 is the sign bit and 𝑒 is an exponent in the format range. Subnormal values use the minimum exponent with a leading significand bit of zero. The format also contains signed zeros, infinities, and NaNs. We use a high-precision oracle 𝑓 oracle as the mathematical reference for a target function, following the common use of multiple-precision libraries as reference implementations [18]. 2.2 Localized Repair 

Localized floating-point repair has three roles. A detector finds high-error inputs; a localizer expands such an input into a repair domain where the problem recurs; and a repair backend synthesizes code for that domain. AutoRNP uses perturbation-based testing (PTB) to localize intervals and then emits source-level patches for the localized region [56]. NPTaylor reuses this localization interface for a baseline-aligned comparison: both systems repair the same localized domains and are compared on the generated backend time, patch size, post-repair sampled error, and patched-code runtime. A guarded repair has the form 

𝑃 patch (𝑥 ) =

(

𝐸 𝐷 (𝑥 ) 𝑥 ∈ 𝐷, 𝑃 0 (𝑥 ) 𝑥 ∉ 𝐷, 

where 𝐷 is the localized repair domain, 𝐸 𝐷 is the generated evaluator, and 𝑃 0 is the original implementation. This form localizes behavioral change to the suspicious region. It also makes the validation boundary explicit: post-repair claims are about the checked inputs inside the guard, while the outside path is the original routine plus guard overhead. 

2.3 Error-Free Transformations and Compensated Evaluation 

Error-free transformations (EFTs) expose the rounding error of a floating-point operation as an explicit floating-point residual [17, 38]. For addition, TwoSum returns a rounded sum and a compensation term: 

(𝑠, 𝑒 𝑠 ) = TwoSum (𝑎, 𝑏 ), 𝑠 = fl (𝑎 + 𝑏 ), 𝑠 + 𝑒 𝑠 = 𝑎 + 𝑏, 

assuming the operation does not overflow and the standard conditions for the transformation hold. For multiplication, TwoProd similarly computes 

(𝑝, 𝑒 𝑝 ) = TwoProd (𝑎, 𝑏 ), 𝑝 = fl (𝑎𝑏 ), 𝑝 + 𝑒 𝑝 = 𝑎𝑏. 

Dekker’s construction obtains the product residual by splitting significands into high and low parts, while hardware fused multiply-add can compute the residual directly as 

𝑒 𝑝 = fma (𝑎, 𝑏, −𝑝 )

when FMA is available [5]. EFTs are useful for generated polynomial code because approximation error and floating-point evaluation error interact. A high-precision Taylor coefficient 𝑐 can be stored as a pair 

𝑐 ℎ = fl (𝑐 ), 𝑐 ℓ = fl (𝑐 − 𝑐 ℎ ),

so the emitted evaluator can use the high part in the main computation and feed the low part into a compensation path. In an EFT–Horner evaluator, each Horner multiply-add step records multiplication and addition residuals with TwoProd and TwoSum; the final value combines the main Horner result with accumulated residual terms. This improves the numerical behavior of the emitted Taylor evaluator, but it is still only a candidate construction: NPTaylor accepts a repair only after checking the emitted C patch.

4 Problem Formulation 

This section states the repair interface that NPTaylor must satisfy; the search procedure appears in section 5. NPTaylor does not infer repairs from arbitrary C code in isolation. A concrete repair instance is supplied by a detector/localizer front end and contains the original routine, localized domain, oracle policy, threshold, and validation policy. 

4.1 Domain-Conditioned Repair Interface 

Let 𝑃 0 be the original floating-point implementation and 𝑓 oracle be the high-precision mathemat-ical reference. A repair instance supplies a target floating-point format F, one or more localized construction domains Dloc , a checked validation set 𝐷 val , target C floating-point semantics 𝑆 𝐶 ,and an error threshold 𝜖 . The construction domains come from the repair front end, such as PTB localization around a high-error input; the validation set is the finite set on which the final emitted patch is checked. NPTaylor emits local evaluators 𝐸 1, . . . , 𝐸 𝑚 and composes them with ordered guards and the original fallback: 

𝑃 patch = 𝐶 repair [𝐸 1, . . . , 𝐸 𝑚 ].Taylor-Based Repair of Floating-Point Errors 7

For one domain 𝐷 , this context is 

𝐶 repair [𝐸 ] ( 𝑥 ) = if 𝑔 𝐷 (𝑥 ) then 𝐸 (𝑥 ) else 𝑃 0 (𝑥 ),

where 𝑔 𝐷 is the emitted guard for the localized domain. With multiple pieces, the guards are ordered and the fallback remains 𝑃 0. The checked object is the generated C program, not only the mathematical Taylor polynomial used to construct it. The common checker contract is: 

Check (𝑃 patch , Φrepair , 𝐷 val , 𝑓 oracle , 𝑆 𝐶 ) = pass .

4.2 Repair Acceptance Condition 

Using the ErrBits metric from section 2.1, the evaluated repair condition is 

Φrepair (𝑃, 𝑥, 𝑓 oracle ) ≡ ErrBits (𝑃, 𝑥 ) ≤ 𝜖. 

The checker applies this predicate to its finite recorded validation set. In our experiments, this set includes deterministic repair-domain samples, guard endpoints, and the pre-repair peak input identified before synthesis. A repair is reported only if the final emitted patch, including all guards and fallback paths, satisfies the threshold on this set. The construction domain and checked domain play different roles. Dloc guides Taylor construc-tion, guard generation, and subdivision; 𝐷 val is the evidence set for the reported result. The final claim is validation-relative: when NPTaylor reports success, it reports that the emitted patch passed the checker contract for the stated localized domain, validation set, oracle policy, threshold, and C semantics. 

4.3 Claim Boundary 

NPTaylor’s repair claim is local. It does not establish a proof over every representable input in the original routine, and it does not prove continuity between adjacent real-polynomial pieces. At a boundary, the emitted ordered guard selects one C path and the selected output is checked on the validation inputs that include guard endpoints. The repair experiments check the scalar returned value of the generated patch wrapper; they do not claim preservation of every auxiliary observable such as status codes, errno , or floating-point exception flags. These limits are intentional: they keep the paper’s evidence aligned with the checker actually used to accept patches. 

5 NPTaylor Design 5.1 Overview 

Section 4 defines the checker contract that NPTaylor must satisfy. NPTaylor searches for an executable Taylor program that satisfies this contract after being lowered to complete C. The pipeline has five stages: (1) Localize the high-error region. The front end receives a high-error record and uses PTB localization to construct an interval or box around the reported peak input. (2) Build a Taylor candidate. The builder fixes the expansion center, degree, and pieces selected by the policy and computes high-precision Taylor coefficients for the oracle target. (3) Fix the floating-point evaluator. The generator selects the evaluator shape, coefficient splitting, C literals, and operation order, thereby turning the mathematical approximation into a concrete floating-point program. (4) Emit guarded C. The evaluator is composed with guards and the fallback call to the original routine. (5) Check the emitted patch. The checker executes the exact C program that NPTaylor may return, rather than checking only its real-number polynomial. 8 Yi et al. 

A passing check produces a guarded repair patch. A failure returns sampled inputs whose errors still exceed the threshold, and the search policy refines the Taylor descriptor. Consequently, every refinement is validated after lowering to complete C. The loop communicates through a compact Taylor-program descriptor :

𝑞 = ⟨𝐵, 𝑎, 𝑑, 𝜎, 𝑔 𝐵 ⟩.

Here 𝐵 is the current construction region, 𝑎 is the expansion center, 𝑑 is the Taylor degree, 𝜎 is the fixed floating-point evaluator shape, and 𝑔 𝐵 is the emitted guard. The descriptor is not a separate specification language; it is the interface between three roles. The repair policy selects and refines 

𝑞 , the builder lowers 𝑞 to a complete C patch, and the checker alone decides whether the patch is accepted.

5.3 Taylor Candidate Construction 

For each descriptor, NPTaylor evaluates the high-precision oracle near the selected anchor and derives Taylor coefficients for the local target. The center is initially the detector-reported peak input because the peak is the most informative point in the localized region. After subdivision, the policy can reanchor a failed subdomain at the checker-reported difficult input or at the subdomain center. The emitted evaluator uses coefficient splitting and EFT–Horner. Each coefficient is rounded to a high part and a low residual. The high parts form the main Horner chain, while the residual terms from TwoProd, TwoSum, and low coefficients are accumulated and added back. The goal is not to prove a symbolic error bound for the Taylor expression; it is to produce a candidate whose actual floating-point execution has enough numerical headroom to pass the local checker. 10 Yi et al. 

5.4 C Emission and Validation 

After one or more local descriptors are accepted, NPTaylor emits a merged patch with ordered guards. Each guard selects the Taylor evaluator for its localized piece; inputs outside all guards fall back to the original routine. The final validation rechecks the merged patch rather than assuming that local acceptance remains valid after composition. This catches mistakes in guard ordering, coefficient literal emission, and fallback integration. Changing compiler flags, target ISA, floating-point environment, or validation policy can change the behavior of floating-point C. For that reason, NPTaylor’s acceptance decision is tied to the emitted source and the stated checking environment. A repair result is reported only after that concrete source passes the local validation contract. 

6 Implementation and Evaluation 6.1 Implementation 

We implemented NPTaylor as a prototype in Python, C, and C++. The Python orchestrator manages detection, PTB localization, search, candidate selection, and artifact generation; performance-critical oracle and validation paths use C/C++ with MPFR/GMP support [18]. The generator emits ordinary C patches with domain guards and fallback calls to the original routines. All validation and benchmarking use the emitted C source, not an idealized symbolic approximation. The implementation follows the workflow in section 5. The detector consumes high-error inputs reported by FPCC and uses AutoRNP’s PTB algorithm to localize a one-dimensional interval or a low-dimensional box around the reported peak. The deriver builds Taylor approximations over those domains and fixes the expansion center, degree, segmentation, and evaluation order. Repair candidates use coefficient splitting and EFT–Horner. The generator then emits a guarded patch and invokes the local checker on the concrete compiled wrapper. 

6.2 Evaluation Overview 

The evaluation is organized around two questions: 

RQ1 Repair effectiveness. Can NPTaylor repair localized high-error cases on GSL benchmark programs? 

RQ2 Repair quality and cost. How large are the generated patches, how long does repair take, and what runtime impact do the patches have? One-input repair is paired with AutoRNP on shared PTB domains. Multi-input repair is a NPTaylor-only capability study because AutoRNP does not support multi-input repair in its imple-mented workflow.

6.6 Limitations and Threats to Validity 

The repair checker is sampled and local. It validates the emitted patch on the recorded repair-domain samples, endpoints, and pre-repair peak input, but it does not prove the full surrounding original routine or continuity across adjacent pieces. The experiments also check the scalar return value, not all possible library side channels such as status codes, errno , or floating-point exception flags. Taylor polynomials are not the right representation for every localized failure. The gsl_sf_psi_1 

pole case requires factoring the dominant singular term before polynomial repair becomes effec-tive. This points to a natural extension: detect singular or rational structure and choose a local representation before applying the Taylor search. Finally, timing comparisons depend on compiler, platform, and input-stream construction. We report matched workloads, shared PTB domains, repeated timed calls, and geometric means, but the results should be read as evidence for the evaluated environment rather than as platform-independent constants. 

7 Related Work 7.1 Automated Floating-Point Repair and Accuracy Improvement 

Automated repair systems search for source-level or expression-level changes that improve a program’s behavior. General automated-program-repair techniques synthesize patches from tests, constraints, angelic values, learned correctness models, or search [32, 34, 35, 37, 52, 53]. For floating-point programs, prior work also finds inputs that expose high error or instability [11, 55, 59]. FPCC detects high-error inputs using chain conditions [57]; ATOMU uses atomic conditions [60]; FPGen uses symbolic execution to generate error-inducing inputs [24]; CoverMe targets high coverage for floating-point code [20]; and dynamic analyses localize or explain numerical instability and root causes [2, 4, 44, 49]. Herbie rewrites expressions to improve accuracy [39], while transformation and tuning systems change expression structure, precision, or mixed-precision assignments [13, 14, 30, 33, 43, 45, 51]. AutoRNP is our matched repair baseline because it targets numerical-library errors and supplies the same PTB-localized domains used in our comparison [54, 56]. Methodologically, ACESO and OFP-Repair are oracle-free repair tools that synthesize patches using only the original precision [48, 58]. However, both exclude ill-conditioned problems: ACESO explicitly places them outside its scope, while OFP-Repair rejects cases whose condition numbers exceed its threshold. The high-error GSL programs detected in our evaluation all exceed this threshold. In contrast, NPTaylor supports such ill-conditioned cases by using high-precision coefficients together with EFT-based transformations. 16 Yi et al. 

7.2 Polynomial Approximation and Library Implementation 

Taylor, Chebyshev, Remez, and minimax approximations are classical tools for mathematical-function implementation [1, 25, 29, 36]. Range reduction, table-driven reconstruction, and special-case handling are also standard ingredients in numerical libraries [36, 40, 50]. Horner and mul-tivariate Horner schemes organize polynomial evaluation efficiently [6, 7, 41], and compensated arithmetic, error-free transformations, and fused multiply-add can improve the behavior of floating-point evaluation [5, 17, 38]. NPTaylor uses these standard ingredients rather than proposing a new approximation theory. Its use of Taylor polynomials is local and operational: a Taylor expression becomes an emitted floating-point C fragment with a fixed evaluation order, an explicit guard, a fallback path, and a repair-specific checker. The contribution is the checked repair loop around this representation; the GSL experiments instantiate this loop on localized library errors and measure its repair cost and patch size against a matched baseline. 

7.3 Floating-Point Analysis and Verification 

Floating-point analysis tools, testing frameworks, and verification systems provide techniques for finding high-error inputs, bounding roundoff error, or checking numerical properties. Interval arithmetic, abstract interpretation, and static numerical analysis provide foundations for bounding numerical behavior [12, 15, 23, 26, 42]. FPTaylor uses symbolic Taylor expansions to estimate roundoff error and can emit proof certificates [46]. Gappa-style certification and verified numerical pipelines address proof obligations for floating-point code and approximations [3, 16]. Other work verifies or tunes floating-point and math-library code [10, 19, 31]. NPTaylor is complementary to this line of work. It is not a general-purpose floating-point verifier and does not emit proof certificates like FPTaylor. Instead, it generates concrete repair code and relies on the task-specific checker stated in section 4: local threshold validation over recorded repair-domain inputs. 

8 Conclusion 

This paper presented NPTaylor, a Taylor-approximation-based framework for repairing localized high floating-point errors in numerical C routines. NPTaylor uses localized high-error domains to synthesize guarded Taylor patches, lowers each candidate to concrete C with fixed floating-point evaluation order, and accepts a repair only after validating the emitted patch on the recorded repair-domain inputs. The evaluation shows that NPTaylor and AutoRNP both repair all 114 one-input GSL benchmark configurations, but NPTaylor does so with lower cost: 3.33 × geometric-mean repair-time advantage, 0.162 × as many C bytes, and a 157.1 × maximum paired repair-time speedup in the strictest setting. The strict-level maximum patch also shrinks from 5.90MB with AutoRNP to 47.5KB with NPTaylor. The repaired-code runtime matrix is consistent with this picture in aggregate, with 1.56 × overall geometric-mean speedup over the unpatched implementations for NPTaylor and 1.35 × for AutoRNP. NPTaylor also repairs bounded multi-input benchmark cases that are outside AutoRNP’s repair workflow. These results support localized one-input repair and a bounded multi-input capability analysis; full-domain proofs, arbitrary multi-input repair, and automatic singular-representation selection remain outside the present claim.
