# LLM-based Code Auditing by Inferring and Evaluating Developer Assumptions 

JUNMING LIU, MPI-SP, Germany 

MARCEL BÖHME, CISPA, Germany When we see a null pointer check, we know that the developer believes that the pointer may not be initialized. If we see the same pointer later used without a null pointer check, we may consider this a violation of the developer’s belief and ultimately a bug. In this paper, we develop such a belief-guided program analysis for vulnerability detection (VD). For example, when an authentication function returns the same error for both, a wrong user name and a wrong password, a human auditor may infer that the developer believes that both cases are indistinguishable, mitigating a user enumeration attack. This belief is reasonable, as it follows standard security practice. Yet, a function call inducing a difference in response time for both cases, contradicts this belief. This contradiction uncovers a timing side-channel that syntactic analysis tools would miss. Existing static analysis tools struggle with this type of flaws because they require them to be expressible by syntactic patterns. Our belief-guided approach allows us to detect such domain-specific, high-level semantic security flaws that have so far remained elusive. Given a function, our approach, Creed, infers the developer’s security-related beliefs, evaluates how reasonable each one is, and derives the conditions under which it is violated. In contrast to existing ML-based VD techniques, Creed explains the root cause, the symptoms, and the conditions under which each issue is exploitable. To overcome the context-dependency problem in the evaluation , we introduce two measures of the performance of explanation-based VD: recall quantifies how effectively an approach correctly explains a known vulnerability, and overhead quantifies the effort of inspecting its reports. On a recent real-world vulnerability benchmark, Creed detects both semantic and syntactic vulnerabilities more effectively than the existing explanation-based VD tools, achieving the best trade-off between effectiveness and effort. Additional Key Words and Phrases: Vulnerability detection, static analysis, large language models

1 Introduction 

Many types of security flaws require domain-specific, high-level semantic code understanding. For instance, in our random sample of 50 recent vulnerabilities collected by CVEfixes [3], developers forgot to consider a timing side-channel when mitigating user enumeration (CVE-2026-25222), forgot to check object-level authorization before canceling a payment (CVE-2026-2010), forgot to limit a path name only to the allowed directory (CVE-2026-28427), or forgot to verify a cryptographic signature (CVE-2026-22866). How can we discover these automatically and at scale? To detect such semantic security flaws manually, code auditors follow a process of identifying developer beliefs and locations where they are contradicted. Cognitive studies suggest [4, 9, 16]: Developers carry certain beliefs (i.e., implicit assumptions) that can be identified in the source code. Auditors iteratively infer the developer’s beliefs about the program’s behavior, form expectations

Existing attempts to automate this belief-guided analysis are based on traditional static analysis [8, 14, 19]. Beliefs and their violations are expressed and checked as general patterns on static code representations. For instance, a null-pointer check guarding a dereference implies the belief that the pointer may be null. The existence of a path along which that pointer is (not reassigned but) dereferenced without a null-pointer check is inconsistent with this belief. An analysis to detect such paths might use the program dependence graph (PDG). However, identifying general beliefs a priori and encoding them as patterns within a syntactic representation of the source code (e.g., PDG) fundamentally limits the types of bugs that can be found. Most of the recent security flaws, we have encountered, violate domain-specific, high-level beliefs that cannot be expressed as such patterns. How can we expect that it identifies "invcreds" as an error code or that the developer believes that returning the same error code after entering the wrong user or password would not leak that the user existed (to mitigate a user enumeration attack)? These are broad semantic facts specific to the authentication domain that can hardly be derived, e.g., from the (language-specific) PDG.

In this paper, we propose a belief-guided, language-agnostic, semantic static analysis for vulnerabil-ity detection that implements a general belief-guided approach using large language models (LLMs). Our approach, Creed, identifies what the given function tries to achieve (action), which assump-tions the developer made when implementing this action (belief), whether these assumptions are reasonable (sanity), and whether there are conditions under which they are violated (violation). The bugs thus detected can be as low-level and general as missing null pointer checks and as high-level and specific as unintended timing side channels. In Listing 1, the function returns the same error code "invcreds" if the user name or if the password is incorrect (action). The corresponding belief may be that a generic error response makes the two failure modes indistinguishable to attackers (belief). Doing so is standard security practice and prevents user enumeration (sanity). If the response time differs significantly between both failure modes, e.g., due to the additional function call, an attacker could still enumerate valid users (violation). This is CVE-2026-25222. How do we evaluate whether our belief-guided approach is effective? Unlike many existing vulnerability detection techniques, our approach does not classify a function as vulnerable or

not, but produces an explanation of why and under which conditions a function may cause a vulnerability. In fact, casting machine learning for vulnerability detection as a function-level binary classification problem is invalid [27] because in most cases whether or not a function causes a vulnerability depends on the context in which this function is called. This context-dependency problem is alleviated in our problem statement because i) we offer an explanation that a human auditor can check, and ii) the explanation is context-conditional. We suggest evaluating the recall of our approach as the proportion of vulnerabilities where our approach produces an explanation that is consistent with the available evidence (i.e., CVE description, patch commit message, and patch diff code). We cannot compute the precision of our approach automatically since many of Creed’s reports, beyond the one we expect to find, seem reasonable to us. Nevertheless, to get a handle on precision, we manually analyze the first report of each function. Moreover, we evaluate the overhead of our approach as the number of reports per expected vulnerability. We evaluate Creed on 50 recent CVEs spanning 10 programming languages, 40 of which are semantic flaws. Creed achieves the highest recall (0.78), correctly identifying and explaining the root cause of 39 of 50 vulnerabilities. Compared with the strongest baseline, it improves recall by 10 percentage points while lowering overhead from 11.3 to 7.9, about 30%. Even under a tight inspection budget, it surpasses the recall any baseline reaches with unlimited effort. It leads on both memory-related and semantic vulnerabilities, including 15 of 21 cases that cannot be expressed as general static-analysis patterns. In summary, we make the following contributions .

• We propose Creed, a belief-guided, language-agnostic, semantic static analysis for vulnerability detection. 

• We evaluate explanation-based detection with recall and overhead , addressing the context-dependency problem in function-level vulnerability detection. 

• We demonstrate the effectiveness of Creed on both semantic and memory-related vulnerabilities.

2.2 Belief Inference 

A belief is an assumption the developer holds when implementing the code. Beliefs cannot be observed directly. Instead, they are inferred from the observable behaviors the code performs, which we refer to as actions .

Action Identification. A function can be understood as a single action in itself (like the 

signInCredential function implementing authentication). Yet, a function also comprises multiple finer-grained actions that together achieve its overall functionality (like the various checks during authentication). Fixing a specific granularity for identifying actions is therefore insufficient: low-level actions and the function’s overall purpose expose different classes of potential vulnerabilities. Creed thus performs a two-level action identification, letting the LLM identify actions at each level rather than imposing a fixed decomposition. First, it identifies low-level actions, such as dereferencing a pointer, which enables it to detect low-level vulnerabilities such as null-pointer dereferences. Second, it identifies what the function aims to achieve as a whole, such as canceling a payment, which enables it to detect domain-specific vulnerabilities such as improper authorization. 

Belief Inference. For each identified action, Creed infers the beliefs the developer assumes to be true when performing it. A single action may provide evidence for multiple beliefs. For example, as shown in Table 1.right, the validation of the entity only against siteId and payment status ( action )embodies at least two distinct security assumptions ( beliefs ): ( B.1 ) that the user who wants to cancel payment paymentId is sufficiently authenticated by the siteId , and/or ( B.2 ) that the siteId is a trusted, server-side value that is not under attacker control. Creed infers each of them, since any of those may underlie a potential security flaw. 

2.3 Belief Evaluation 

Having inferred a set of beliefs, how can we use them to identify potential vulnerabilities? Recall that a belief is an assumption the developer holds while implementing the code. A potential vulnerability can therefore arise in two ways. The assumption itself may be unreasonable, or the assumption

may be reasonable yet not upheld by the implementation. Creed addresses these two cases with two complementary checks, a sanity check and a violation check .

Sanity Check. The sanity check assesses whether a belief is reasonable, i.e., whether it aligns with standard security practice. If a belief does not align, no implementation built on it can be secure, and a potential vulnerability follows regardless of how carefully the code is written. Beyond a Reasonable or Unreasonable label, the sanity check also produces an explanation of which security practice the belief is compared against and why it is considered reasonable or not. For the 

cancel function in Listing 2, the belief B.1 is unreasonable, because site-level and payment-level authorization are different. Note that vulnerabilities induced by such unreasonable beliefs are 

context-independent : Any code that relies on them is vulnerable. 

Violation Check. Even when a belief is reasonable, the implementation may fail to uphold it under certain conditions, and a potential vulnerability can still arise. Rather than simply judging whether such a condition exists, the violation check derives the specific conditions under which a belief no longer holds. Since Creed operates at the function level, a violation condition may be mitigated by upstream code, so Creed surfaces these conditions explicitly for further verification. For the signInCredentials function (Listing 1), the developer is aware of user enumeration and follows the standard practice of returning a generic error. However, the implementation overlooks a timing side-channel induced by an additional function call, under which the belief is violated and the vulnerability that was meant to be mitigated may still occur. Creed derives the violation conditions for every belief, including those already judged unreasonable, to fully characterize how each belief may fail. 

2.4 Vulnerability Reporting 

The sanity and violation checks together flag the beliefs that may lead to a potential vulnerability: a belief that is unreasonable, or one whose violation condition can be triggered, indicates a potential vulnerability. Based on these flagged beliefs, Creed produces a report of potential vulnerabilities .The report consists of a set of findings , each describing one potential vulnerability together with an explanation of its root cause and the context under which it can be exploited. Since a single potential vulnerability may be indicated by multiple beliefs, each finding is linked back to the beliefs that support it, and overlapping beliefs are consolidated into one finding. We call these vulnerabilities potential because the analysis is performed at the function level, and whether a potential vulnerability is real depends on the surrounding context. 

3 Evaluating Function-Level Vulnerability Detection 3.1 Metrics for Function-Level Vulnerability Detection 

To evaluate function-level vulnerability detection ability, we do not adopt the classic metrics based on binary classification, as recent work has shown that such an evaluation is fundamentally invalid for evaluating machine-learning-based vulnerability detection [27]. Specifically, whether a function causes a vulnerability in a program or not often depends on the context within which this function is called. For example, every caller of a given function may always make sure that a pointer points to allocated memory before it is dereferenced in the function (with a potential null-pointer-dereference vulnerability). Without knowing this context, it is not possible to decide whether the function causes the program to be vulnerable or not. However, our work addresses the context-dependency problem for function-level vulnerability detection using a context-conditional approach that offers explanations for multiple findings rather than a single binary decision. Creed reports each finding with an explanation of the root cause and the conditions under which a function may cause a security issue.

Following PrimeVul [5], we also measure whether detections are specific to the defect by analyzing each vulnerable function together with its patched version, which differ only in the fix. We adapt the binary paired evaluation to explanations: an approach is correct on a pair if it reports a matched finding on the vulnerable function and none on the patched one ( P-C ). The other outcomes are a match on both ( P-V ), on neither ( P-B ), or only on the patched function ( P-R ). A high P-C count indicates that the vulnerability is reported because of the defect, not other features of the function. Recall remains our primary measure, as it directly captures whether an approach finds and explains known vulnerabilities, while the paired outcomes qualify it. This allows us to evaluate how well an approach detects known vulnerabilities. However, most approaches typically generate multiple findings per function. How do we estimate the human effort required to identify a known vulnerability by going through all these findings?

Figure 4 illustrates our evaluation procedure. We construct a benchmark from real CVEs, where each entry consists of a vulnerable function together with its known evidence: the CVE description, the commit message, and the patch. Each evaluated approach analyzes the function and produces a report, i.e., a list of findings, where each finding identifies a potential vulnerability with an explanation of the root cause and the condition under which it occurs. 

LLM-as-a-Judge. Given such a report, how do we determine whether it explains the known vulnerability? Manually inspecting every report is expensive and hard to scale, so we employ an LLM-as-a-Judge [32, 38]. To avoid self-preference bias, where a model tends to favor outputs from its own family, we use a judge from a different model family than the evaluated approaches. The judge receives the known evidence and the report, and labels each finding as matched if its explanation is consistent with the known evidence, and as unmatched otherwise. 

Manual check. To ensure the soundness of our results, we manually recheck the judge’s outputs. For every finding the judge marks as matched, we manually verify the match, so that the reported recall is not inflated by erroneous judgments (see RQ-5). For the unmatched findings, which are too numerous to inspect exhaustively, we sample a subset and manually assess whether each is plausible (see RQ-2).

4.1 Evaluation Setup 

Benchmark. To mitigate data leakage from the LLM training set, we construct our benchmark from recently disclosed vulnerabilities (as of the time of writing). We use CVEfixes [3] to collect CVEs were disclosed between September 2025 and March 2026, yielding 2751 CVEs. We then extract the vulnerable functions modified in their fixing commits. Each instance consists of a vulnerable function, which serves as the input to each approach, together with its CVE description and fixing commit, which serve as the ground truth for evaluation. To ensure that a collected function is genuinely the one fixed by the CVE, we retain only CVEs where (1) the function is the only one changed by the commit, or (2) the CVE description explicitly names the function, or names its file and the function is the only one changed in that file. This yields 903 vulnerable functions spanning 622 CVEs. Since these heuristics do not guarantee that a function contains the defect logic of its CVE, we randomly sample functions and manually confirm that each function contains the root cause of its CVE, until we reach 50 confirmed functions. In total, we analyzed 60 sampled functions, 10 (17%) were discarded as merely co-modified or as callers of the defective function. The final benchmark spans 45 distinct projects, 10 programming languages, and 10 vulnerability types. Figure 6 shows the distribution of vulnerability types in our benchmark, of which the majority (40 of 50) are semantic vulnerabilities rather than memory-related ones. Many of these are also beyond what a general static-analysis pattern can express, which we analyze in detail in RQ-3 (Section 4.1). The distribution closely tracks that of the 622-CVE pool (percentages in parentheses in Figure 6), suggesting that the 50 functions are representative of recent CVEs. 1

Tools and Techniques. We compare Creed with four baselines that span different paradigms of LLM-based vulnerability detection, none of which implement a belief-guided analysis. 

• RepoAudit [10] represents the syntactic static-analysis paradigm, an LLM-assisted repository-level auditing tool that follows a traditional static-analysis workflow. 

• PrimeVul-CoT exp [5] represents prompt-based chain-of-thought reasoning , where the LLM is declared an expert in static program analysis and asked to provide, if any, the vulnerabilities, reasons, as well as the context and finally a binary label (i.e., vulnerable or not). To give this baseline a fair advantage, we do not evaluate the label (as in the original PrimeVul-CoT work) but the entire explanation as our evaluation requires. 

• LLM-Thinking enables the LLM’s thinking mode [2] and features a prompt similar to PrimeVul-CoT exp to find vulnerabilities like a security expert. 

• VulTrial [35] represents the multi-agent paradigm, a framework that audits code through multiple cooperating agents. One agent works like PrimeVul-CoT exp and reports potential vulnerabilities while the three other agents debate and filter these reports. For VulTrial , PrimeVul-CoT exp , and LLM-Thinking what exactly constitutes a vulnerability remains undefined while for Creed a vulnerability is defined as an unreasonable or breakable belief.

Presentation . For each vulnerability, we ask whether there exists a general pattern that could facilitate detection by an idealized static analysis. We call a vulnerability expressible if a general pattern exists. An expressible vulnerability can be detected by traditional static analysis using a general pattern. For instance, a use-after-free vulnerability can be detected if there exists a path in the PDG such that there is first a call to free on a pointer-type variable that is later used without being redefined in-between. An injection vulnerability can be detected in the PDG if there exists an information flow (i.e., a transitive control- or data-dependency) between a public source and a sensitive sink. We call an expressible vulnerability that requires user-provided annotations of the source and sink, like in the latter example, as custom . Otherwise, we call an expressible vulnerability as generic , like in case of the use-after-free. Cases that are not expressible depend on the application’s authorization policy, the meaning of a value or resource, or the adequacy of a check. Specifically, expressible vulnerability types cover all memory-related vulnerabilities, as well as information-flow-based semantic cases, such as classic injection or simple path traversal.

5 Related Work 5.1 Belief-Guided Bug Detection 

Inferring developer beliefs from code to find bugs has been explored for more than two decades in static analysis. Engler et al. [8] pioneered this view by extracting beliefs with manually designed templates and reporting statistical deviations as potential bugs. Later work extends this idea beyond hand-written templates by using automatic inference techniques to extract developer beliefs from code [1, 14, 19]. This idea has also been specialized to concrete bug domains, such as beliefs about API post-handling in API misuse [20], error-return conventions and recovery actions in error handling [13], as well as required validation or security checks [21, 24]. Although these works use different signals and target different bugs, they share the same pattern-based, syntactic view. They first turn developer beliefs into patterns, and then find bugs by checking deviations of them. We evaluate the prospects of this approach in RQ-3.b and discuss it further in Section 6. 

5.2 LLM-assisted Static Bug Detection 

At a high level, static bug detection typically proceeds in three steps: identifying bug-relevant program entities, constructing the analysis context around these entities, and applying bug detection rules to report bug candidates. Recent LLM-based approaches augment different stages of this workflow. One line of work uses LLMs for bug-relevant entity identification , leveraging their semantic understanding to locate suspicious APIs [31], sources and sinks [18], or key variables and statements [29]. Another line uses LLMs to assist analysis-context construction , for example, by generating graph queries for code property graphs [15] or guiding program slicing [28]. A third line uses LLMs for detection-rule construction . For example, KNighter [36] synthesizes static analysis checkers from historical bug-fixing patches, extending pre-defined human-written patterns with generated patterns. Finally, more recent end-to-end systems further employ LLMs to orchestrate the entire workflow [10, 17, 23]. Although these works reduce manual effort, they assume that bugs can be sufficiently captured by patterns. However, vulnerabilities often arise from semantic flaws, which patterns cannot completely capture. 

5.3 Direct LLM-based Vulnerability Auditing 

Prompt engineering. Recent works apply general prompt engineering techniques to vulnerability detection, including CoT for step-by-step vulnerability reasoning [5, 26], tree-of-thoughts for explor-ing multiple reasoning paths [30], and in-context learning for demonstration-based guidance [22]. Beyond these general techniques, some works tailor prompts with code-specific evidence, such as data flow, control flow or API call sequence [37]. While such prompt designs can improve LLMs’ reasoning, they mainly elicit generic reasoning steps rather than bug-detection-specific reasoning. 

Role-based agents. Multi-agent approaches decompose the auditing process into different roles: one agent identifies potential vulnerabilities, while others critique or validate the findings. GPTLens [12] employs a collaboration between an auditor and a critic, and VulTrial [35] instantiates roles such as auditor, defender, and judge. Similar role specializations have been explored in specific fields, such as smart-contract analysis [25, 33]. A role specialization can better elicit LLMs’ semantic reasoning and improve the validation of candidates identified by the auditor agent. However, the initial auditing step still largely depends on a single agent’s heuristic reasoning. As a result, subtle or novel bugs may be missed before the debate or critique stage begins. We confirmed this finding in RQ-1 when we replaced the vulnerability-reporting agent in VulTrial with our Creed. 

Knowledge-enhanced LLMs. Another line of work enhances LLMs with additional vulnerability knowledge. Fine-tuning-based approaches update the model’s parameters on labeled vulnerability data. VulLLM [6] adds vulnerability localization and interpretation as auxiliary tasks to capture  

> , Vol. 1, No. 1, Article . Publication date: October 2026. LLM-based Code Auditing by Inferring and Evaluating Developer Assumptions 17

root causes, while R2Vul [34] distills structured, security-aware reasoning into small models via reinforcement learning. Such adaptation can improve accuracy, but fine-tuned models often learn surface patterns rather than real security logic, and generalize poorly to new code. RAG-based approaches augment LLMs with external vulnerability knowledge at detection time. Vul-RAG [7] retrieves relevant knowledge from historical cases, while VulInstruct [39] extracts security specifications from past vulnerabilities and retrieves them during detection. Such retrieval can supply domain-specific knowledge to the model, although irrelevant or incomplete retrieval can still bias it toward incorrect judgments. 

Our belief-guided reasoning. Creed takes a different view of how LLMs should be used for vulnerability auditing. Instead of using LLMs as components in a static-analysis pipeline or directly prompting them to generate vulnerability reports, Creed reframes vulnerability auditing as the discovery of unreasonable or incorrect developer beliefs, guiding LLMs to reason about why code is buggy rather than whether it matches a known pattern. 

6 Discussion 6.1 Beyond Rule-Based Detection 

We consider static analysis as the analysis of source code without executing it, and are convinced that our belief-guided static analysis offers new opportunities for identifying semantic bugs that have previously been out of reach. In the security domain, our randomly sampled benchmark shows that most of the vulnerabilities are semantic (40 of 50), and among them over 50% (21/40) are difficult to express as a rule. This means that a large proportion of domain-specific vulnerabilities cannot be captured by the traditional static analysis paradigm based on patterns or rules, since they depend on the specific context (such as the timing side-channel that is only vulnerable in the sign-in authentication context). With the rule-based, language-specific view these domain-specific contexts are reduced or hard to recognize, and thus the vulnerabilities that need more semantic meaning are difficult to detect. Creed addresses this problem through belief-guided vulnerability detection. Rather than fixing rules before detection, it derives the violation conditions while evaluating each belief. Since each belief is inferred from an action and grounded in the specific context, Creed can identify semantic vulnerabilities such as the timing side-channel and the insufficient permission check that rule-based detection overlooks (see Table 1). In this paper, we explore the opportunities of LLMs for program analysis and find that they are indispensable when it comes to semantic, high-level, domain-specific, language-agnostic reasoning about developer intention and beliefs. 

6.2 The Boundary of Belief-Guided Vulnerability Detection 

The main boundary of belief-guided vulnerability detection is that evaluating a belief sometimes requires knowledge that lies beyond common security practice and cannot be inferred from the code alone. This appears in both the sanity check and the violation check. For the sanity check, an application may have its own specified security policy or threat model beyond common security practice, making it hard to judge whether a belief is reasonable. For withPermShare (CVE-2026-32761), judging that checking only the share permission is insufficient requires the application’s specified policy that a user without download permission should not share a file. For the violation check, a belief may be violated under open-ended conditions, and knowing which of them can actually occur often requires context beyond the function. 6.3 Threats to Validity 

Construct validity . In our study, we evaluate each approach with two metrics, recall and overhead, both of which we report conservatively. For recall, a report counts as matched only if a human confirms it, so the reported recall is a lower bound on the true recall. For overhead, we treat every unmatched finding as a false alarm, so the reported overhead is a worst-case upper bound and the actual inspection effort is no higher (Section 3). Deciding whether a finding matches the known evidence relies on an LLM-as-a-Judge [32, 38]. Like for any LLM-based evaluation, there is inherent uncertainty: the LLM may misjudge a match. To mitigate this, a) we choose the judge from a different model family than the evaluated approaches, and b) we manually verify the matches and assess the judge’s reliability against human experts in RQ-5. 

Internal validity . A key concern is whether our experimental setup compares Creed and the baselines fairly. The first such factor is the underlying model. To ensure that the comparison reflects the approaches rather than the model, all approaches use the same backbone model. A robustness experiment with a different backbone (DeepSeek V4 Pro) shows that Creed still achieves the highest recall, suggesting that the result is not specific to a single model. The second is the non-determinism inherent in LLMs, which could make the results unstable. We mitigate this by setting the temperature to 0 for all approaches, except for LLM-Thinking, for which the temperature is not configurable in thinking mode. A third factor is the differing settings some baselines require. RepoAudit performs repository-level analysis, so we provide it with the full repository and manually supply the user-specified functions it needs. PrimeVul-CoT originally outputs a binary label, so we use its explanation-generating variant so that it can be evaluated on the same basis as the other approaches. Another common concern is that the dataset itself may have been part of the LLMs’ training data. To mitigate data leakage, we explicitly collect only vulnerabilities disclosed after the backbone model’s training cutoff, so that the model is unlikely to have seen them during training. Finally, the evaluation itself relies on an LLM-as-a-Judge, whose reliability we address under construct validity. 

External validity . Our benchmark contains 50 vulnerable functions, a size that may limit how far our findings generalize. To reduce bias, we sample randomly from recently disclosed CVEs collected by a third-party tool [3] and retain only those whose function contains the CVE’s root cause, rather than selecting cases favorable to our approach. Despite its size, the benchmark is diverse and its type distribution closely tracks that of the 622-CVE pool it was sampled from (Figure 6). Its 50 vulnerable functions come from 45 distinct projects and span 10 programming languages and 10 vulnerability types, covering both memory-related and semantic categories. We therefore believe it is reasonably representative of real-world vulnerabilities. 

7 Conclusion 

Many real-world vulnerabilities are semantic and domain-specific, and cannot be captured by the syntactic patterns that traditional static analysis relies on. We propose Creed, a belief-guided semantic static analysis implemented with large language models. Given a function, Creed identifies the actions implemented by the code, infers the beliefs behind these actions, and checks whether each belief is unreasonable or can be violated under specific conditions, and finally reports potential vulnerabilities with explanations of their root causes and exploitation contexts. To address the context-dependency problem of binary metrics in function-level vulnerability detection, we propose two metrics, recall and overhead. Recall measures detection effectiveness  

> , Vol. 1, No. 1, Article . Publication date: October 2026. LLM-based Code Auditing by Inferring and Evaluating Developer Assumptions 19

as the fraction of known vulnerabilities for which an approach produces a matching explanation. Overhead measures human inspection effort as the number of findings that must be examined per identified vulnerability. Our evaluation on 50 recent real-world vulnerable functions shows that Creed achieves the highest recall among all evaluated approaches and the best recall-overhead trade-off, and is effective across both memory-related and semantic vulnerabilities.
