# From Software History to Executable Regression Tasks: A System for Evaluating Software Agents 

RUIKAI SHI ∗, Peking University, China 

ZHENGRAN ZENG ∗, Peking University, China

WEI YE †, Peking University, China As software agents increasingly generate and modify code, evaluating their ability to review changes and discover defects becomes important. Such evaluation needs executable project environments for investigation and reliable defect references supported by reproducible behavior. Existing code review benchmarks provide limited support for this combination. We present a system that constructs executable regression instances from historical introducing–fixing commit pairs and developer tests. The system extracts candidate tests from fixing-side changes, then uses constrained agents to transplant them and configure version-specific environments while preserving production code and test expectations. Independent replay and evidence-based review verify whether tests that fail on the introducing version and pass on the fixing version support the proposed regression relationship. Accepted instances retain both versions’ replay recipes, validated tests, and execution evidence. Repair-supported analysis and human review add root-cause locations, tested repairs, and causal explanations. These instances support bug detection and localization in code review, and further enable bug repair and regression-test generation on the same defects. The system constructs 172 validated instances from 522 candidates across 11 Python projects. We evaluate three software agents with ten models and additional reasoning-effort settings on 83 manually selected, enriched instances across the three tasks. Precise root-line localization remains challenging, while baseline combinations achieve repair and regression-test generation success rates of up to 68.7% and 77.1%, respectively. Leading configurations differ by task, and higher task performance does not necessarily yield greater API-cost efficiency. Our approach provides reusable executable evidence for studying agents’ defect discovery, repair, and testing capabilities. 1 Introduction 

As LLM-based agents take on more code generation and modification tasks [42], evaluating and improving their code review and defect discovery capabilities becomes increasingly important. Finding defects in a change can require executing the program, constructing inputs, and checking suspected behavior. Evaluation therefore needs executable project environments that support investigation and reliable reference answers identifying the defects and their locations. SWR-Bench, CodeFuse-CR-Bench (SWE-CARE), and AACR-Bench provide pull requests, reposi-tory context, and review annotations [12, 44, 46]. Their published construction workflows do not describe systematic reconstruction and validation of project execution conditions for each reviewed revision. Repository snapshots and general Agent containers still require historical dependencies and test support to run the affected behavior reliably. Reliable evaluation also needs reproducible behavioral evidence supporting the reference defect. We address these needs by constructing executable regression instances from software history.

Software history records introducing changes, repairs, and developer tests. Constructing exe-cutable instances presents three challenges. Fixing-side test changes may pass on both versions or exercise unrelated behavior. Historical versions may require different dependencies and test support that must be reproducible beyond an Agent session. Fail-to-pass outcomes must reflect proposed code changes rather than incompatible test support or unintended validation edits. We present EReg-Factory , a system for constructing executable regression data from candidate introducing–fixing pairs. The system extracts fixing-side candidate tests for constrained Validation Agents to transplant and execute in version-specific environments. Operation Judges check Agent actions; an environment replayer independently reruns tests; and a Regression Verifier connects paired outcomes to code changes. Instances retain two replay recipes, validated tests, execution evidence, and explanations. Repair-supported analysis and human review add root locations, tested repairs, and causal explanations. These instances support bug detection and localization in code review, where Agents examine the introducing change without access to later fixes or target regression tests. Retained repairs and behavioral evidence further support bug repair and regression-test generation. These three related tasks are evaluated independently on the same defects. Across 522 candidates from 11 Python projects, EReg-Factory yields 172 validated regression instances. We evaluate three Agents with ten models and additional reasoning settings on 83 manually selected enriched instances across the three tasks. Precise root-cause localization remains challenging, while repair and regression-test generation show promise. Leading models differ by task, and higher performance does not necessarily provide greater benefit per dollar. Our contributions are: 

• A regression construction system combining paired environment construction, indepen-dent replay, and evidence review to validate historical introducing–fixing relationships and retain reproducible execution conditions. 

• Instance enrichment for three tasks using reviewed root locations, repairs, and explana-tions to support code review through bug detection and localization, alongside repair and regression-test generation. 

• An empirical study characterizing construction outcomes and comparing Agents, models, and reasoning configurations by task performance and cost efficiency.

3 EReg-Factory: Regression Instance Construction 

EReg-Factory constructs executable regression instances from candidate introducing–fixing commit pairs through paired validation, independent environment replay, and regression verification. This section describes that core construction process. Figure 2 summarizes the process from candidate acquisition to a validated, independently replayable regression instance. 

3.1 Candidate Relationships and Test Scope 

Candidate acquisition is replaceable: other mining methods or curated sources can supply pairs, provided that both commits and fixing-side test changes are available. We use GH Archive, which records public GitHub activity in hourly archives [11]. Its cross-repository history enables mining without selecting repositories individually in advance. We mine its 2023–2025 PushEvents across repositories. Case-insensitive matching identifies repair ( fixes , correct , resolve ) or causal terms (regression , introduced by , broken since ), followed by a full 40-character hexadecimal SHA. The message links fixing candidate 𝐹 to introducing candidate 𝐼 through an explicit SHA reference, without cross-message similarity matching (Figure 3). Filters remove dependency updates, routine merges, CI, documentation, formatting, releases and backports; repository and test-change screening retains Python projects with pytest indications and candidate test files. Following this initial rule-based screening, all candidate relationships undergo rigorous manual secondary screening to confirm their credibility and provide reliable inputs for subsequent validation. To further screen candidate inputs, we examine the pull requests associated with each fixing candidate. Fixing candidates pass when any associated pull request is merged; those without requests also proceed to later validation, accommodating direct commits. Those with only unmerged requests are excluded. For eligible fixes referencing one introducing commit, we select the latest event: later attempts may complete an earlier repair. Paired execution tests this relationship.

We treat tests changed by a fixing commit as candidate regression tests because they may express the behavior targeted by the fix and its expected outcome. Pytest tests check program behavior through given inputs and assertions on expected results, providing a basis for reusing the same behavioral check across versions. In subsequent stages, we preserve these inputs and assertions and transplant the complete fixing-side tests to the introducing version, checking the earlier version against the same expectations after necessary adaptation. Changes confined to assertions or expected results can therefore also yield candidates. We map changed locations in test code onto Python abstract syntax trees to identify the corre-sponding test functions or methods and generate pytest nodes, forming candidate scope 𝑇 0. If no eligible nodes are identified, we discard the candidate commit pair. For retained candidates, later stages configure the environment and adapt test support to verify executability and behavioral differences between versions, establishing valid regression tests.

The introducing-side Validation Agent receives the repository, the introducing and fixing commit identifiers, candidate test paths and the specified pytest nodes 𝑇 0. It applies to 𝐼 the complete fixing-side test files containing the nodes extracted in Section 3.1, configures the required environment, and executes those candidate nodes 𝑇 0. Existing non-production fixtures, helpers, test data and test configuration may be restored or adapted to support execution, but candidate inputs, assertions, expected results, parameters and skip behavior must remain unchanged. Production implementation cannot be copied or edited, even to resolve an import, because doing so could import the fix under investigation. If some candidates cannot execute within these constraints, the Agent may narrow the scope to 𝑇 run ⊆ 𝑇 0 and report the omitted tests. Its final report records the environment preparation, self-contained test command, exit code and observed outcome. Before independent replay, an LLM-based Judge reviews task compliance using the task require-ments, Agent execution record, code changes and validation report (Figure 5). It allows supporting adaptations needed to run the tests while requiring the candidate tests’ behavioral expectations and the production implementation to remain unchanged. Runs that pass this review proceed to independent replay. We use GPT-5.6 Sol with reasoning effort set to max for the Judges on both the introducing and fixing sides. 

Independent replay. Environment construction is exploratory, involving dependency installation, temporary inputs, environment variables and repository build commands; neither a package list nor the final test command captures all these conditions. Our environment replayer converts the recorded configuration process into a recipe executable in a fresh container, avoiding reliance solely on the Agent’s account or temporary session. SetUpAgent and Repo2Run reuse Agent exploration for setup [15, 38]; our replayer couples this process with the historical source state and candidate test scope.

Replay starts from the target commit and extracts environment configuration operations and their required temporary inputs from the execution trace, preserving their order and necessary environment settings. Environment and source state are reconstructed separately: setup and build commands restore dependencies and generated artifacts, while a patch applies test transplantation and permitted supporting changes, avoiding duplicate application of generated artifacts. The replayer then reconciles the final report with the execution record to determine the test command and runtime settings, so that replay corresponds to the Agent’s final reported experiment rather than an exploratory attempt. We also retain dependency information and recorded versions for Python packages, system packages and build tools used to construct the Agent’s environment. When replay exposes missing dependencies during test startup, collection or setup, the replayer uses these records to install the corresponding package versions and reruns the same test command, rather than modifying the program under test to eliminate failures. Replay preserves per-case results and failure output for behavioral comparison, regression verification and re-examination. 

3.3 Validation on the Fixing Version 

Fixing-side validation checks that the tests exercised on 𝐼 pass on 𝐹 , resolving the observed failures. The Validation Agent receives the repository at 𝐹 and the introducing side’s final test command and exercised scope, including any narrowed subset (Figure 4). It configures its own environment and runs the existing tests without changing source code or tests, recording the environment, command and outcomes in a structured report. The fixing-side Judge reviews the execution evidence under this environment-only constraint, checking that preparation preserves the program, tests and required test scope. Runs that pass proceed to independent validation with the environment replayer described in Section 3.2. Replay uses the fixing-side Validation Agent’s own configuration and final command in a fresh container. The two sides therefore share a test scope, while allowing the dependency versions and runtime settings needed by each historical version to differ. Paired replays yield independently observed outcomes for the same tests. A fail-to-pass difference alone does not establish the proposed introducing–fixing relationship; Section 3.4 examines both executions, failure causes and commit changes.

The verifier receives both Agent reports, paired replay results and failure output, relevant test code and its changes, and the introducing and fixing commit differences (Figure 6). It examines whether the change in 𝐼 explains the observed failure, whether 𝐹 addresses the same problem, and whether the test exercises the affected behavior. Unlike the operation Judge’s compliance check, this assessment links code changes, test expectations and paired outcomes to distinguish supported regressions from unrelated behavior, environment failures or incompatible test transplantation. The verifier produces a structured assessment comprising supported regression tests 𝑇 ∗, a bug explanation describing the defect and how it was introduced and repaired, and a regression explanation describing the behavior checked by the tests and why their outcomes support that relationship. Unresolved or unsupported cases are excluded from 𝑇 ∗. We retain the supported tests and explanations with both replay recipes and execution results. These instances are then enriched with root-cause annotations and task-specific evidence for evaluation. 

4 Instance Enrichment and Evaluation Task Design 

EReg-Factory constructs executable regression instances with validated tests and environments for both versions (Section 3). We enrich these instances with root-cause annotations and tested repairs, then use the resulting evidence to design three complementary evaluation tasks: bug detection and localization, bug repair, and regression-test generation. 

4.1 Repair-Supported Root-Cause Annotation 

Validated regression tests expose affected behavior but do not directly locate its root cause. Repair locations need not coincide with root-cause locations: a repair may adjust downstream handling or add a guard to eliminate a failure whose cause lies elsewhere. We combine repair-based analysis with human annotation to locate the regression’s causes in the introducing change, providing reference locations and explanations for evaluation (Figure 7).

The environment replayer reconstructs the introducing version with the accepted regression tests and confirms their failure. Our Root-Cause Agent is based on SWE-agent [42] and uses DeepSeek V4 Flash. It receives the prepared environment, read-only access to the introducing and fixing changes, and the preceding stage’s validated regression tests, failure output, bug explanation and regression explanation. Together, these provide the context for analyzing how the problem arose, why the tests expose it, and how the fix changes the affected behavior. The Agent is instructed to first analyze the failure and propose root locations, then implement its own repair. It is encouraged to repair at the identified root cause rather than mechanically reproduce the developer’s repair. It preserves the tests and their execution conditions and reruns the tests in the same container. When the tests pass, we retain the proposed source-line root locations, repair patch 𝑅 and causal explanation for subsequent manual annotation and review. The three reviewed artifacts jointly support subsequent evaluation. Two master’s students in computer science independently assess all three artifacts : whether the root locations are accurate, whether 𝑅 addresses the stated problem, and whether the causal explanation agrees with the source and execution evidence. They annotate and correct locations and explanations, review and confirm the repair, and resolve disagreements through discussion to estab-lish the final reference answers. Root locations support localization comparison and test-coverage evaluation; 𝑅 provides the repaired state for regression-test generation; and causal explanations inform task descriptions and behavior specifications. 

4.2 Evaluation Task Design 

We turn validated and enriched regression instances into three complementary tasks: finding a problem in a code change, repairing its behavior, and writing a test that exposes it (Table 1). The tasks share a behavioral basis but are evaluated independently. Each provides task-specific inputs to the Agent while retaining reference answers with the evaluator. 

Bug detection and localization. This task assesses whether an Agent can identify a potential problem when examining a code change. We provide the introducing version, its parent, the change description and diff, allowing analysis of both added and deleted behavior without later fixes or regression-test evidence. The Agent judges whether a bug is present and identifies the responsible source lines without changing the repository. We compare the reported locations with the instance’s root-cause lines. 

Bug repair. Following an evaluation pattern similar to SWE-bench [18], this task assesses whether an Agent can repair a problem from a symptom description. Regression-test generation. This task assesses whether an Agent can turn a behavioral require-ment into a test that detects the regression. The Agent receives a behavior specification, the parent and introducing versions, and their diff. Ordinary tests and reusable support remain available. The Agent analyzes the specified behavior and designs its own test inputs, assertions and implementa-tion without changing production code. Its tests must fail on the introducing version and pass on that version with the validated repair 𝑅 applied. The failure must expose a behavioral difference, rather than an import or test-collection error. The generated tests should also cover as many of the regression’s root-cause lines as possible. To assess repair and test generation more independently of an Agent’s ability to discover and localize a problem from scratch, we provide concise descriptions of the target behavior. We use GPT-5.6 Sol with reasoning effort set to max to generate repair symptom descriptions and test behavior specifications from the instances’ validated regression tests and execution evidence; the latter also use the introducing change. We manually review these descriptions for fidelity to the evidence and answer leakage, retaining necessary trigger conditions and behavioral requirements without revealing root locations, repair solutions or reference test implementations. The Agent must still analyze the repository to complete each task. 

5 Study Design 

We study the regression data constructed by EReg-Factory and Agent performance on the three tasks defined in Section 4.2. 

5.1 Research Questions 

RQ1: What executable regression data can EReg-Factory construct? We examine construction output, project distribution, and the root-cause and test evidence supporting the three tasks. 

RQ2: How do Agents and models differ across the three tasks? We compare Agents and models on the same instances to examine whether their relative strengths carry across localization, repair and regression-test generation. 

RQ3: How do reasoning effort and model configuration affect performance and cost efficiency? We vary Sol’s reasoning effort under a common request budget and compare GPT

5.3 Execution and Comparison Protocol 

For each task and instance, Agents receive identical descriptions and permitted evidence under Section 4.2’s information boundaries; the evaluator retains the task-specific private reference material. Agents keep their native tools and context management, using isolated workspaces without access to one another’s solutions. Table 2 specifies the common context, output and main-request budgets; requests, not shell commands, are counted. Temperature is zero, with Agent time limits of 2 h for localization and 4 h for repair and test generation. Localization allows up to two additional format-recovery requests of up to 4,096 output tokens each, using the existing record without renewed repository exploration. We retain one effective attempt per instance–Agent–configuration combination, not the best retry. Infrastructure interruptions are recovered separately from capability failures; budget-limited, invalid and unsuccessful runs remain in the denominator. A verified repair can still succeed after request-budget exhaustion. Tasks are scored separately, without a composite ranking.

7 Discussion and Threats to Validity 7.1 Discussion 

Historical regressions as reusable experimental data. EReg-Factory turns historical regres-sions into reusable executable instances by retaining both versions’ replay recipes, validated tests and execution evidence. Root-cause annotations and tested repairs support complementary evaluations grounded in the same behavioral difference. 

Repair and test generation show promise; precise localization needs improvement. The strongest combinations show practical promise for repair and test generation (Section 6.2). Identi-fying relevant code, however, still falls short of precise, complete root-line recovery, motivating better links between behavioral reasoning and source changes. 

Agent–model combinations should be selected by task. Relative strengths differ across local-ization, repair and test generation. Combinations should therefore be evaluated on the intended task rather than selected solely from overall Agent or model rankings. 

Reasoning effort should match the task. For Sol, medium effort captures most Agent-averaged repair gains, while high effort further improves test generation but not mean localization F1 (Section 6.3). More reasoning is thus not uniformly beneficial across tasks. 

Parameter count is not a performance guarantee. Larger total parameter counts in Qwen3.5 do not consistently yield better results, whereas newer Qwen generations improve average results at the same parameter scale. Total parameter count alone is insufficient for selecting models. 

Cost efficiency changes the model-selection objective. Among GPT configurations, Luna provides the highest yield per dollar, whereas Sol high leads Agent-averaged repair and test-generation success. Selection should balance the required performance against API cost. 

7.2 Threats to Validity 

Internal validity. Environment reconstruction, automated judgments and annotations can in-troduce errors, mitigated through independent replay, evidence checking and two independent annotators who resolve disagreements through discussion. One retained effective attempt per combination leaves run-to-run variability unmeasured. 

Construct validity. Repair acceptance covers targeted failures and previously passing cases in scope, not complete program correctness. Location matching measures agreement with reviewed 

> 17

roots; coverage records execution, not comprehensive assertion adequacy. The positive-only local-ization cohort does not measure false-alarm rates on bug-free changes. 

External validity. Our configuration and experiments target Python projects using pytest. Other languages and testing frameworks may require different environment setup and test execution mechanisms, and applicability there remains to be validated. 

8 Related Work 

Historical defects and executable data. SZZ traces fixes to potentially inducing changes [36]. Defects4J and BugsInPy package reproducible defects for testing and debugging [19, 39]; Bugs.jar and ManyBugs broaden the available repair subjects [20, 33]. Bears and BugSwarm reproduce failing and passing builds from CI histories [24, 37]. Building on this emphasis on execution, EReg-Factory follows explicitly linked introducing–fixing commits and checks fixing-side tests at both historical states, rather than treating a mined association as a verified regression. 

Automated environment and task construction. Executable repository tasks support evalua-tion and training [18, 30, 45], while R2E constructs function-level test harnesses [16]. SetUpAgent and Repo2Run automate environment exploration and reusable setup [15, 38]. SWE-Factory and SWE-rebench V2 integrate environment preparation with task validation [4, 13]; SWE-smith and R2E-Gym scale task construction through synthetic generation [17, 43]. Our focus is validating a proposed historical regression: side-specific environment reconstruction, independent replay, and review of operations and regression evidence together connect the observed behavior to the introducing and fixing changes. The retained instances include both replay recipes and behavioral explanations, supporting reuse beyond repair alone. 

Fault localization and program repair. Spectrum-based, learned, and LLM-guided localizers identify suspicious program elements [1, 22, 31]. Test-guided repair spans search-based methods and conversational or autonomous LLM systems [7, 21, 41]. Repository-level approaches further address code search, planning, and tool-driven editing [5, 40, 42, 47]. EReg-Factory uses repair-supported analysis and human review to annotate inducing locations separately from repair locations: restoring behavior need not modify the change that introduced the problem. These annotations support localization evaluation independently of repair acceptance. 

Regression tests and behavioral oracles. Random and search-based generators construct ex-ecutable test suites [10, 23, 29]. LLM approaches generate or improve tests using code context and execution feedback [2, 8, 34]; CoverUp and SymPrompt explicitly guide generation toward coverage [3, 32]. However, coverage alone does not establish fault detection [35]: oracle research examines how assertions distinguish intended from observed behavior [6, 9, 14]. SWT-Bench evaluates issue-reproducing tests through fail-to-pass execution and change coverage [25]. EReg-Factory supplies validated historical regression tests and reviewed root locations, linking behavioral discrimination with root-code coverage in the subsequent test-generation evaluation. 

9 Conclusion 

We presented EReg-Factory, a system for constructing executable regression data from real-world software history. By combining constrained Agent exploration, paired environment construction, independent replay, and evidence review, the system turns candidate introducing–fixing rela-tionships into instances with validated regression tests and reproducible execution conditions. Repair-supported analysis and human review enrich these instances with root locations, repair patches, and causal explanations for localization, repair, and regression-test generation. Our evalu-ation shows promising repair and test-generation performance, while precise root-line localization 

> 18

remains challenging. Agent–model strengths differ by task; greater reasoning effort or model size does not uniformly improve performance, and higher success does not necessarily yield greater benefit per dollar. Together, the construction system and multi-task evaluation provide a reusable basis for developing executable data and studying software agents on real historical regressions.
