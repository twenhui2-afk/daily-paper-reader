Abstract —Owners of data in cloud object storage cannot directly check whether the provider still keeps every object unchanged. Existing research mostly checks blocks inside files or relies on third-party auditors, and less attention has been given to checking each object against a public blockchain reference while measuring the cost. A full-data audit downloads every object and compares it with a saved hash list, which is slow and only as reliable as that list. We propose a public auditing system in which the SHA-256 hash of each object and its name forms a leaf of a Merkle tree, so the whole dataset is represented by one Merkle root. This root is stored in an Ethereum smart contract as a trusted public record, while the objects stay with the provider. An auditor downloads an object, rebuilds the root using a short Merkle proof and compares it with the stored root, marking the object as intact, modified or missing. In five experiments on an S3-compatible store and a local Hardhat blockchain (normal audit, single- and multiple-object tampering, deletion and scalability), the system detected 15 of 15 single modifications, 2,205 of 2,205 modified objects and 830 of 830 deleted objects with no false alarms. The proof needed only 14 hashes for 10,000 objects, so checking one object took about 10 ms and a 100-object sample about 150 ms regardless of dataset size, while a full audit of 10,000 objects (14.3 s) took about as long as downloading them (13.5 s). Storing the root cost 91,863 gas, 252 times less than storing 1,000 hashes on-chain. The system thus shows exactly which objects were modified or are missing, with its main savings coming from checking selected objects.

I. I NTRODUCTION 

Organizations increasingly keep unstructured data in cloud object stores whose hardware they neither own nor operate [1]. Objects can be damaged or lost through disk faults, software bugs, operator mistakes or deliberate interference, and as long as nobody checks, an overwritten or deleted object looks no different to its owner from one that is still intact. An integrity audit therefore needs two ingredients: a description of the correct state that the provider is unable to alter, and a procedure, affordable enough to run regularly, that compares the stored data with that description. The most direct procedure is a full-data audit, in which the auditor fetches every object and compares its SHA-256 digest with a digest list kept locally. The work grows with the volume of data, failures can be pinpointed only if one digest per object is retained, and the result can be trusted only as far as the stored list can. A Merkle tree [2], [3] compresses the digests of n objects into one 32-byte root and allows any single object to be checked against that root with a proof of about log 2 n hashes. If the root is recorded in a smart contract, it becomes a public reference that neither the provider nor the auditor can silently change, while the objects themselves stay off-chain. This paper designs, implements and measures such a mech-anism for an S3-compatible object store. Its aim is not to propose a new cryptographic primitive, but to establish experi-mentally what the combination of SHA-256, a Merkle tree and an on-chain root actually provides: which integrity violations it detects, what each audit costs in time and transferred data, how these costs scale with the number of objects, and what the blockchain adds in gas and latency.

B. Contributions 

1) A Merkle-tree commitment for object storage in which each leaf binds an object’s key to its SHA-256 digest, in-ternal and leaf nodes are domain-separated, and unpaired nodes are promoted rather than duplicated (Section V). 2) A smart contract that stores only the root, the object count and an append-only audit log, and that can also verify a Merkle proof on-chain; the off-chain tree is treated as untrusted (Sections V–VI). 3) A public audit procedure that downloads the challenged objects themselves, recomputes their leaves and classi-fies each object as intact , modified or missing , in full or sampled form. 4) A measured evaluation on a local testbed covering normal audits, single- and multiple-object tampering, deletion, scalability from 10 to 10,000 stored objects (and to 220 leaves in memory), communication volume and smart-contract gas, with five repetitions per configu-ration (three for the largest dataset) (Sections VII–VIII).

A. Cloud Object Storage and the Trust Problem 

In an object store, every item is an opaque byte sequence that carries some metadata and is addressed by a key in a flat namespace; clients manipulate it through a small set of HTTP requests (PUT, GET, DELETE, LIST). The request vocabulary of Amazon S3 [4] has become a common interface that other servers, MinIO among them [5], reimplement. Under the service models described by NIST [6] and in the early analysis of cloud computing by Armbrust et al. [1], the tenant decides what is stored but does not operate the machines that store it. Kamara and Lauter [7] therefore argue that a tenant should be able to check its outsourced data cryptographically rather than rely on the provider’s word. For integrity, the difficulty is easy to state: a successful GET shows only that 

some bytes came back, not that they are the bytes that were uploaded, and the loss of an object may go unnoticed until someone next asks for it. Role here: the object store holds the data and is treated as untrusted. 

B. Cryptographic Hash Functions 

SHA-256, specified in FIPS 180-4 [8], compresses an input of arbitrary length into a 256-bit value. The properties our argument needs are those formalized by Rogaway and Shrimp-ton [9]: second-preimage resistance (given one input, finding another with the same output is infeasible) and collision resistance (finding any two inputs with the same output is infeasible). NIST rates the collision strength of SHA-256 at 128 bits [10]. These guarantees are not universal across hash functions: a practical collision for SHA-1 was demonstrated in 2017 [11], which is why the digest algorithm has to be chosen with care. Role here: each object is reduced to a 32-byte digest, and the digest changes if any bit of the object changes. A set of n digests, however, still has to be stored somewhere trustworthy; hashing by itself does not remove that need. 

C. Merkle Trees 

Merkle’s hash tree [2], [3] places digests at the leaves of a binary tree and labels every internal node with the hash of its two children. Because the label at the top depends on every leaf and on their order, the root acts as a short commitment 

to the whole sequence: altering, dropping or permuting a leaf alters the root. Building the tree costs exactly n − 1 node hashes for n leaves. The same structure underlies tamper-evident logs [12], the Certificate Transparency protocol [13], [14] and file systems on untrusted servers [15]. Certificate Transparency also introduced the practice, which we follow, of hashing leaves and internal nodes with different one-byte prefixes, so that an internal node can never be passed off as a leaf [13]. Role here: the tree replaces n trusted digests by one trusted 32-byte root. 

D. Merkle Proofs 

To show that a given leaf belongs to a tree with a known root, it suffices to supply the hashes of the siblings met on the way from the leaf to the root, often called the authentication or audit path. The verifier folds these siblings into the leaf, one level at a time, and checks whether the result equals the root. A balanced tree with n leaves needs at most ⌈log 2 n⌉ siblings, so the proof is small regardless of how large the object is; Szydlo [16] studies how such paths can be produced efficiently for successive leaves. The path does not have to come from a trusted party: a wrong sibling simply leads to a wrong root. 

Role here: one object can be checked without fetching the others, and the untrusted provider can serve the proofs. E. Blockchains and Smart Contracts 

A public blockchain is a ledger replicated across many nodes, extended only by appending blocks, and practically immutable unless an attacker controls a large share of the network’s resources [17], [18]. Ethereum [19], [20] lets pro-grams, called smart contracts, keep state on this ledger. The state changes only through transactions that pass the contract’s own checks and can be read by anyone. Execution is metered in gas ; writing a new 32-byte storage word is among the most expensive operations, so contracts are usually designed to keep large data off-chain and store only short commitments on-chain [21]. Contract code can also contain defects [22], [23], which is why our threat model treats the correctness of the contract as an explicit assumption. Role here: the contract is a public, provider-independent place for the root. It never sees the objects and cannot itself notice tampering; detection happens only when an auditor compares freshly computed values with the stored root. III. R ELATED WORK 

We group prior work into four lines: proofs of storage, public and dynamic auditing, hash-tree structures for untrusted storage, and blockchain-assisted auditing. Table I compares representative schemes along the dimensions that matter for our design. 

A. Provable Data Possession and Proofs of Retrievability 

Provable data possession (PDP), proposed by Ateniese et al. [24] and extended in a later journal version [25], lets a client check that a server still stores a file. The client attaches homomorphic tags to file blocks before upload; afterwards it challenges a random subset of blocks, and the server answers with one short aggregated value instead of the blocks them-selves. A lighter variant relies only on symmetric primitives and allows a bounded number of updates [26], and MR-PDP [27] extends the idea to several replicas of the same file. Proofs of retrievability (PoR) give a stronger guarantee: a server that passes the checks must hold enough data for the file to be recovered. Juels and Kaliski [28] obtain this with hidden sentinel blocks and error-correcting codes; Shacham and Waters [29] construct compact PoRs, one of which can be verified with public parameters; Dodis et al. [30] analyze PoR through hardness amplification; and HAIL [31] spreads a file over several providers so that integrity and availability can be checked and restored together. All of these protocols operate on blocks inside a file and keep their verification material with the owner or in public keys rather than on a ledger. The idea we borrow from them is random sampling: challenging c random units catches a corrupted fraction with a probability that can be computed in advance (Section V-G). 

B. Public and Dynamic Auditing 

Public auditing delegates verification to any third party. Wang et al. set out the requirements for publicly auditable cloud storage [32] and designed auditing that hides the data from the auditor by masking the server’s response [33], [34]. In a separate scheme [35], they authenticate block tags with a Merkle hash tree, so that the auditor can check block positions and the owner can modify, insert or delete blocks; the owner signs each new root and the server keeps it. Erway et al. [36] support updates with a rank-based authenticated skip list. Yang and Jia [37] add dynamic updates and batch auditing over many owners and clouds, and Zhu et al. [38] combine responses from several providers in a multicloud setting. In this line of work, the auditor trusts the reference value because the owner has signed it. 

C. Hash Trees over Untrusted Storage 

Hash trees have long been used to protect data held by parties that are not trusted. SUNDR [15] keeps a file system on an untrusted server while letting clients detect misbehavior, and Crosby and Wallach [12] build tamper-evident logs from a history tree that yields compact membership and consis-tency proofs. Certificate Transparency [13], [14] publishes certificates in Merkle-tree logs that anyone can audit. Our commitment follows the leaf and node encoding of these logs, but it is applied to the objects of a storage bucket and the root is anchored in a smart contract. 

D. Blockchain-Assisted Auditing 

Several schemes use a blockchain to remove or constrain the third-party auditor. Liu et al. [39] let owners and consumers of IoT data verify integrity through smart contracts, and Yue et al. [40] combine Merkle trees with a blockchain for peer-to-peer cloud storage and study how many samples to check. Zhang et al. [41] keep certificateless tags for the proof itself and use Ethereum to derive unpredictable challenges and to time-stamp each audit, so that a late auditor can be identified. Wang et al. [42] replace the auditor with a contract that pays the provider only when its periodic possession proofs verify. Shu et al. [43] decentralize auditing over a blockchain network and use a DAO-style design to limit dishonest auditors and miners. Lin et al. [44] record auditor activity on a consortium chain, where a contract flags abnormal behavior. These works study proof aggregation, incentives and auditor accountability; to our knowledge, they do not provide an S3-level, per-object classification of objects as intact, modified or missing together with a measured breakdown of where audit cost arises. 

E. Positioning 

Our design deliberately uses fewer primitives than the tag-based schemes: SHA-256 only, no keys for verification, and one 32-byte root per dataset on-chain. The price is that each audited object must be downloaded, so communication savings come from auditing a subset of objects rather than from aggregate proofs. We do not claim stronger security than the schemes above. Our contribution is an implementation and measurement study of the simpler design on an S3-compatible store, with per-object, three-way classification. IV. P ROBLEM STATEMENT , T HREAT MODEL AND 

REQUIREMENTS 

A. Problem Statement 

A data owner stores a dataset D =

{(k1, D 1), . . . , (kn, D n)} of objects with keys ki and contents Di in a bucket of an object store. At a later time, any party should be able to decide, for any object or for the whole dataset, whether the stored data still equals D, and to identify which objects were modified or deleted, without trusting the provider, without the owner being online, and without downloading the dataset for every check. 

B. System Entities  

> •

Data owner uploads D, computes the commitment and registers it on-chain. Trusted at commitment time.  

> •

Cloud storage provider (CSP) stores the objects and the off-chain tree metadata and runs the prover , which answers proof requests. Untrusted for integrity.  

> •

Public auditor challenges objects, verifies proofs and may record the outcome on-chain. Needs no secret; anyone can act as auditor.  

> •

Smart contract on an Ethereum-compatible chain stores the trusted root, the object count and the audit log. 

C. Threat Model 

The CSP, or an attacker who controls it, may: (i) modify the content of one or more objects; (ii) delete objects; (iii) replace an object with another stored object’s content or rename it; (iv) alter the off-chain tree metadata; (v) return forged sibling hashes, wrong keys or proofs for a different index; and (vi) answer audits inconsistently, for example serving correct data only to some requests. It may also try to change the integrity reference itself. 

Assumptions. SHA-256 is collision- and second-preimage-resistant. The chain provides integrity of committed state and the contract code is correct. The owner’s signing key is not compromised, and the owner computes the commitment over the intended data. The auditor’s own environment (client code, reading of chain state) is not compromised. 

Out of scope. The mechanism does not protect against: data that was already wrong when the root was computed; a compromised owner key or root-generation process, which can register a wrong root; denial of service and unavailability of the CSP or the chain; a compromised auditor client; loss of confidentiality (objects are not encrypted by this mechanism); and recovery of lost data, since auditing detects but does not repair. 

D. Requirements 

R1 Detection: any modification or deletion of a committed object is detected when that object is audited. R2 Localization: a full audit identifies exactly which objects failed and whether each was modified or missing. R3 Public verifiability: verification uses only public informa-tion (the on-chain root and object count). R4 Tamper-resistant reference: the CSP cannot change the trusted root. R5 Efficiency: a single object can be audited without retriev-ing other objects, and on-chain state is independent of

A. System Architecture 

Fig. 1 shows the architecture and the two phases of the protocol. In the commitment phase , the owner uploads the objects, hashes them, builds the Merkle tree and registers the root and the object count in the contract; the full tree (object keys and node hashes) is stored off-chain next to the data, where the prover can use it. In the audit phase ,the auditor reads the trusted root from the contract, chooses which objects to challenge, downloads each challenged object, obtains its sibling path from the prover, recomputes the root and compares. The division of state is strict:

Off-chain (object store): object contents; object keys; the Merkle tree metadata ( n keys and 2n−1 node hashes). None of it is trusted.  

> •

On-chain (contract): dataset identifier, Merkle root (32 bytes), object count n, registration time, version and owner address; one audit record per audit (root checked against, time, objects checked, objects failed, auditor). No object data.

The prototype is written in Python and Solidity; Table II lists its components. In total it comprises about 1,030 non-blank lines, including the experiment harness and plotting code. 

Merkle library. Digests use Python’s hashlib SHA-256. The tree is kept as a list of levels, so proof generation is a walk of ⌈log 2 n⌉ list lookups. Proofs carry the sibling list and an integer bitmap of directions, the same encoding the contract accepts. 

Storage and prover. Objects are stored in one bucket per dataset under flat keys ( obj-0000000.bin , . . . ) and ac-cessed with the MinIO Python SDK [5]. The prover is a class that holds the commitment’s levels and keys and answers 

challenge (i) with (ki, π i); in the experiments it runs in the auditor’s process, so its time is measured separately and transport of the proof is accounted for by its byte size, Eq. (9). 

Smart contract. MerkleAuditRegistry exposes 

registerRoot , getRoot , recordAudit , getAudit ,

auditCount and the view function verifyProof . Adataset occupies three storage slots (root; count, time and version; owner) and an audit record two. A second contract, 

PerObjectHashRegistry , which stores every object digest on-chain, exists only as an evaluation baseline. Both are compiled with solc 0.8.24 (optimizer, 200 runs; 2,656 bytes of runtime code for the registry) [45] and deployed on a local Hardhat network [46]; chain.py calls them through Web3.py [47]. 

Measurement. Each audit records separately the time to read the root from the chain, to retrieve objects, to compute digests and leaves, to generate proofs and to verify them, using time.perf_counter , as well as the bytes of object content and of proof metadata. Python’s garbage collector is run before each repetition, and peak memory of commitment construction is measured with tracemalloc in a separate, untimed pass. For transactions we record gas used from the receipt and wall-clock time from submission to receipt; for view functions we record eth_estimateGas , which includes the 21,000 intrinsic gas of a transaction, although a view call made off-chain costs nothing. 

Validation. Six automated tests check that every proof verifies for all indices of trees with 1–69, 127–129 and 1,000 leaves, that proof length never exceeds ⌈log 2 n⌉, that a modified leaf, a swapped key or a forged sibling fails, that the promotion rule of Eq. (4) holds, and that the Solidity 

verifyProof accepts every proof the Python verifier ac-cepts (trees of 1, 2, 3, 7 and 33 leaves) and rejects a forged leaf. 

A measurement artifact we removed. In initial runs every GET took about 44 ms regardless of object size, while a HEAD request took 1 ms. The cause was Nagle’s algorithm on the server socket interacting with delayed acknowledgements on the client. We patched the S3 server to set TCP_NODELAY ,after which a GET of 100 B to 200 KiB took 1.1–3.5 ms. All reported results use the patched server. VII. E XPERIMENTAL METHODOLOGY

Registration and audit records would then take seconds to minutes to confirm, while the root read stays a local RPC call.

IX. S ECURITY ANALYSIS 

The integrity decision is always made the same way: current data → current digest and leaf → root reconstructed with the proof → comparison with the trusted root → decision. The blockchain does not detect tampering; it only guarantees that the value compared against has not changed since registration. 

A. Modification. If D′

B. Multiple modifications. Each object is verified through its own path against the same root, so several modifications neither cancel nor hide each other (E3: 2,205 of 2,205). With sampling, an unchallenged modification goes unnoticed in that audit; the residual risk is 1 − Pdet of Eq. (8), and repeated audits with fresh random samples reduce it further. The challenge must be unpredictable to the CSP; our auditor draws it locally, and Zhang et al. [41] show how block hashes can make it publicly verifiable. C. Deletion. The committed tree fixes the key and position of every object and the contract fixes n; a missing object therefore fails as MISSING , and removing or renaming its tree entry fails as MODIFIED (E4). Integrity auditing cannot restore the object; that requires replicas or backups. 

D. Substitution, reordering and replay. Because the leaf binds SHA256( ki), serving one object’s content under another key, or swapping two objects, fails. Serving an older version of an object passes only if that version is the one committed by the current root; after a legitimate update and re-registration, stale content fails. 

E. Integrity of the reference record. Only the owner address can change a dataset’s root, and every change increments the version and emits an event, so a CSP cannot replace the root and a legitimate change is visible. Audit records are append-only and include the root they were checked against. 

F. Hash collisions and tree structure. NIST assigns SHA-256 a collision strength of 128 bits [10]; no practical collision is known for it, in contrast to SHA-1 [11]. Distinct prefixes for leaves and internal nodes [13] prevent presenting an internal node as a leaf, and promoting unpaired nodes avoids the ambiguity of trees that duplicate the last node, in which two different leaf sequences can share a root. 

G. Smart-contract trust and root generation. Blockchain immutability guarantees that the registered root is the one that was submitted, not that it was correct . If the owner’s environment or key is compromised, or the data was already corrupted when hashed, an attacker-chosen root is registered and the faulty data will pass every audit. Root generation must therefore run in a trusted environment over the intended data, and the owner key must be protected. 

H. Limits of immutability and of the mechanism. The contract cannot see off-chain data, so its guarantee is only as strong as the auditor’s honest execution of Algorithm 4, and it rests on the contract being free of the implementation flaws catalogued for Ethereum contracts [22], [23]. The scheme pro-vides neither availability nor confidentiality: a CSP that refuses to answer causes a failed audit but no recovery, and auditors read the plaintext of the objects they check; confidentiality would require encrypting objects before upload [7]. A chain reorganization or a censored transaction can delay registration on a public network, which is outside our local evaluation. X. D ISCUSSION 

Answers to the research questions. RQ1: unmodified objects always passed (E1), and single modifications of three kinds were detected and localized in 15 of 15 trials (E2). RQ2: full audits identified all 2,205 modified and all 830 deleted objects, separated the two classes and produced no false positives (E3, E4); sampled audits detect violations with the probability of Eq. (8). RQ3: construction and full audits are linear in n, proof size and verification logarithmic, and targeted and sampled audits constant in n (E5). RQ4: a full Merkle audit transfers about 1% more than a full-data audit; a targeted audit needs one object and a proof of under 500 B, and a 100-object sample 1% of the 10,000-object dataset. RQ5: the root costs 91,863 gas per dataset version independent of n, and an audit needs one free chain read. 

Where the benefit lies. The measurements correct a common expectation: a Merkle tree does not make checking every 

object cheaper, because each object still has to be read and hashed, and in our testbed retrieval was 94% of a full audit. Its benefits are elsewhere. It replaces a per-object reference list, which grows with the data and must itself be protected, by a 32-byte value that fits in a contract at constant cost (Fig. 12); it lets anyone check one object, or a random sample, against that value at a cost independent of the dataset size; and it localizes each failure. Practical deployments would therefore combine frequent sampled audits, whose detection probability can be chosen through c, with occasional full audits. XI. T HREATS TO VALIDITY 

Internal validity. All components share one 2-vCPU virtual machine, so object retrieval competes with the auditor and the chain node for CPU, and absolute retrieval times would differ with separate hosts. The S3 server needed a socket-option patch (Section VI); without it, retrieval times were inflated by 40 ms per GET. Five repetitions (three at 10,000 objects) give modest statistical power; we report standard deviations, not confidence intervals. The prover ran in the auditor’s process, so network transfer of proofs is represented by byte counts, not by measured time. Detection probabilities of sampled audits were estimated by drawing samples over the measured per-object outcomes, complemented by one real sampled audit per repetition. 

External validity. The object store was s3s-fs over loopback, not MinIO or a production cloud store; network latency, bandwidth limits, erasure coding and request pricing of real providers would raise retrieval time and cost, which strength-ens rather than weakens the relative value of sampled audits. The blockchain was a local Hardhat network with instant mining; gas values are those of the EVM and carry over to Ethereum-compatible chains, but latencies do not. Datasets were synthetic, with object sizes from 1 KiB to 256 KiB and at most 10,000 stored objects (441.66 MiB); very large objects or millions of stored objects were evaluated only through the in-memory benchmark. Timings depend on the Python implementation. 

Construct validity. “Detection time” is the duration of a targeted audit of an object already known to be affected; time until a violation is noticed in practice depends on the audit schedule. Peak memory was measured with tracemalloc 

and covers Python allocations only. XII. L IMITATIONS 

The evaluation is a local simulation, not a production cloud deployment. The security of the scheme depends on the root being generated over correct data and registered with an uncompromised key. Any change to the dataset requires re-building the affected path and registering a new root (37,885– 37,897 gas per update here), so frequently changing data incurs on-chain cost per committed version; the prototype rebuilds the tree rather than updating it incrementally. Auditing detects but cannot restore deleted or modified objects, and it does not guarantee availability; recovery requires redundancy across providers, as in HAIL [31]. Auditors must download the objects they check, which reveals their contents and makes full audits as expensive as full downloads. On a public chain, transaction latency and gas fees would add seconds to minutes and monetary cost to every registration and recorded audit. XIII. F UTURE WORK 

We plan to repeat the evaluation against MinIO and a public cloud object store with the auditor on a separate host, and on an Ethereum test network to measure confirmation latency. The tree can be extended with incremental updates for insertions and deletions, and challenges can be derived from block hashes so that sampling is publicly verifiable. Combining the root with homomorphic tags [24], [35] would allow auditing without downloading object content, and privacy-preserving auditing [34] or zero-knowledge proofs could hide object contents from auditors. Incremental tree maintenance can draw on dynamic schemes [36], [37]. XIV. C ONCLUSION 

This paper examined, through an implementation and re-peated measurements, how far a deliberately simple design can go: SHA-256 leaves that bind each object’s key to its content, one Merkle root per dataset, and a smart contract that keeps the root and an audit log. In the S3-compatible testbed with a local Ethereum network, no unmodified object was ever flagged, and every injected fault was found and attributed to the right object and class: 15 single modifications, 2,205 modifications in multi-object trials and 830 deletions. The costs separate cleanly. Building the tree and auditing every object grow linearly with the number of objects, and a complete audit is about as expensive as downloading the data. Checking a single object depends only on the logarithmic proof length (14 hashes, or 495 B including key and bitmap, at 10,000 objects), which kept targeted audits near 10 ms and 100-object samples near 150 ms at every dataset size we tried; the measured detection rates of sampled audits followed the hypergeometric model. Anchoring the root on-chain cost 91,863 gas per dataset version, 252 times less than writing 1,000 individual digests. The mechanism verifies integrity only; it neither keeps data confidential nor repairs it. All measurements come from a single-host simulation, and repeating them on production storage and a public blockchain remains future work. DATA AVAILABILITY
