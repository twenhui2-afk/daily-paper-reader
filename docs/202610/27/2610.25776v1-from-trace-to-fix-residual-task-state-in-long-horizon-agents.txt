ABSTRACT 

Recovering from failures in long-horizon, stateful language agents is challenging because the action introducing a defect, the symptom exposing it, and the per-sistent state requiring repair frequently diverge. Existing methods largely focus on retrospective failure attribution, leaving sequential diagnosis and state repair poorly integrated under constrained budgets. We introduce TRACE–FIX , a unified recovery framework centered on versioned residual task state. T RACE transforms execution logs into a structured dependency-linked ledger, prioritizing unresolved task requirements rather than salient surface errors. F IX formulates recovery as budgeted planning over admissible actions, incorporating outcome forecasting and explicit repair-reserve constraints to prevent premature budget exhaustion. To rigor-ously decouple localization accuracy from downstream repair capability, we present 

LongH-Debug , evaluating root-cause attribution, verified-fault recovery, and end-to-end closed-loop execution independently. Our empirical analysis demonstrates that structured residual tracking substantially improves causal localization over raw-trace baselines, while budget-aware sequential planning converts verified fault signals into more reliable task recovery without destructive trial-and-error. Code is available at https://github.com/toffeecat/tracedp .

1 INTRODUCTION 

Language-model agents increasingly complete tasks by changing persistent state: they write files, update databases, invoke tools, create intermediate artifacts, and make decisions that later steps depend on (Dong et al., 2026; Zhou et al., 2024; Xie et al., 2024; Jimenez et al., 2024). In such tasks, the action that introduces a problem need not coincide with the step where the problem becomes visible. The environment can also change again before debugging begins. As a result, the historical cause, the observed symptom, and the state that currently needs intervention can be different. A retained database-recovery run illustrates the distinction. A successful SQLite operation silently removes the write-ahead log that contains records needed later in the task. Subsequent commands continue normally, the actor eventually recognizes the mechanism, and the final failure occurs long after the destructive state transition. At recovery time, replaying the final error or blaming the latest suspicious command does not identify what information was lost; restarting from scratch would also discard work that remains valid. The useful recovery question is instead: which task requirement is still unsupported, which historical state change is relevant to it, and what affordable action can improve the task from here? 

Prior work has made substantial progress on failure attribution, critical-step localization, counter-factual replay, and intervention-based verification (Zhang et al., 2025b; Chen et al., 2026; Ma et al., 2025; Liu et al., 2026; Zhang et al., 2025a; Qiao et al., 2026). These methods primarily organize evidence about what went wrong . Recovery adds a sequential decision problem: additional diagnosis consumes time and intervention budget, repair can invalidate earlier evidence, and the best next action depends on what will remain possible after its outcome. A more complete diagnosis is therefore not automatically a better recovery decision. We address this problem with two components over a shared runtime state. TRACE represents current task requirements together with versioned execution evidence and ranks historical events that can explain requirements that remain unresolved. 2 METHOD 

Figure 2 summarizes the runtime path. The key design choice is to treat the execution history as evidence used to construct the current recovery state, rather than as the state itself. 2.1 VERSIONED RESIDUAL TASK STATE 

The runtime maintains three linked views with different semantics. The task view contains public requirements, their prerequisite relationships, and required outputs. The execution ledger contains ordered actions, observations, resource interactions, and resource versions. The acceptance view 

contains task predicates together with the evidence and incidents that currently support or refute them. These references make a historical event relevant to a task requirement without treating a dependency or last-writer edge as causal proof (Weiser, 1981; Ferrante et al., 1987; Agrawal & Horgan, 1990). Evidence is version-bound. When evidence is recorded for a proposition, the runtime stores the versions of the resources on which that evidence depends. If a later observation changes any of those resources, the evidence is marked stale ; task revisions supported only by stale evidence are excluded when the live task view is rebuilt. We call a requirement a residual obligation when it is not currently supported, is blocked by an unresolved prerequisite, or has lost its support through such a version change. The recovery state consists of these residual obligations, their current evidence, the historical events linked to them, and the legal action slate. We keep the remaining intervention budget separate from this state representation; a planner decision is made from the compiled state together with the remaining budget. This avoids counting budget both inside a state transition and again in the planning recursion. 3Under review 2.2 TRACE: STRUCTURED HISTORY , EXPLICIT RANKING 

TRACE first compiles the public execution into a residual ledger. Each event retains its identity and order and is annotated mechanically with its actor or tool summary, observed result, referenced resources, explicit write targets, and upstream writer links. The task contract and current residual obligations provide the context in which these event-level effects are interpreted. The current ranking stage is explicit rather than implicit in the graph construction. An audited LLM call receives the public task specification, the observed failure, and the compiled residual ledger and returns the top historical event IDs, ranked from most to least likely to have created an unresolved task condition. The prompt asks the ranker to distinguish state-changing writers from later observations, tests, or reports of the failure, and to consider omitted or misordered actions when no explicit harmful write explains the outcome. The ledger therefore structures the evidence presented to the ranker; it does not deterministically declare the root cause. TRACE writes its result to an immutable fault packet containing the ranked event hypotheses, their public evidence references, the residual obligations they may affect, and qualified checks that can test them. Verification remains separate from ranking: a high-ranked event is a localization hypothesis until an admissible check, replay, or intervention supports it. 2.3 FIX: BOUNDED PLANNING OVER THE LIVE ACTION SLATE 

FIX does not operate over a fixed four-action alphabet. At each recovery boundary the runtime emits the actions that are actually legal for that state, with stable action identities, target bindings, and declared costs. Depending on the environment, the slate can include actor continuation, registered checks, task- or resource-targeted recovery requests, additional diagnosis or completion requests, and submission of the current state. The current planner uses a separate no-tool LLM as a forecast model . It receives only public runtime state: the task graph, residual predicate states, registered checks, a bounded window of recent actor execution summaries, the live candidate catalogue, remaining time, and remaining intervention budget. For each root action it predicts bounded numeric outcomes; for checks these include masses for supported , refuted , and unknown together with estimates of what the same actor can accomplish after each verdict. It may additionally expand at most two reachable second-step actions. Terminal leaves carry a compact estimate of task success and the fraction of the residual problem expected to remain unblocked. These forecasts are planning estimates, not calibrated probabilities. Runtime code validates their schema and numeric ranges, derives outcome semantics from the action type, rejects transitions that create time or budget, and compiles the accepted forecast into a depth-two decision tree. Standard dynamic programming then compares the expected downstream recovery of the affordable candidates. The model never outputs the selected action or a Bellman value directly; both are recomputed by the runtime from the admitted forecast. If the forecast is missing or fails an admission gate, the runtime falls back to actor continuation rather than inventing a transition. The intervention budget is an abstract, frozen cost ledger rather than a token or dollar measure. In the evaluation contract, each declared TRACE, FIX-controller, or actor-continuation model call costs one unit; executable checks and repairs use the costs frozen in the environment’s qualification catalogue. Tokens, wall-clock time, and monetary cost are reported separately. This shared ledger makes “inspect more” and “preserve budget for repair” directly comparable. 2.4 EXECUTION , RECOMPILATION , AND HANDOFF 

Planning ends when an action is selected; recovery evidence begins only after that action is executed. The execution receipt records the observed result and the resource versions at the resulting boundary. Any changed resource invalidates evidence bound to its previous version, incidents and predicate states are updated, and the residual task is recompiled before another decision is allowed. A local intervention is not treated as task success. After its postcondition is checked, control returns to the same actor when continuation is legal; the benchmark’s final verifier scores the state produced by that continuation. 4Under review 10 2 10 3

3 LONG H-D EBUG BENCHMARK 

LongH-Debug is organized in two tiers so that corpus scale is not confused with recovery capability. A failure record contains a public task specification, the actor-visible trajectory, and the public failure signal needed for localization. A recovery-qualified case additionally requires a reproducible failed entry state, the task/resource/version records needed to reconstruct residual obligations, a frozen catalogue of executable checks and repairs, a common cost ledger, and an independent final verifier. Only this qualified subset is used for experiments that execute recovery actions. 

Source environments. The corpus draws natural failures from seven environments with different state mechanisms. Terminal-Bench (Merrill et al., 2026) supplies persistent filesystem and artifact state; τ 2-bench (Yao et al., 2024) supplies transactional state across tool-mediated conversations; ALFWorld (Shridhar et al., 2021), ScienceWorld (Wang et al., 2022), and TextWorld (Cˆ ot´ e et al., 2019) supply symbolic embodied state; and BrowseComp-Plus (Chen et al., 2025b) and xbench (Chen et al., 2025a) supply long search trajectories. We preserve each environment’s native task semantics rather than converting them into a shared synthetic state space. We plan to collect 1,500 natural failure trajectories, with each environment quota bounded by the executions that the source environment can actually provide. The quotas are planned allocations, not counts of collected trajectories. 

Long-horizon annotations. We do not use transcript length as the definition of a long-horizon failure. For localization cases with supported dependency annotations, we record two separate axes. 

Dependency depth Hc counts the supported dependency chain connecting a decisive historical event to the residual obligation it blocks. Feedback delay Hf counts the decisions between that event and the first public evidence that reveals its consequence. The localization population is stratified by these axes, allowing a long transcript with a local fault to be distinguished from a failure with genuinely distant dependencies or delayed evidence. 

Evaluation populations and outcomes. LongH-Debug defines three matched populations. TRACE is evaluated on N = 200 task-disjoint natural failure records under identical public inputs. FIX is evaluated on N = 120 recovery-qualified cases where every fixer receives the same independently verified fault packet. The full TRACE ×FIX crossing uses N = 60 qualified tasks restored from the same failed entry state and scored by the same official verifier. The protocol records three different outcomes. Each row removes one decision-relevant mechanism rather than replacing the method with an unrelated weak agent. Three additional diagnostics are required before a strong planning claim is made. Second, we compare the selected action against an oracle-outcome upper bound and report action-ranking regret rather than treating forecast probabilities as calibrated by construction. Experience adaptation. The optional cross-case outcome adaptation is not part of the primary experiment chain. Historical guarded development removed negative transfer but produced no uplift over the non-memory policy. We therefore do not use this component to support the TRACE or FIX claims. 

5 LIMITATIONS 

TRACE–FIX has several boundaries. First, the residual state is an approximation: missing dependen-cies, unobserved side effects, or incorrect resource links can exclude relevant events; dependency links narrow hypotheses without establishing causality. Second, FIX relies on bounded lookahead with uncalibrated forecasts, where truncation and estimation errors can affect action selection. Third, recovery requires reproducible failed states, a frozen check-and-repair catalogue, and an independent verifier, so results may not transfer to open-world settings without replay or known repair actions. Finally, recovery value depends on the continuation actor and cost model; we claim neither optimal control nor unique causal identification. 

6 CONCLUSION 

Diagnosing and recovering from long-horizon agent failures requires decoupling root-cause local-ization, budgeted state repair, and end-to-end execution. We formalize this separation through TRACE -F IX : T RACE represents public history as an explicit residual ledger to prioritize unsatisfied task requirements, while F IX conducts bounded dynamic programming over verified public states and runtime execution receipts. Across matched benchmarks and factorial evaluations, structured residual tracking substantially improves root-cause localization, targeted planning enhances recovery yield under equivalent fault packets, and their closed-loop integration outperforms either component in iso-lation. By converting historical failure explanations into actionable residual obligations, T RACE -F IX 

provides a principled framework for reliable, budgeted recovery in persistent stateful environments. 9Under review
