# A Deterministic Security Runtime for LLM Agents on MPI and Batch-Scheduled HPC Systems: Consensus-Governed, Hardware-Rooted Supervision of Every Rank 

Alfredo Metere Enclawed, Inc., California, USA

Abstract 

Large language model agents launch simulations on high-performance computing (HPC) systems, where one sbatch or mpirun can commit thousands of node-hours and a forged result can cost lives. Of 23 surveyed systems, none supervises the running job, and none holds when the control host is compromised. We fix both. Enclawed , our deterministic security runtime for AI agents, has until now served a single user; this work makes it a distributed runtime for parallel HPC and agent swarms. The Enclaweder , our hardware root of trust, keeps a compromised host from becoming a catastrophe. A launch gate decides every launch by policy alone, refusing what it cannot parse. Once the job runs, a swarm chain grants short leases against signed heartbeats and evicts on evidence, and a supervisor around every rank pauses it when its lease lapses and kills it on tampering. Each node signs with its Enclaweder’s key, so the host can forge none of this. Enclawed needs no administrator privileges and plugs into existing clusters unchanged, over Secure Shell alone. Supervision leaves the compute loop of a 16-rank LAMMPS job unchanged, on graphics processors too, and adds about 3 s of start-up. Twelve live attacks on Enclaweder-keyed ranks, colluding coordinators included, ended fail-closed. Sixteen agents on a real model attempted 24 launches that planted instructions ordered; the gate denied all 24 and allowed all 108 legitimate ones. Enclawed’s core and the HPC Agent Security Benchmark are open source. 

# 1 Introduction 

1.1 Agents act with the operator’s authority 

Scientific high-performance computing (HPC) is where large language model (LLM) agents will first spend real money unattended, because an agent that runs a simulation acts through the scheduler rather than through an application programming interface (API): it writes an input deck, picks a rank count and a wall time, and types sbatch or mpirun . Each of those commands runs with the submitting user’s full credentials on every node it touches, so a wrong or hijacked decision is executed with the operator’s authority. Current HPC controls cannot tell the two apart, since they authenticate the submitter rather than the behavior; a recent position paper names this the “hijacked authorized agent” problem [26]. Without a control that can tell them apart, facilities fall back on prohibition: at least one university center now bans agents from submitting or operating jobs without explicit per-action human approval. 1arXiv:2610.33318v1 [cs.CR] 23 Oct 2026 1.2 Forged results cost lives 

A hijacked decision can do worse than waste node-hours: it can forge a result, and a forged simulation result can cost lives. A hijacked agent can run another build of the code, change one parameter or one line of the input deck, rewrite a restart file or a material table that the running job reads, or report numbers the run never produced, and none of these changes the form of the output. A forgery written into a running simulation is the hardest to detect, because every later step is computed from the forged state. Rerunning the job does not expose it either. Atomic additions in force accumulation on graphics processing units and the reduction order of MPI collectives make floating-point sums depend on scheduling, so two honest runs of one input already differ in their last bits; where the dynamics amplify perturbations, as hydrodynamic instabilities do, those differences grow, and a rerun that disagrees with the forged run cannot tell the forgery from the nondeterminism. A systematic forgery, such as an altered equation-of-state table, shifts the answer itself and survives every rerun with the same inputs. Wherever simulation is the evidence for a design, the forgery passes into the design. The clearest case is the stockpile stewardship of the National Nuclear Security Administration (NNSA): the United States has conducted no nuclear explosive test since 1992, so its laboratories use simulation to predict the performance, safety and reliability of nuclear weapons and to certify them in the absence of testing [28]. Government and industry design and certify on physics simulation in the same way: weapons, aircraft, spacecraft and launch vehicles, ships and submarines, cars, trains and other vehicles, nuclear reactors, medical devices, precision machinery, and the structures, materials and drugs behind them. In each of these, a design certified on a forged result can fail in service, and when it fails, people die. A hijacked agent with scheduler access at such a site therefore puts lives at risk, not only an allocation. 

1.3 Where existing systems stop 

The systems that let agents use HPC today sit at two layers. Agent frameworks such as Academy [23], URSA (Universal Research and Scientific Agent) [18], LAMMPS-Agents [3] (agents for the Large-scale Atomic/Molecular Massively Parallel Simulator, LAMMPS) and Lawrence Livermore National Laboratory’s (LLNL’s) descriptive execution work [46, 47] give the agent the operator’s scheduler access and concentrate on capability. A second group gates the launch: Diamond Agent checks partitions, wall time and credit before placement [50]; LARA-HPC, a validation-driven workflow framework on the Fugaku supercomputer, removes shell access and submits only fixed templates that pass a dry run [10]; a few Model Context Protocol (MCP) servers allow-list operations and cap resources per site [39]. These gates reduce the risk, and we compare against them in Section 4.1, but three limits keep them from removing it. First, they stop at submission, so nothing watches the job after the scheduler accepts it. Second, they trust the host that runs the gate, so a compromised gateway or credential store removes the gate with it. Third, they are not deterministic in the sense a security reviewer needs: several let the LLM itself choose resources inside loose bounds, and none refuses a command it cannot fully parse. 

1.4 Our approach 

This paper describes a runtime that removes these three limits. Enclawed has until now applied deterministic guarantees to the tool calls of a single user’s agents [32]. This work makes it a distributed runtime: for parallel jobs under the Message Passing Interface (MPI) and batch schedulers, and for swarms of agents across many machines, with the Enclaweder keeping a compromised host from becoming a catastrophe. The design question is therefore not how to launch a job, which every 2framework above does, but how to run an agent’s job under a security runtime whose decisions do not depend on any single host, any single process, or the model’s judgment. Three mechanisms answer it (Figure 1): 1. A launch gate (Section 2.2) in the agent’s tool path. Before an exec tool call runs, the gate parses the shell line with a POSIX (Portable Operating System Interface) word splitter, unwraps launcher wrappers, recognizes mpirun , mpiexec , Hydra, srun , sbatch (including --wrap and 

#SBATCH directives), salloc , msub (-l nodes=N:ppn=P,walltime=... and #MSUB /#PBS ), and 

flux run , submit , batch , alloc and bulksubmit with #FLUX: directives and Flux Standard Duration times. It follows sh -c , source and executable scripts, and refuses any construct it cannot see through — an unexpanded variable in a launcher argument, an unknown option spelling, a change to PATH or LD_* — rather than guessing. The decision is a pure function of policy and the command text. 2. A swarm chain (Section 2.3): n ≥ 2 coordinators run Tendermint, plus a finality step that makes forks accountable, over a ledger of membership, policy epochs and leases [17]; the coordinator set grows with the swarm. A node holds permission to perform irreversible actions only while a lease for the current epoch is in force, and a lease is granted only against a fresh heartbeat signed by the node’s hardware key with status clean . A dirty heartbeat is itself the eviction evidence; a coordinator’s two conflicting signatures for one slot are the evidence for its own eviction. Below two coordinators the chain halts and every node fails closed. 3. A per-rank supervisor (Section 2.4): the site’s mpiexec is a shim that wraps every rank in 

swarm rank , which reads its rank and job id from the process management interface (PMI) environment, or the one set by its successor PMIx (Process Management Interface – Exascale) [38], Slurm [52] or Flux [1], follows the chain as a node, serves lease decisions to the simulation over a Unix socket protected by a per-launch token, pauses the rank ( SIGSTOP ) when its lease lapses, resumes it when a lease returns, and kills it ( SIGKILL ) on eviction, device tampering or chain halt. We evaluate on LAMMPS [48] with MPICH (originally MPI over Chameleon) [36], a widely used MPI implementation. 

1.5 The open issues this paper closes 

No existing system lets an agent drive HPC jobs under guarantees that hold when the agent, a host or a coordinator is compromised. We identified and address four issues, each a strict requirement for the security of such a runtime. The first three follow from the three limits of existing gates; the fourth follows from the prohibition with which facilities answer the risk today, which only a runtime they can deploy will replace. Because the agent’s requests are untrusted text, every launch it attempts must be decided from site policy and the command text alone, and a launch that cannot be fully parsed must be refused. 2.1 Threat model 

The agent runs inside an Enclawed gateway on a login node, a workstation or a service host. It has a model, tools, and the operator’s credentials for one or more schedulers. We assume the following adversaries, singly or together. • A hijacked agent. Prompt injection, a poisoned skill or a model error makes the agent request launches the operator would not: wrong code, wrong size, wrong queue, exfiltrating or destructive payloads; or it stays within policy and changes the result: another input, another parameter, a rewritten restart file, a falsified report. The agent’s requests are untrusted text. • A compromised gateway host. The process that runs the agent, including the launch gate, may be subverted. Any control that lives only on this host is assumed lost. • A compromised node. A compute node running ranks of the agent’s job may be subverted by its own workload or through the job’s user account. The node’s hardware root of trust is not compromised — its key does not leave the device — but the software around it is. What the job’s account and root can do to the supervisor is bounded in Section 4.2. • A minority of compromised coordinators. Up to f of n = 3 f + 1 coordinators may be Byzantine: crash, delay, equivocate, or sign arbitrary statements with their genuine keys. • An outsider on the network. Can connect to any coordinator port, claim any role, replay anything it has seen, and edit files on a coordinator’s disk if it has gained that access. We want five goals, G1–G5: (G1) no launch the policy forbids ever reaches a scheduler, whatever the agent says; (G2) no rank performs an irreversible action without a lease recorded on a chain that 2 f + 1 honest coordinators agreed to; (G3) a node whose root of trust reports tampering, or whose lease lapses, stops acting within a bounded time; (G4) a coordinator that misbehaves in a detectable way is removed on evidence, and undetectable misbehavior by ≤ f coordinators cannot forge, fork or revive a lease; (G5) loss of quorum stops the swarm rather than freeing it.

A launch within policy can therefore compute the wrong thing, and an agent can misreport a right one; E6 (Section 3.6) shows both, by accident. Under one account, the agent’s later commands can also write the files a running job reads, and on a host that allows ptrace between processes of one user, its memory too. A site that uses agents for consequential computation therefore adds four checks of its own: 1. it fixes the input decks and parameters itself; 2. it runs the job under an account the agent cannot act as; 3. it recomputes every result from the code’s own output rather than taking the agent’s report; 4. it verifies independently every number that feeds a decision. Which commands an agent may run besides launches is a matter for Enclawed’s tool gate [32]. Leases bound who may act , not what they compute , and a wrong computation inside policy is outside G1–G5. Also out of scope: side channels inside a legitimate job; launches that reach a scheduler outside the agent’s exec tool, which Enclawed’s tool gate and egress controls cover; the scheduler’s own correctness; and physical attacks on the hardware root of trust. 

2.2 The launch gate 

The gate is a hook on the agent’s exec tool. It receives the command text, the working directory, the acting agent’s identity and any environment the tool call sets, and returns allow or refuse with a reason code. It never edits the command. 6Parsing. A POSIX shell word parser splits the line into simple commands joined by ;, && , || 

and |, keeps quoted text whole, records which words contain unexpanded expansions, and keeps redirections out of argv . Every simple command is walked. Wrappers ( env , nice , nohup , time ,

stdbuf , timeout , . . . ) are unwrapped. sh -c , bash -c , source , . and ./script recurse into the quoted text or the file, to a bounded depth. Interpreters ( python3 -m , python3 file.py ) are checked against the allow-list by the payload they will run, not the interpreter. 

Launchers. A launcher parser per family turns the command into a launch : a scheduler, a list of programs (with their argument offsets, so multiple-program, multiple-data (MPMD) launches yield several), a rank count, a node count, a wall time in minutes, a partition, an account, and whether the command controls an existing job. sbatch reads the batch script and merges #SBATCH 

directives below the command line; the same for #MSUB /#PBS and #FLUX: . A directive in the script can never raise a limit the command line set. The body of a batch script is then walked like any other shell text, so an srun inside an sbatch is seen. Read-only scheduler queries ( squeue , sinfo ,

flux jobs ) are not launches. 

Policy. A site policy lists the schedulers agents may use, an executable allow-list (a directory prefix, an exact file, a bare name resolved on PATH , or module: X for python -m ), caps on ranks, nodes and wall time, partition and account allow-lists, a lifetime node-hour budget, and whether job control ( scancel , mjobctl , flux cancel ) is allowed. A node-hour ledger charges every allocation at admission time; a launch inside an existing allocation (an srun step within a Slurm job, detected from the job environment) is not charged twice. Lists that are absent impose no limit; a list that is present but empty allows nothing. An enforce: false mode decides, records, and never blocks, for sites that want to observe before they turn the gate on. The gate parses shells and never executes them, so a construct its parser does not model costs a refusal, which this mode lets a site measure in advance. 

Fail-closed rules. The gate refuses a launch when: a launcher argument contains an expansion it cannot resolve; the launcher is named by a path that is not one of the site’s pinned shims (launcherPaths ); the command, inline or through export , env , the tool call’s own environment, 

alias or hash , changes PATH , LD_PRELOAD , LD_LIBRARY_PATH or another resolution variable; an option spelling is not one the parser knows; quoting is unterminated; or recursion exceeds its depth. The point is that an unparsed launch is treated as a forbidden one. 

Why not an LLM guardian. Some recent infrastructure-agent guardrails ask a second model to judge the first. We do not, for the same reason we do not ask the scheduler to guess: the decision must be reproducible from the policy and the command text, so that an auditor can re-derive every 

allow after the fact, and so that an attacker cannot talk the gate into a launch the way it talked the agent into requesting one. 

2.3 The swarm chain 

The launch gate protects submission; the chain protects the job while it runs, and protects the gate’s own decisions from a single compromised host. The design borrows from permissioned Byzantine-fault-tolerant (BFT) blockchains, but its ledger is small and its purpose narrow: it is a replicated, tamper-evident record of who may act now .72.3.1 Participants and keys 

A swarm has n ≥ 2 coordinators , a set of admins who approve joins and policy changes, and nodes :each MPI rank is a node, and so is each long-lived host (a gateway or service node) that may later be promoted to coordinator (Section 2.3.5). Every participant has an Ed25519 key. In production deployments coordinator and node keys live in an Enclaweder, Enclawed’s hardware root of trust, one per machine; the device holds the key, signs a 32-byte digest on request, and reports its own integrity as clean or dirty . Genesis can require that coordinator and admin keys are device keys ( requireDeviceKeys ); software keys are accepted only when a deployment turns that off. A machine may hold several devices; a key then names all of them, any one may sign for it, and its signatures are spread across them, so their throughput adds up (Section 2.5). Every signed object is hashed with SHA-256, the 256-bit Secure Hash Algorithm, as SHA-256( tag ∥ 0 ∥ canonicalJSON( v)) with a distinct tag per object type, so a signature over one kind of statement cannot be presented as another. 

2.3.2 Ledger state 

The state at height h holds: the coordinator roster; the node roster with each node’s key; the set of evicted ids (permanent: an evicted id can never rejoin); the current epoch ; the hash of the policy/trust bundle in force; a lease per node ( epoch , heartbeatSeq , durationMs , height ); and, per node, the highest heartbeat sequence number ever used for a lease. Transactions are: • node.join : a node’s key, its proof of possession (a signature over the join), and an admin approval. Refused if the id is taken or evicted, if device keys are required and the key is not one, or if either signature fails. A host’s join may name the address it would listen on as a coordinator; the admin approval covers that field, so no one else can make a node eligible for promotion. • lease.grant : a lease for the current epoch, carrying the clean heartbeat it answers. Refused if the heartbeat is for another swarm or a future epoch, if its sequence number is not above the node’s last used one (so no heartbeat buys two leases and no replay buys any), or if the duration exceeds the genesis maximum. • node.evict : with reason dirty , carrying a dirty heartbeat signed by that node’s own key; or with an admin approval. Nothing else is accepted as evidence. A promoted coordinator is still a node, so a dirty device removes it from the coordinator set as well. • coordinator.evict : carrying two statements by one coordinator for the same slot that name different blocks (Section 2.3.4). Both signatures are checked; fabricated evidence is refused. If fewer than two coordinators would remain, the chain halts .• coordinator.add and coordinator.retire : admin-approved changes to the coordinator set, with the approval bound to a roster version so it cannot be replayed after a later change; retiring below two coordinators is refused. coordinator.promote : the automatic growth rule (Section 2.3.5). • bundle.publish : a new policy bundle hash with an admin approval bound to the current epoch (an old approval cannot be replayed into a new epoch). It increments the epoch and clears every lease; nodes must renew against the new epoch. • params.update : new lease and heartbeat lengths, within fixed bounds, with an admin approval bound to the current epoch. It increments the epoch like a bundle publish. 8The policy epoch. The epoch numbers the versions of what a lease vouches for: who is in the swarm, and under which rules. It starts at 0 and increases by one with every transaction that changes either: a node joins, a node or a coordinator is evicted, a policy bundle is published, or the lease timing changes. Each increase clears every lease, so every node must renew under the new epoch against a fresh heartbeat. A lease therefore never outlives the membership and policy it was granted under: a node that holds a lease for epoch e was vouched for by a quorum that knew the roster, the bundle and the timing of epoch e, and a rank that asks its decision socket after the epoch has moved on is refused with stale-epoch until its lease is renewed. Admin approvals are bound to the epoch for the same reason, so an approval given under one policy cannot be replayed under another. 

The epoch chain. Epochs are chained. Each epoch’s hash is taken over the previous epoch’s hash and everything the new epoch starts with: its number, the block it starts at, the policy (lease timing, expiry and bundle), the coordinators, admins, members, observers and evicted ids. Every block header carries the hash of the epoch it runs in, so the quorum certificate of every block signs the whole epoch history. Rewriting any past epoch’s policy or membership changes every later epoch hash, and every later block’s certificate then fails; a block that names another history of its epoch is refused outright. Policy approvals bind to the epoch’s hash, not only its number, so an approval made in one history is worthless in another. 

2.3.3 Consensus Choice of protocol. We weighed Practical Byzantine Fault Tolerance (PBFT) [6], Tendermint [4], HotStuff [51] and its successors, Simplex [7] (an independent design), directed-acyclic-graph (DAG) based protocols, and hybrids that use trusted hardware to reach n = 2 f + 1 such as MinBFT [49]. Three properties of this system decided it: 1. Accountability outranks throughput. A misbehaving coordinator must be named by its own signatures so that the chain can evict it, and the forensic analysis of Sheng et al. [42] shows that forensic support varies sharply even between minor variants of the same protocol. 2. A machine-checked safety argument. Tendermint has a specification in TLA+, the Temporal Logic of Actions, model-checked for small systems, in which the correct processes collectively hold evidence naming at least n/ 3 culprits of any fork [24, 35]; that evidence is collective, not a proof a third party can check (Section 2.3.4). 3. A tiny load on small validator sets. The chain carries one block a second and a few hundred small transactions, so the quadratic message cost that HotStuff’s linear protocols avoid does not matter here, while HotStuff’s threshold-signature variants would erase the per-signer evidence that accountability needs [42]. Simplex is the simplest modern design and a reasonable alternative; we kept Tendermint for its verification record. We did not use trusted hardware to shrink quorums to f + 1 of 2 f + 1: with that quorum two certificates overlap in a single coordinator, so a fork exposes at most one culprit, and a single rolled-back trusted component breaks safety outright [20]. We use the hardware for key custody instead, keep n − f quorums, and leave a device-enforced sign guard as defense in depth (Section 4.2). 9Rounds. 2.3.4 Finality and accountable forks 

Tendermint as published is not fully accountable. A coordinator that precommits block A in one round and, ignoring its lock, precommits block B in a later round has signed no two statements for the same (kind, round) slot; with enough such “amnesic” coordinators two blocks can each gather a quorum of precommits, and Dong et al. show that no transferable proof then identifies more than one culprit [11]. Eviction evidence limited to same-slot double signs misses this attack. We close it with one extra step. After a coordinator decides a block by Tendermint’s rules it signs a single final statement for the height, which carries no round, and only a quorum of finals commits the block; the finals are the block’s certificate. Every follower — a node, a monitor, a coordinator catching up — accepts a block only after verifying each final in that certificate against the roster at that height, together with the parent hash and the transaction root. A certificate made of precommits is refused. The sign guard (below) allows one final per height and nothing after it. 

Proposition 1. If two different blocks at one height each carry a valid certificate, at least 2q − n

coordinators signed finals for both, and each such pair of finals is valid coordinator.evict evidence on its own. 

The proof is quorum intersection: two sets of q signers out of n share at least 2 q − n, and a final names the height and the block but no round, so two finals by one signer for different blocks at one height occupy the same slot. When a fork appears the ledger halts and reports these pairs, which any party holding the roster can check without trusting the reporter. The cost is one message delay per block. Section 2.10 checks the proposition, and the amnesia attack that motivates it, with a model checker; red-team scenarios R10 and R11 (Section 3.5) attack it live. 

2.3.5 Small swarms and growth 

Safety and liveness depend on the quorum differently. With quorum q out of n, two certificates share at least 2 q − n signers, so no fork is possible while fewer than 2 q − n coordinators are faulty; and the chain can keep committing while at most n − q are down [30, 31]. Table 2 gives both for small n. A two-coordinator swarm, the smallest we allow, is already safe against one Byzantine coordinator: both must sign every block. What small swarms lack is liveness, and losing liveness here is the safe failure: when the chain stops, no lease is renewed and every rank pauses. A swarm can therefore start with two coordinators — the operator’s computer and a login node, say — and grow. Admins may add or retire coordinators explicitly. A genesis growth rule 

(maxCoordinators , nodesPerCoordinator ) adds them automatically: a node may be promoted when its admin-approved join named it as a coordinator candidate, it holds a lease in the current epoch, the swarm has at least nodesPerCoordinator · (n + 1) nodes, and n < maxCoordinators . MPI ranks are never candidates. Only the candidate can ask: coordinator.promote carries its own signature over a recent height (within 32 blocks), proving that it is running, synced and holding its key. We added that requirement after a live run in which a host was promoted before its coordinator process was ready; at three coordinators every vote is needed, so the chain stopped until the host came up. Peers learn new coordinators’ addresses from the chain. An evicted identity can never return; a retired one returns only with a new admin approval. Dynamic membership is where BFT systems have historically been weakest: Dyno [12] gives it a foundation with paper proofs, and no mechanized proof of BFT reconfiguration exists to reuse. We test reconfiguration (Section 3.2) rather than prove it. Beyond a few dozen coordinators the next step is structural rather than numerical: per-rack or per-pod chains that checkpoint into a root chain, which we leave to future work. 

Skipping dead proposers. A crashed proposer costs a propose timeout every n-th height in plain round-robin. Each block header therefore lists the coordinators whose finals certified the previous block, and round 0 rotates over that list, a variant of the leader-reputation rule of Carousel [8]; later rounds rotate over the whole set. The list must be a sorted quorum of the current roster or empty, so a faulty proposer cannot keep the role for itself, and the list affects only who proposes first, never what is safe. The list has to be in the header: each coordinator assembles its own copy of a certificate, so deriving it from a certificate would let coordinators disagree about who may propose. 

2.3.6 Recovery 

Three details matter for an HPC deployment. (i) Restart safety. Each coordinator keeps a write-ahead sign guard: before it signs a statement for (height, round, kind) it records the hash; after a crash it will not sign a conflicting statement for the same slot, and once it has signed a final it signs nothing more at that height, so a restart cannot turn an honest coordinator into an equivocator. (ii) Liveness after partitions. Coordinators re-gossip their own current statements every second and, on seeing a later height, request a throttled sync; a coordinator that was down for minutes rejoins without operator action. (iii) Self-correction. On restart a coordinator re-verifies its stored chain from genesis, truncates at the first block that fails verification, and syncs the rest from peers; and a follower that is shown two valid certificates for different blocks at one height halts and reports the pairs of conflicting finals. 11 2.3.7 Leases and heartbeats 

A node sends a heartbeat every heartbeatMs : its id, the epoch it believes current, a strictly increasing sequence number, its wall time, and its device status, all signed by its device. Any coordinator that receives a clean heartbeat submits a lease.grant for it; a dirty heartbeat becomes a node.evict .The lease’s duration is leaseMs from genesis. The node does not trust the coordinator’s clock. When a committed block grants it a lease for heartbeat s, the node computes expiry as sent (s) + durationMs − margin on its own monotonic clock, where sent (s) is when it transmitted that heartbeat. The lease therefore ends at the node strictly before it could end at any coordinator, so the node always gives up first (G3). A reversible 

action is always allowed; an irreversible one is allowed only when the chain is not halted, the node is a member and not evicted, its device is clean , and it holds an unexpired lease for the current epoch. A node whose lease is about to lapse sends its heartbeats to every coordinator it reaches rather than to one, so a single faulty coordinator that drops them cannot starve it. Every refusal carries a code ( halted , evicted , not-member , device-dirty , no-lease , stale-epoch , expired ). 

Expiry. A node that has renewed no lease for more than the epoch’s expiryBlocks blocks is evicted ( node.evict with reason expired ). The clock is the chain itself: blocks, each certified by a quorum, never a timestamp, so no proposer can hurry it, and while the chain is stalled (a lost quorum, R2 and R11) it does not advance, so a quorum loss never turns into evictions. The evidence is the chain state every coordinator already holds: the height at which each node joined or was last leased. The rule is a pure function of that state, so every coordinator reaches the same verdict. Coordinators are exempt (their faults are judged by their own signatures), and so are observers, which hold no lease. The limit is part of the epoch’s policy: set in the genesis (by default two leases’ worth of blocks), changed only by an admin-approved params.update , and never fewer than three blocks, so that a live node, which renews on every heartbeat, is never expired between two of its own renewals. 

2.3.8 Transport 

Coordinators, nodes and monitors exchange newline-delimited JavaScript Object Notation (JSON) envelopes over the Transmission Control Protocol (TCP): hello , consensus , commit , heartbeat ,

tx and sync . The transport is not trusted: a peer may claim any role in its hello . Role claims gate only what a coordinator will bother to look at ; every statement, block, heartbeat and transaction is verified by signature against the roster before it has any effect, so a spoofed coordinator can waste bandwidth and nothing else (Section 3.5, R7). 

2.4 Per-rank supervision 

Shims. The site installs mpiexec , mpirun and srun shims ahead of the real launchers on the agent’s PATH , and pins them in the gate policy’s launcherPaths . A shim runs swarm launch , which admits the job: it creates a key per rank, submits one node.join per rank with the admin approval, waits for the joins to commit, then calls the real launcher with every program argument rewritten as swarm rank --job J -- program args . For MPMD launches each program is wrapped at its own offset. Admission for 16 ranks takes 0.2–0.5 s (Section 3.1). 

The rank supervisor. swarm rank reads its rank, job size and job id from the environment the process manager set (PMIx, PMI, Open MPI, Slurm or Flux variables, in an order that prefers the scheduler’s job id when both are present), loads its key, and runs as a swarm node. It opens 12 a Unix-domain decision socket in a mode-0700 directory, with the socket itself mode 0600, and generates a per-launch token. It then spawns the real program with the socket path and token in its environment and the PMI file descriptor passed through, so the program joins the MPI job exactly as it would have without the supervisor. Every 100 ms the supervisor evaluates the lease for an irreversible action. If the answer changes from allowed to refused with a recoverable code ( expired ,

no-lease , stale-epoch ) it sends SIGSTOP ; when a lease returns it sends SIGCONT . If the code is 

evicted , device-dirty or halted , or the site chose --on-lease-loss kill , it sends SIGKILL .When the program exits, the supervisor exits with the program’s code, or 137 if it killed it. 

The whole process tree. A rank need not be a simulation: in Section 3.6 every rank is an agent, which runs tools, and one of those tools launches a LAMMPS job. MPICH’s launcher runs its process manager in a session of its own, so that job’s ranks are outside the agent’s process group, and a signal to the group would pause the agent and leave its LAMMPS running. Every signal therefore goes to the program’s entire process tree, which on Linux the supervisor reads from the parent links in /proc before it signals anything: a killed parent’s children are reparented and can no longer be found through it. A kill first stops the whole tree and reads it again, so no process can start a child that escapes. The program itself stays in the supervisor’s process group, because a launcher ends a failed job by killing each rank’s group. A first version that moved the program into a group of its own let 15 LAMMPS ranks outlive their killed supervisors in red team scenario R3; the version measured here does not. 

Reporting a dirty device. When the supervisor kills a rank because its device went dirty , it does not exit at once: it sends a dirty heartbeat — the eviction evidence — and keeps heartbeating until the eviction is on chain or two lease durations have passed. The red team found this necessary (Section 3.5, R3): without it the rank was dead within 100 ms but the node’s lease stayed valid until it expired, and other components could not have learned why. A device that has been removed, however, cannot sign its node’s report: its key went with it, which is what a hardware key is for. Such a node stops at once, sends no further heartbeat, and leaves the swarm by expiry (E7, Section 3.7). 

The decision socket. A program that wants to check before an irreversible step (writing a checkpoint, calling an external service) writes one JSON line {token, action, class} and reads one back, {allowed} or {allowed:false, code, reason} . Tokens are compared in constant time. The socket only answers from memory, so a check costs one local round trip. A program that never asks is still supervised, by the signals above; the socket exists so that a cooperating simulation can fail closed on its own terms rather than be stopped mid-write. 

Fail-closed summary. Every path that loses certainty ends in refusal: quorum loss halts the chain and every node’s lease expires (G5); a node that cannot reach a coordinator stops renewing and pauses within leaseMs − margin (G3); a node whose device reports tampering is killed and evicted (G3); a gate that cannot parse a launch refuses it (G1); a follower shown a fork halts (G4). The one thing a compromised host can do is stop its own ranks, which is the outcome the design wants. 

2.5 One machine’s devices, shared 

Every process on a machine needs that machine’s Enclaweder: each rank’s supervisor, the operator’s monitor, an agent’s own gate. A device can have only one owner: two processes driving one device 13 interleave their requests, and the device’s answers to both are lost; in an early run 16 agents booting at once each bound the device and all 16 halted on a genuine device. Enclawed’s bootstrap therefore makes the first process on a machine that boots the hardware root its owner. The owner binds every device present (with the genuine check and the persisted dirty latch the bootstrap always applies) and serves them on a Unix socket in a directory only the user can open; every later process is its client, signs through it, reads its health, and never opens a device. Ownership is the socket itself, claimed by listening on it, so two processes cannot both own the devices. Requests from the clients are scheduled, never raced. Queues are per process and served in turn, so a process that floods the device cannot starve another’s heartbeats; each process may have at most four requests waiting, and further ones are refused at once; a request that has waited longer than its deadline (one second at most, about twenty device operations) is dropped unsent; and each device takes one request at a time. A client reaches only its own queue: the owner assigns its identity, and a reply goes only to the connection that asked. Every request, and its outcome, is recorded before it reaches the device and before its answer is returned, in an append-only, hash-chained journal (Enclawed’s audit log), and once a second the device itself signs the journal’s head into it. Rewriting the journal up to its last checkpoint would need a signature only the device can make. When the owner exits, its clients read the root as unavailable : not dirty , since a process exiting is not tampering. Gated work is refused, ranks send no heartbeat and pause, and one client takes ownership by binding the devices itself, through the same genuine check and latch. Only a real tamper, a removal, or a takeover the guard refuses latches dirty . Without a device, everything still works on software keys, and Enclawed says each time what that means: keys held on the host can be used by whoever compromises it. Using Enclawed without an Enclaweder is far more secure than not using it at all; for security that holds when the host itself is compromised, the device is required. A dirty latch belongs to the machine, not to the number of devices on it. A device that latched 

dirty refuses every later boot on that machine, whether it boots with that device, with another, or with none, until a human recovers the latch with that device present. Otherwise plugging in a second device, or unplugging one of two, would clear a tamper. 

2.6 Regulated sites: Secure Shell (SSH) as the only way in 

At most of the facilities where agentic science matters most — national laboratories and classified enclaves — a cluster exposes one thing to the outside: SSH on its login nodes, usually behind a bastion host and two-factor authentication, and often with SSH port forwarding turned off. Nothing in the design may assume more. In particular, the operator’s computer cannot open a port to a coordinator, cannot be reached from the cluster, and does not get to choose which port it connects to. 

One interactive login. The operator authenticates once, interactively, so that the site’s own prompts happen in the operator’s terminal; that connection becomes an OpenSSH control master, and every later session rides on it without a new login. Nothing in the runtime chooses or overrides how ssh authenticates, so whatever the site requires works as it does by hand: a password with a fixed part and a hardware-token part, a one-time code, keyboard-interactive prompts, a security key that must be touched, a smart card, or a certificate. Sites that require a Kerberos ticket before ssh are handled explicitly: the login first checks for a valid ticket and obtains one interactively if there is none, then authenticates with it, and forwards the ticket to the login node only when the site requires that. 14 One shared session. The master listens on the control path the operator’s own ssh configuration names for the host, so the agent’s plain ssh login1 ... commands share the authenticated session and never prompt; if the session ends, the runtime says so and asks for a new login, and until then no lease is renewed through it. Only the login node needs this: from there, the relays reach coordinators over the cluster’s internal network, and launchers reach allocated compute nodes as the site already arranges, typically without further authentication. 

Swarm peers as SSH sessions. Each swarm peer is an ordinary SSH session that runs swarm relay on the login node, which pipes the session’s standard input and output to one coordinator. The swarm’s transport was generalized from TCP sockets to arbitrary byte streams for this, so the session is the connection; no port is opened or forwarded on either side. Every session pins host keys, disables agent and display forwarding, clears all forwardings, and runs in batch mode. The relay connects only to an address the swarm directory on the cluster lists — a coordinator, or the declared endpoint of a model server running inside the job — so it cannot become the general-purpose port forwarder a site has deliberately disabled. 

The model over SSH. A model served on the cluster’s graphics processing units (GPUs) reaches the operator’s computer the same way, one SSH session per connection, and appears on that computer’s loopback interface, so a local agent can use it as if it ran locally. 

The gate and SSH. With an agent on the operator’s computer, a launch reads ssh login1 sbatch /p/stage/job.sh . The gate now parses ssh , scp and rsync . It allows only hosts, including jump hosts, that the policy lists (compute nodes by a pattern such as node*.lab.gov , whose wildcard matches only host-name characters), and refuses every option that changes where commands run or what is forwarded: local, remote and dynamic port forwarding, stdio forwarding and tunnels, agent and X Window System (X11) forwarding, a configuration file, a proxy or local command, a chosen port, control-master operations, and any -o setting outside a short allow-list (host-key checking may only be made stricter). The remote command is then checked exactly as a local one would be. A remote batch script is accepted only at an absolute path inside a declared staging directory, where the gate reads its local mirror; a relative remote path is refused, because ssh starts in a home directory the gate cannot know. Copies are allowed only from the local staging directory into the remote one, and nothing may be copied off the cluster unless the policy says so. Writing these rules exposed a gap that also affected local launches: cd /tmp && sbatch job.sh made the gate read one file while the scheduler would run another. After cd , pushd or popd , relative script paths are now refused. 

Two admin keys. Rank admissions are approved automatically by the site’s launch shims, so the cluster needs an admin key of its own. The operator’s key, created on the operator’s computer and in production held by that computer’s Enclaweder, is added to genesis as a second admin. Operator actions are signed with it, admissions with the cluster’s key, and the monitor below accounts only for the operator’s. 

The local session. A local Enclawed session attaches to such a cluster through one configuration block that names the login host (and any bastion), the swarm directory on the cluster, the operator’s key, and where the model runs: on the operator’s computer, or inside the job, in which case the model server appears on that computer’s loopback interface through the SSH bridge above. The session refuses to start cluster mode unless the HPC policy lists the login and bastion hosts, the 15 swarm’s genesis names the operator’s key as an admin, and, when the key is that computer’s Enclaweder, the device is bound and clean . Logging in needs the site’s interactive prompts and a gateway may run without a terminal, so the gateway never prompts: the operator logs in once, in a terminal, and the gateway only reuses that session. 

2.7 Deployment without administrator changes 

Cluster administrators are reluctant to change a production system’s kernel or scheduler daemons, and for good reason: a kernel module, a Linux security module, an extended Berkeley Packet Filter (eBPF) program or a Slurm plugin has to be reviewed, installed on every node and carried through every upgrade. Enclawed needs none of them. Every component runs under the account of the user who launches the job: • Shims. Ordinary executables in a directory placed ahead of the real launchers on the agent’s 

PATH . The real launchers, the scheduler and its configuration are untouched. • Supervisors. Each is the program the launcher starts in place of the rank, and the rank is its child: pausing and killing the rank are signals from a parent to its own child, and the decision socket lives in a directory the user owns. The process manager’s environment and descriptor pass through, so the scheduler and the MPI library see an ordinary job. • Coordinators. Ordinary processes on unprivileged ports, on hosts the project already uses or as steps of the user’s own allocation. • The operator’s path. The site’s own SSH with the site’s own authentication. The relay is a command in an ordinary session, and no port is opened or forwarded (Section 2.6). The runtime is a single Node.js program installed in a directory the user owns. The experiment scripts, published with this paper (Section 5), run the coordinators, the supervisors and the attack programs inside one Slurm allocation using nothing but sbatch , srun and scancel . The one component that involves the site is the hardware root of trust: a Enclaweder attached to each machine, which an administrator makes readable to the user once, as for any USB security key. A deployment can start on software keys, as part of the evaluation in this paper does, and turn on 

requireDeviceKeys once the devices are in place. 

2.8 The operator’s monitor 

The monitor is the operator’s view of a swarm and the operator’s only way to act on it. It shows whether the swarm is running and under which rules, which nodes may run work, and whether the Enclaweder behind each node, and behind the operator’s own key, still vouches for it. It lets the operator evict a node, retire a coordinator, change the lease timing or publish a policy, each within fixed bounds. And it refuses to be used against the operator: a monitor whose page was tampered with, or whose key was used behind its back, evicts itself and says why. It runs on the operator’s computer as a loopback daemon that reaches the swarm over SSH as above, signs with the operator’s key (held by that computer’s Enclaweder, through Section 2.5), joins the chain as an observer (a role the admin approves, which can never hold a lease and never expires), and serves one web page in a fresh browser window without extensions, opened with a single-use token. The browser is not trusted: whoever controls it can read and change the page’s code. The page is therefore treated as a skill in the sense of the skills trust schema and its biconditional correctness criterion [33]: it ships with a manifest of every value it shows and every 16 action it may request, with bounds, and every action passes the skill gate. Two independent checks run continuously, and either one failing evicts the session, writes the reason to the tamper-evident audit log, and records the eviction on the chain under the session’s own identity: 1. The biconditional over the chain. The admin-approved operator actions that actually committed during the session must equal, as a multiset, the actions the skill gate audited as executed. An action on chain with no audit record means the operator’s key was used outside the monitor; an audit record with no action on chain means the record is wrong. 2. Page conformance. The page must be the one served, show exactly what the daemon sent, and have asked for exactly the actions the daemon received. The page also shows every Enclaweder in the swarm, from the chain rather than from the page. On the cluster side it counts the Enclaweders that hold the nodes’ keys and lists, for each node, its Enclaweder, the clean heartbeat its current lease was granted on, and every eviction with the reason its Enclaweder gave. On the operator’s side it counts and names the Enclaweders on the operator’s computer that hold the operator’s key, and says whether they still answer, since without them no action can be signed. Figure 2 shows the page against a live swarm. Actions outside the manifest’s bounds are refused before anything is signed. What the design cannot do is distinguish the operator from someone else at the operator’s own browser: an in-bounds action sent by a hijacked browser is executed and then detected, not prevented. Preventing it needs a per-action confirmation on the Enclaweder itself, outside the browser, which we leave to future work.

2.10 Model checking the finality step 

We specified one height of the protocol in TLA+ [25] ( spec/SwarmFinality.tla , about 230 lines) and checked it exhaustively with TLC, the TLA+ model checker [53]. The model has Tendermint’s propose, prevote and precommit rules with locking and validRound , the decision rule, and the swarm’s final step: a decided coordinator signs one final, and a block commits on a quorum of finals. Rounds can be entered at any time, which over-approximates every timeout schedule, so the safety results hold for any network timing. Faulty coordinators come in two strengths: equivocators 

may sign anything, including two votes for one slot; amnesic coordinators sign at most one vote per slot but ignore their locks. Either kind may sign finals for several blocks. As in Informal Systems’ accountability specification [35], faulty messages are fixed in the initial state: all of them for equivocators, one chosen per slot for amnesic coordinators. Correct coordinators act on “there exists a quorum”, so every adaptive attacker’s message set is one of the enumerated ones. Two further reductions are sound for safety: a correct coordinator may precommit nil at any point of its prevote step, and faulty coordinators’ nil votes are omitted, since a nil vote never counts toward a block. Three properties are checked: Agreement , no two correct coordinators commit different blocks; 

FinalAccountability , whenever two blocks both have a quorum of finals, at least 2 q − n coordinators signed finals for both and all of them are faulty; and VoteAccountability , the same question asked of Tendermint’s own votes: if correct coordinators decide differently, did someone sign two votes for one slot? Section 3.8 gives the results.

3.3 A cluster reached over SSH alone 

Experiment E4 runs the whole path of Sections 2.6 and 2.8 as an operator would. On the “operator’s computer”, swarm keygen creates the operator’s key; on the “cluster”, a two-coordinator swarm is created with that key as a second admin. The job finished with exit 0 and all 16 ranks leased; the new lease length was on chain and on the page; the monitor was not evicted, because the cluster’s admissions are not operator actions and the operator’s own action matched its audit; the whole session used four SSH sessions and none carried a forwarding option. Four observations. First, R2 shows that an MPI job survives a multi-second SIGSTOP of every rank and resumes correctly: MPICH’s collectives block while a peer is stopped and continue when it returns. A supervised job therefore degrades to a pause, not a crash, when the control plane is briefly unavailable. Second, R3 is the scenario the design is for: a tampered node is stopped in well under one heartbeat interval, and the whole job then stops, because MPI cannot continue without rank 5. A job that could continue with a tampered rank’s results would be the failure. Third, R10 and R11 put more Byzantine coordinators into the swarm than four can tolerate, and show the two ways that can go. Colluders that otherwise keep following the protocol are caught by their own finals and evicted, and the honest pair continues; in R10 coordinator 2 even co-signed the block that evicted it. Colluders that withhold their votes leave the honest pair short of a quorum, so the chain stops and every lease runs out. Neither produced a fork. R11 loses liveness, which no protocol can keep beyond its fault threshold, and it loses it in the safe direction. Fourth, withholding produces no evidence, so the colluders are not evicted, and the swarm waits for an operator.

3.8 Model checking 

Table 9 gives the results for two values and two rounds. The n = 3 row is beyond the nominal f = 0 of three coordinators, and agreement still holds, as the quorum arithmetic of Table 2 predicts. The violated row is the result we wanted. It asks plain Tendermint, without our finality step, whether a fork always leaves a culprit, and the answer must be no: that gap is why the finality step exists, and the model checker has to find the attack that exploits it before it can show the step closes it. TLC found it, the amnesia fork, in nine steps: in round 0, c1 proposes B, and c1 with the two faulty coordinators prevotes and precommits it, so 

c1 decides B; in round 1, a faulty coordinator proposes A, both faulty coordinators prevote and precommit A despite their lock, and c2 decides A. No coordinator signed two votes for one slot, so Tendermint’s votes convict no one. With the finality step, the same attack convicts its authors: in the same setting, the final step’s accountability holds over all 90 million states: a fork is possible, since there are more faulty coordinators than four tolerate, but it cannot happen without the faulty coordinators signing two finals each. We also ran n = 5 with two equivocators; with all faulty messages present from the start, a quorum forms there exactly when two correct coordinators agree, 29 as with n = 4 and one equivocator, and the two models turned out to be the same state machine, so that run adds no independent evidence and we do not count it. To make sure the passing rows are not vacuous, we mutated the model twice. With the quorum one smaller, TLC finds an agreement violation; with correct coordinators allowed to sign a final for a block they did not decide, it finds a FinalAccountability violation. The model covers a single height and two rounds; reconfiguration between heights is argued in Section 2.3.5 and tested, not model-checked. 

# 4 Discussion 

The results answer the four issues of Section 1.5. (I1) The gate decided every launch of agents driven by a real model from policy alone: it denied all 24 launches that planted instructions ordered and none of the 108 legitimate ones (Section 3.6). (I2) No single host, and not even two colluding coordinators of four, could free a job: insiders with genuine keys were evicted on their own signatures or stopped the chain, no run forked (Section 3.5), and the model checker finds the same accountability in every state it explores (Section 3.8). (I3) Control outlasted submission: a lost quorum paused every rank, and every agent together with its job, and a device reported removed (a file standing in for it) killed its rank in 54 ms and an agent’s LAMMPS job in 58 ms (Sections 3.5 and 3.6). On the real Enclaweder, its physical removal stopped every rank it backed, and, since a removed device cannot sign its own report, the chain evicted every one of them as expired by its own count of blocks (Section 3.7). (I4) The runtime ran under the user’s own account, was operated over SSH alone (Section 3.3), and left the compute loop unchanged on the CPU and on the GPU, at about 3 s of start-up per job (Section 3.1). What it does not settle is whether a launch within policy computes the right thing: every wrong result the agents reported came from an allowed launch, which is why Section 2.1 sets out the checks a site adds for consequential computation.

Where existing systems stop. The surveyed systems fall into five groups, and each stops short of a running job. Agent frameworks with the operator’s scheduler access (Academy, URSA, LAMMPS-Agents, the LLNL servers and descriptive execution, RCAC MCP, and research codes such as MDCrow and ChemGraph) bound the agent’s behavior only by the model’s own judgment. Submission gates (Diamond Agent, LARA-HPC, dtu-hpc-mcp, Globus Compute, Flux job policy, S3M) check a launch and stop there: once the scheduler accepts the job, nothing they run watches it, and the host that runs the gate is trusted. General agent policy engines (the Agent Governance Toolkit, Keycard) are deterministic but know no launcher, scheduler or rank. Guardrails that ask a second model to judge the first are not deterministic, and the injection that hijacked the first model can argue with the second (Section 2.2). Fault-tolerant ledgers (TrustMesh, BAASH) govern scheduling or storage, not agents or running ranks. Among the systems surveyed, Enclawed is the only one that supervises every running rank (C5) and the only one that combines a deterministic gate, a BFT runtime chain, device-held node keys and per-rank supervision, and it needs no root privileges, kernel changes or scheduler plugins (Section 2.7). HASB makes the difference testable: a system without C5 has no mechanism for R2, R3, R9, R11, A2 or A3; one without C2 none for A1; and one without C3 none for R1, R2, R4–R8, R10 or R11. 

Agents on HPC (C1). Academy [23] provides middleware for stateful agents across federated facilities; Diamond Agent [50] drives several supercomputers through Globus Compute with typed skills; LLNL’s descriptive execution and dispatch papers [46, 47] and MCP servers [9, 45] translate requests into Slurm and Flux jobs; URSA [18], LAMMPS-Agents [3] and El Agente [54] are domain agents that submit simulation jobs, and MDCrow [5] and ChemGraph [37] set up and run simulations through their own tools; Parsl with LangChain [29] and VibeCodeHPC [21] dispatch agent work to clusters. All of these are complementary: they are what an operator would run through the runtime described here, and the launch gate’s parsers were written so that their existing sbatch ,

srun , mpirun and flux lines work unchanged when they are within policy. 

Deterministic gates (C2). Diamond Agent’s placement checks and LARA-HPC’s template-and-dry-run discipline are the closest prior art, and dtu-hpc-mcp is the closest single-site tool server. Each sits outside the agent and inside one host; none reaches into a running job, and in Diamond Agent the model still chooses resources within the ceilings. Native scheduler policy (Slurm job_submit.lua , Flux policy.limits and signed jobspecs [15]) and Globus Compute’s function allow-list [16] are production primitives our gate is designed to sit in front of, not replace: they see the submission, not what the agent did to produce it. The Microsoft Agent Governance 33 Toolkit [34, 43] is a deterministic, fail-closed policy engine for agents in general, without HPC semantics, consensus or hardware keys. 

Consensus and hardware (C3, C4). BFT among LLM agents has meant consensus over answers 

(e.g. [55]), not over runtime control state; the “honest quorum” argument [22] that agreement does not imply semantic validity is one we agree with, which is why the chain here records only facts that are verifiable by signature. TrustMesh [40] uses PBFT to govern scheduling on IoT edges and BAASH [2] runs a lightweight fault-tolerant chain on HPC aimed at resilience, not accountability; neither involves agents or launch control. Hardware-bound agent identity is appearing in products [27] and drafts, with per-request signing but, in every system we surveyed, without device-signed liveness or eviction on removal. We found no system in which MPI ranks themselves consult a runtime (C5). 

The problem statement. The “hijacked authorized agent” position paper [26] sets out the gap this work fills and proposes a benchmark rather than a defense; National Institute of Standards and Technology (NIST) Special Publication (SP) 800-223 [19] gives the zone model that coordinators and nodes map onto; the ORNL S3M mesh [44] shows a facility moving toward token-scoped, audited agent access at the API layer, which is the layer below ours. 

4.2 Bounds of validity 

Goals G1–G5 hold under the threat model of Section 2.1. At its edges they hold as follows. • More than f Byzantine coordinators. Safety becomes accountability: a fork cannot occur without naming at least 2 q − n culprits, each pair of whose finals is eviction evidence on its own; in R10 both colluders were evicted and no fork occurred. Colluders that only withhold votes leave the chain without a quorum, so it stops and every lease lapses (R11); the swarm fails closed and waits for an operator. • The job’s own account, or root, on a compute node. The supervisor runs under the job’s account (Section 2.7), so either can stop it. The rank then runs unleased, which the chain shows and any decision-socket check reports as a failure, but unpaused; a stopped process signs no evidence to evict it on, so its node leaves by expiry once it has renewed nothing for the epoch’s 

expiryBlocks . A site that wants the supervisor out of the job’s reach runs it under a separate account, which takes the privileges the default deployment avoids. As deployed, supervision contains a hijacked agent, a lapsed lease and a tampered device. • A compromised coordinator host. The sign guard is a file on the host. A host that rolls it back to make its key double-sign produces exactly the evidence that evicts it; a guard enforced inside the Enclaweder removes even that window. • Other processes of the same user on a machine with a device. The device’s owner serves any process that can open its socket, which is any process of the user, and such a process could open the device itself. So this is host compromise, the case the device is there to make visible, not preventable: the key never leaves the device, every request it signs is in the journal before it is signed, and the device signs the journal as it grows, so what was signed on its behalf cannot later be hidden. • A removed device. Its ranks stop within about the owner’s check interval (the first 0.3–1.2 s after removal in E7’s runs); its eviction takes the epoch’s expiryBlocks , during which the node is a member that holds no lease and can authorize nothing. 34 • No device at all. Everything runs on software keys, and Enclawed says so wherever they are used: keys on the host can be used by whoever compromises it. That is far more secure than no runtime at all, and short of security that holds against a compromised host, which needs the Enclaweder. • A launch within policy that computes or reports the wrong thing. Outside G1–G5. Section 2.1 sets out which part of a result’s integrity the runtime protects and what a site adds for consequential computation. • Commands the parser does not model. The gate parses and never executes, so such a command is refused, never admitted; the cost is a false refusal, measurable in advance with 

enforce: false .

4.3 Limitations of the testing environment 

• One machine, one device. All measurements run on one host, coordinators and ranks on loopback TCP. The red team and E7 run on one Enclaweder attached through the virtual machine’s USB passthrough, every rank’s key the device’s, and so does E1; E3 and E6 ran on software keys, before it was attached. Where one rank’s device is removed and the others keep theirs (R3, A3), a file stands in for that rank’s device. Machines with several devices are exercised only with software stand-ins for the devices beyond the first. In this testbed, detaching the device through the passthrough while it was in use left it unresponsive until it was physically reconnected; it kept its key and its certificate. Multi-node runs on a real interconnect with a device on every node are the next experiment. • One device’s signing rate. Through this testbed’s passthrough the Enclaweder makes about 20 signatures a second (45–50 ms each), one at a time. In an attempt to run E6 on it, the 16 agents’ ranks and their LAMMPS ranks, about 28 nodes, renewed their leases at one epoch change. The scheduler refused the requests that outwaited its one-second deadline, and eight ranks paused for about a second. This is the capacity of one device, not of the design: on a cluster each node carries its own device, which serves only that node’s ranks, and a machine with more ranks than one device serves carries more devices, bound as one principal. • One model on one GPU. The agents of Section 3.6 run an 8-billion-parameter model with 4-bit weights, 16 of them on one GPU. The gate’s decisions, the pauses and the kills do not depend on the model; the share of agents that measure the right pressure depends on the model and on the prompt (Table 8). The injected and hijacked instructions are fixed text; what the model did with them is its own. • Scripted attackers. The attack programs connect over the network, sign with real keys, kill real processes and edit real files, each along a fixed script. The R10 colluders otherwise follow the protocol, which is what gets them evicted; R11 covers colluders that do not. • Network conditions. Liveness is exercised after crashes, restarts, promotions and evicted insiders on loopback, not under adversarial network delay; the protocol is live under partial synchrony [13]. • MPI stack. SIGSTOP on every rank is safe for MPICH collectives in these runs. Stacks whose progress engine times out a stopped peer run with --on-lease-loss kill and rely on checkpoints. 35 5 Conclusion 

An LLM agent can therefore drive MPI and batch-scheduled jobs under guarantees that rest on no single host, process or model judgment, and Enclawed, until now a runtime for a single user, governs distributed parallel jobs and swarms of agents. The launch gate decides from policy and the command text what may start, so a hijacked agent cannot start what the policy forbids. The swarm chain decides which nodes may act and evicts on evidence, so a compromised host or coordinator can at most stop the swarm, never free a job. The supervisor around every rank turns a lost lease into a pause and a tampered device into a kill, so control lasts as long as the job does, and a node whose device is gone leaves the swarm by the chain’s own count. One owner per machine shares its Enclaweder with every process on it, under a scheduler and a journal the device signs. Under live attack, on the real device and with agents on a real model, every test ended in this secure outcome, with the compute loop unchanged and about 3 s of start-up per job, and no surveyed system offers the combination. What remains open is scale: runs across many nodes, with a device on every node, are the next step.
