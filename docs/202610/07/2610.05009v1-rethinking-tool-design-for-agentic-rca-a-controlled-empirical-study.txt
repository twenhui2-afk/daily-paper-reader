Large language model (LLM) agents are increasingly explored for root cause analysis (RCA) in microservice systems, yet empirical guidance on how to design and combine their tools remains limited. We conduct a controlled empirical study of tool abstraction and composition across models and microservice environments. We implement 24 structured tools for metric access (L1), evidence analysis (L2), and diagnosis (L3), alongside a Python-based reference setting (L0). Using 375 failure cases from three microservice systems, we evaluate eight configurations with Qwen3.7-Plus and compare four Qwen models on a shared subset of four configurations. Our results show that tool configurations affect root cause localization and failure type identification differently. With Qwen3.7-Plus, L3 achieves 82.8% top-1 localization accuracy compared with 85.4% for L0, while requiring less than half the time per case. Adding tool levels can improve type identification while reducing localization accuracy. Trajectory analysis reveals cases in which agents override correct diagnostic recommendations after consulting additional evidence. Model choice also changes tool benefits: adding L3 to L1+L2 improves diagnosis for three models but hurts Qwen3-8B, which rarely invokes L3. Tool configuration rankings further change across microservice systems. These findings provide an empirical foundation for designing and using RCA tools, guiding tool selection and composition according to the model, diagnostic objective, and target system.

# 1 Introduction 

Large language model (LLM) agents are rapidly emerging as autonomous problem solvers for complex real world tasks (Yao et al., 2022; Schick et al., 2023). Root cause analysis (RCA) is a particularly promising application in AIOps, where identifying the entities and failure types behind system incidents requires iterative evidence collection and reasoning for timely mitigation and recovery (Chen et al., 2024; Roy et al., 2024; Shetty et al., 2024). Recent agentic arXiv:2610.05009v1 [cs.SE] 4 Oct 2026 RCA systems have explored multi-agent collaboration (Zhang et al., 2024; Sun et al., 2025; Luo et al., 2025), causal and structured reasoning (Jiang et al., 2026; Xie et al., 2026), SOP guided diagnosis (Pei et al., 2025; Zhao et al., 2026; Gao et al., 2026), explicit reasoning state management (Luo et al., 2026a), and memory augmented diagnosis (Sun et al., 2026; Zhang et al., 2026), substantially advancing automated RCA. Yet, across these efforts, one fundamental design choice remains largely unexplored: what tools should an RCA agent be given to extract useful information from massive metric streams? This question is critical as metric data in microservice systems is massive and noisy (Zhang et al., 2025), while only a small fraction is relevant to the root cause. Existing systems broadly address this challenge in two ways: some rely on expert designed preprocessing to distill raw metrics into diagnostic signals (Sun et al., 2025; Luo et al., 2025; Jiang et al., 2026), while others allow agents to actively acquire and analyze metrics using a predefined toolset (Pei et al., 2025; Luo et al., 2026a; Sun et al., 2026). Despite these efforts, none of these studies has systematically examined what analytical capabilities RCA tools should provide or how those capabilities should be combined. Through an analysis of how existing agentic RCA systems process metrics, we find that their tools already span different degrees of analytical responsibility. We capture this hierarchy with three tool levels: L1 tools retrieve raw metric data, L2 tools transform the data into diagnostic evidence through operations like anomaly detection or causal analysis, and L3 tools return diagnostic results. OpsAgent’s metric processor provides a concrete example of this progression: it retrieves target metric series within a specified time window (L1), applies the 3-sigma rule and temporal shape classification to detect anomalies (L2), and aggregates deviation scores to produce top-5 service instance and metric candidates corresponding to root cause entities and failure types (L3) (Luo et al., 2025). As the abstraction level increases, tools encode more domain knowledge and undertake a larger portion of the RCA process, which intuitively suggests that higher level tools should provide stronger support for diagnosis. However, does this intuition hold in practice? 

Answering this question requires more than comparing tool configurations in a single setting, because tool effectiveness may depend on both the agent that uses the tool and the environment in which diagnosis is performed. Models differ in their abilities to analyze data and use tools (Lu et al., 2025; Patil et al., 2025), while microservice systems differ substantially in scale, metric space, dependency structure, and failure propagation (Pham et al., 2025; Liang et al., 2026). We therefore study tool design together with these two contextual factors, conducting controlled experiments across tool abstraction and composition , model capability , and microservice system complexity . Specifically, we ask three research questions: 

RQ1: How do tool abstraction and composition affect agentic RCA? We examine whether higher-level tools and richer tool combinations consistently improve diagnostic effectiveness and efficiency. 

RQ2: Does model capability affect the benefits of different tool levels? We examine how the performance gains from different tool levels vary across models with different capabilities. 

RQ3: Does system complexity affect the effectiveness of different tool configurations? We study whether diagnostic environments that differ in system scale and complexity favor different tool levels and combinations. By answering these questions, this paper makes the following contributions: 

• We derive an abstraction with three levels for structured RCA tools from representative agentic RCA systems and implement 24 structured tools spanning metric access, evidence analysis, and diagnostic methods, establishing a controlled experimental space for studying tool abstraction and composition. 

• We conduct a controlled empirical study across eight tool configurations, four Qwen models spanning distinct capability levels, and three RCAEval environments with different system architectures and complexity profiles, systematically examining the effects of tool abstraction and composition and their interactions with model capability and system complexity. 

• We reveal that tool composition can have opposing effects on root cause localization and failure type identification, and that tool benefits depend on model capability and diagnostic environment. Through trajectory analysis, we identify failures in tool use and conflicts in evidence interpretation that help explain these differences. Together, these findings provide an empirical foundation for the design and use of tools in agentic RCA. 

# 2 Background and Motivation 

Metric Based Agentic RCA. In microservice systems, metric based agentic RCA is complicated by massive and noisy metric spaces along with failure propagation across dependent components, which can separate observed symptoms 2from their underlying causes (Zhang et al., 2025; Fang et al., 2026). For example, a frontend error may stem from 

memory exhaustion in an underlying service or node, illustrating how failure propagation can obscure the true source of an incident and require further evidence across components. Agentic RCA therefore treats diagnosis as an iterative investigation in which the agent forms hypotheses from available evidence, determines what additional information is needed, acquires and analyzes relevant metrics, then refines its diagnosis until it identifies the root cause entity and failure type (Pei et al., 2025; Luo et al., 2026a; Sun et al., 2026). Since the complete metric space can easily exceed an LLM’s context window, the system must decide “what evidence to expose to the agent” and “how much analysis to delegate to its tools” .

Challenge 1: Fixed Preprocessing Creates an Evidence Bottleneck. Fixed preprocessing uses expert knowledge and statistical procedures to filter, aggregate, and rank metrics into compact diagnostic signals (Sun et al., 2025; Luo et al., 2025; Jiang et al., 2026). Although this reduces the search burden and provides salient evidence for diagnosis, it also fixes the evidence boundary before the root cause is known. If a signal needed to distinguish the true cause is excluded, subsequent reasoning cannot recover it, turning an efficiency mechanism into a potential evidence bottleneck. 

Challenge 2: Tool Abstraction Creates an Analytical Tradeoff. Active metric access relaxes this fixed boundary by allowing agents to retrieve additional metrics as the diagnostic process unfolds (Pei et al., 2025; Luo et al., 2026a; Sun et al., 2026). However, its effectiveness depends on the abstraction of the tools available to the agent. Basic tools mainly expose metric data, leaving anomaly detection and evidence association to the agent, whereas higher level tools perform more of this analysis and return processed diagnostic information. The former preserves greater analytical flexibility but places a heavier burden on the agent, while the latter reduces this burden but increases reliance on embedded analytical methods and may obscure intermediate evidence needed for verification. 

Challenge 3: Lack of Systematic Empirical Guidance. Existing agentic RCA methods typically evaluate a predefined toolset as part of a complete diagnostic system (Luo et al., 2025; Pei et al., 2025; Luo et al., 2026a; Sun et al., 2026). Because tool design is coupled with preprocessing, prompts, agent workflows, and model choices, these evaluations cannot isolate its effect on diagnostic performance. They also provide limited evidence about whether the same configuration remains effective across models with different capabilities or microservice systems with different scale and complexity (Lu et al., 2025; Patil et al., 2025; Pham et al., 2025; Liang et al., 2026). 

Our Study. We address these challenges through a controlled empirical study centered on RCA tool design. We construct tools with three different abstraction levels over the same underlying metric data and evaluate both individual levels and their combinations under a consistent agent setting. We further vary model capability and microservice system complexity to examine how the effectiveness of different tool configurations changes across diagnostic conditions. By separating tool design from other components of the agentic system, our study provides an empirical basis for understanding what tools should be provided to RCA agents and under what conditions. 

# 3 Study Design 

This section presents the design of our empirical study on tool design for agentic RCA. First, we describe the evaluation workflow used for each failure case. Next, we introduce the four-level RCA tool spectrum, including the concrete tool implementations and eight experimental configurations. We then describe the four Qwen models spanning different capability levels and the three RCAEval diagnostic environments with different system architectures and complexity profiles. Finally, we define the evaluation metrics for diagnostic effectiveness, reliability and tool use, and efficiency. ## 3.1 Evaluation Workflow 

Each run evaluates a model on a failure case under a specified tool configuration. We use a ReAct-style agent harness with a shared task prompt and configuration-specific interface instructions. The task prompt asks the agent to produce a final diagnosis containing ranked root cause candidates and a predicted failure type. Under common limits on interaction steps and per-response output length, the agent iteratively reasons about the case, invokes an available tool, and uses the returned observation to guide its next action. A run ends when the agent submits a final diagnosis or reaches the interaction limit. ## 3.2 RCA Tool Space and Configurations 

Tool abstraction. By analyzing the tool designs of representative agentic RCA systems ( e.g., OpsAgent (Luo et al., 2025), Flow-of-Action (Pei et al., 2025)), we derive a three-level abstraction of RCA tools. We distinguish these levels by their analytical responsibilities and outputs. L1 exposes metric observations, basic summaries, and system metadata; L2 analyzes metrics and returns results such as anomaly scores, temporal features, and metric relationships. L3 performs diagnosis-oriented analyses that produce root cause candidates or explanations. Inspired by OpenRCA (Xu et al., 2025), we further introduce L0 as a setting with no predefined RCA tools, where the agent is provided only with the same incident data and a general Python execution interface and must construct the entire analysis process on its own. L0 serves as a reference for analysis implemented by the agent, while L1–L3 represent increasing abstraction among predefined RCA tools. Together, they define the tool settings evaluated in this study. 

Tool implementation. We implement a general Python execution interface for L0 and 24 structured RCA tools across L1–L3. Each tool corresponds to a callable interface, which may support multiple analytical methods. 

L0: Analysis implemented by the agent Design. A general Python interface exposes the case metrics, incident context, and service topology without predefined RCA procedures. The agent writes and executes code to select and process data, compute statistics, and implement further analyses. 

Output. The interface returns the results produced by the agent’s programs as observations. 

Agent role. The agent determines both how to implement the analysis and how to interpret its results. 4L1: Access to metric observations (6 tools) Design. Six interfaces provide metric discovery and retrieval, batch queries, simple aggregation, metric ownership resolution, and local topology inspection. Metric queries allow the agent to specify a service, metric, and time window. Batch queries summarize several metrics in one call, while aggregation supports mean, maximum, minimum, sum, and percentiles. 

Output. The interfaces return time series samples, summary statistics, metric ownership information, and local service dependencies. They do not assign anomaly scores or rank root cause candidates. 

Agent role. The agent chooses what to inspect and interprets the observations to identify anomalies and reason about root causes. 

L2: Evidence analysis (12 tools) Design. Twelve interfaces cover time series processing, anomaly and change point detection, feature extraction, anomalous metric filtering, and relationship analysis. Anomaly detection supports 3-sigma, IQR, MAD, ESD, and SPOT (Siffer et al., 2017). Change point detection includes CUSUM, PELT (Killick et al., 2012), binary segmentation, and Page–Hinkley. The agent specifies analysis targets and time windows and selects supported methods and parameters. 

Output. Results include anomaly scores, change points, candidate metrics, temporal features, and evidence graphs describing relationships among metrics. 

Agent role. The agent relates these findings across services and determines their diagnostic significance. An anomaly ranking identifies unusual behavior; translating that evidence into root cause candidates remains the agent’s responsibility. 

L3: Diagnostic methods (6 tools) Design: Candidate generation. Propagation analysis searches for paths from specified symptom metrics. Graph ranking supports PageRank (Brin and Page, 1998), personalized PageRank (Jeh and Widom, 2003), and random walk with restart (Tong et al., 2006). The classic RCA interface supports MonitorRank (Kim et al., 2013), CloudRanger (Wang et al., 2018), MicroRCA (Wu et al., 2020), Microscope (Lin et al., 2018), MicroCause (Meng et al., 2020), and MicroHECL (Liu et al., 2021). It internally filters candidate metrics, prepares their time series, and supplies the selected method with case context and topology. This interface encapsulates data preparation and diagnostic computation in a single agent action. 

Design: Evidence integration. The fusion interface combines anomaly scores, classic RCA rankings, graph scores, and topology information, and conditionally incorporates change point timing. It associates these contributions with candidate services and metrics and combines them using predefined scoring rules. Evidence chain and explanation interfaces gather supporting observations and organize them into diagnostic explanations. 

Output. Depending on the interface, the tools return ranked root cause candidates with scores, propagation paths, or diagnostic explanations with supporting evidence. 

Agent role. The agent decides whether to adopt or revise the diagnostic recommendations and produces the final ranked candidate list and predicted failure type. Combining L3 with lower-level interfaces allows us to examine whether additional observations and analyses help the agent assess or supplement these recommendations. L2 and L3 tools access case data and perform their required internal analyses without prior agent calls to lower-level interfaces. A configuration controls which interfaces the agent can directly invoke, while the underlying data and tool implementations remain unchanged. Combining levels therefore provides additional analytical entry points without imposing a fixed invocation order. 

Configuration design. We instantiate eight configurations, shown in Table 1, to isolate the effects of metric access, evidence analysis, diagnostic methods, and their combinations. L0 captures analysis without predefined RCA tools, while the standalone L1, L2, and L3 configurations evaluate metric access, evidence analysis, and diagnostic methods, respectively. Because introducing any structured RCA tool changes the defining condition of L0, we evaluate L0 independently and construct compositions only among L1–L3. The three pairwise combinations examine complementarity between tool levels, while L1+L2+L3 assesses the effect of exposing the full structured toolset. ## 3.3 Model Selection Across Capability Levels 

To examine whether the benefits of different tool levels vary with model capability, we evaluate four Qwen models spanning a broad range of model scale and capability. We select models from the same Qwen lineage and access them through the same provider, reducing variation introduced by unrelated model families and serving interfaces. The first three models are drawn from the Qwen3 family (Yang et al., 2025), while Qwen3.7-Plus serves as a stronger proprietary model representing the highest capability level in our study. Specifically, we evaluate: 1. Qwen3-8B , the smallest dense model in our study; 2. Qwen3-32B , a larger dense model with 32 billion parameters; 3. Qwen3-235B-A22B , a mixture of experts model with 235 billion total parameters and 22 billion activated parameters; 4. Qwen3.7-Plus , which represents the highest capability setting in our study. We evaluate Qwen3.7-Plus under all eight tool configurations to provide the complete comparison of tool abstraction and composition for RQ1 and the cross-system analysis for RQ3. For RQ2, we compare all four models under L0, L1, L1+L2, and L1+L2+L3, which span the RCA tool spectrum from no structured RCA tools to the full structured toolset. This progression allows us to compare how models with different capabilities benefit as tools undertake a larger portion of the RCA process. The remaining four configurations are evaluated only with Qwen3.7-Plus for the more detailed analyses in RQ1 and RQ3. 

## 3.4 Datasets and Diagnostic Environments 

We evaluate all 375 failure cases in the RE1 suite of RCAEval (Pham et al., 2025), an open source benchmark for RCA in microservice systems. RE1 provides 125 cases for each of Online Boutique (OB), Sock Shop (SS), and Train Ticket (TT). All three environments cover the same five failure types: CPU, memory, disk, network delay, and packet loss. Each case includes ground truth labels for the root cause service and injected failure type. The shared failure taxonomy and equal case counts support comparisons of tool and model effects across the three systems. Although the three environments follow the same task protocol, their underlying systems differ substantially in service scale, communication structure, and metric dimensionality, as summarized in Table 2. Rather than reducing system complexity to a single ordered score, we characterize each environment through these observable properties. # 4 Empirical Results

We first examine how tool abstraction and composition affect RCA under a fixed strong model (RQ1), and then study how these effects change with model capability (RQ2) and system complexity (RQ3). Within each RQ, we also analyze agent trajectories to explain the observed differences, and say that the agent considers a service when the service appears in its thoughts or tool inputs. We use AC@1 and TA as the primary metrics for root cause localization and failure type identification, and report AC@3, Avg@5, and efficiency metrics as complementary evidence.

Why do combinations not add up for localization? We compare the four configurations with L3 and call the top candidate of the first L3 ranking in a trajectory its L3 candidate . Additional levels change how the investigation starts but not what L3 returns. With L2+L3, the agent begins with anomaly filtering in 91% of trajectories rather than with the L3 ranking. Yet on the same case, L3 and L2+L3 return the same candidate in 99.9% of trajectory pairs that obtain one, as do L1+L3 and L1+L2+L3. This candidate is correct in more than 80% of trajectories in every configuration (Figure 5). The accuracy differences therefore arise after L3 returns, when the agent decides whether to keep the candidate. We call a trajectory a correction when its L3 candidate is wrong but its final diagnosis is correct, and an override 

in the opposite case. Overrides outnumber corrections in every configuration, so adopting the L3 candidate directly would have been more accurate. Additional levels shift this balance in opposite directions. With L1+L3, the agent calls 9L1 after the L3 ranking in 98.5% of trajectories, mostly to inspect the ranked candidates. This verification doubles corrections from 2.7% to 5.3% of trajectories, while overrides rise only from 4.2% to 5.8%. L2 instead supplies competing evidence, such as the metrics that its candidate filtering ranks as most anomalous, and the agent sometimes abandons the L3 candidate for the entity this evidence points to. With L2+L3, overrides more than double to 9.3%, while corrections rise only to 3.8%; adding L2 to L1+L3 likewise raises overrides. 

Finding 3. Additional levels change whether the agent keeps the L3 candidate rather than the candidate itself: L1 helps the agent verify it, whereas L2 competes with it and more often leads the agent away from a correct one. 

Why does type identification remain difficult? The agent tends to name a fault after its most prominent symptom, and failure propagation makes CPU and latency anomalies prominent regardless of the injected fault. Under L0, Qwen3.7-Plus identifies memory faults in only 28.9% of trajectories and disk faults in none, labeling most of both as CPU faults; with L3 alone, disk faults are still identified in only 4.0%. The full toolset raises TA to 77.8% for memory and 29.8% for disk faults, but identifies delay faults less often than L0 (50.2% vs. 84.4%). Packet loss, mostly labeled as delay or CPU faults, is identified in at most 0.9% of trajectories in any of these configurations. Type identification is thus not a by-product of localization: under L0, 46.2% of all trajectories locate the correct service but name the wrong failure type. 

Finding 4. Agents tend to name a fault after its most prominent symptom and thus mislabel memory and disk faults as CPU faults. L1+L2+L3 reduces but does not remove this error, and packet loss is almost never identified. 

Answer to RQ1. Higher abstraction improves both localization and type identification, whereas combining levels rarely improves localization and, beyond L3, improves type identification only slightly. Because additional levels affect whether the agent keeps the L3 candidate rather than the candidate itself, L3 alone is the most cost-effective choice for localization.

# 5 Discussion 

## 5.1 Failure Analysis 

RQ1–RQ3 identify the tool configurations that work best; we now ask why even the best of them fail. With its most accurate structured toolset, L1+L3, Qwen3.7-Plus still selects a wrong root cause in 16.4% of cases, and its TA never exceeds 49.0%. We examine its failed trajectories under the configurations with L2 or L3. 

The agent finds the root cause but does not keep it. Qwen3.7-Plus completes every case, considers the true root cause in at least 96% of trajectories, and receives a correct top L3 candidate in more than 80% of the trajectories with an L3 ranking. Yet the agent had considered the true root cause in 84–95% of trajectories with incorrect localizations, 14 indicating that localization failures arise mainly during the final decision rather than the search. Two patterns recur. The agent mistakes a service affected by the fault for its source, which is how L2 leads it away from correct L3 candidates on Sock Shop and Train Ticket (RQ1, RQ3). In a Train Ticket case with a delay fault in ts-auth-service , L3 ranked the correct service first, but candidate filtering ranked a memory metric of the payment service highest; finding no CPU or memory anomaly in the auth service, the agent treated its latency as a propagated symptom and blamed the payment service. The agent also uses tools to confirm rather than test a hypothesis: the evidence chain interface gathers observations that support a given candidate, and when that candidate is wrong, the agent keeps it in 83% of such calls. 

The agent names the fault after its most prominent symptom. Type identification fails more often than localization: when Qwen3.7-Plus locates the root cause, it names the failure type correctly in only 55.7% of such trajectories under L1+L2+L3 and 45.9% under L0. The agent infers the failure type from anomalous metrics highlighted in the tool outputs. Since failure propagation makes CPU and latency anomalies prominent whatever the injected fault, these metrics point to the symptom rather than the fault: even with L3, disk faults are identified in only 4.0% of trajectories, and packet loss is almost never identified (RQ1). More evidence shifts these errors rather than removing them, as the full toolset identifies memory and disk faults more often but delay faults less often than L0 (50.2% vs. 84.4%). 

Both failures call for tools that discriminate between explanations. In both cases, the agent must choose between explanations that the evidence fits equally well: the source of a fault versus the services it propagates to, and one failure type versus another with the same symptoms. Tools that rank evidence by how anomalous it is leave this choice unresolved, consistent with the small gains from adding levels beyond L3 (RQ1). For capable models, tools that seek counter-evidence or rank evidence by how well it separates failure types are thus more promising than tools that add analysis. Weaker models fail earlier: they leave more cases unfinished (Table 4) and, under L0, never consider the root cause in 41–51% of trajectories. They benefit first from a small and robust tool interface. 

## 5.2 Threats to Validity 

Internal validity. Our implemented toolset covers representative RCA capabilities across abstraction levels, and each function was unit-tested to verify its intended behavior. While these tools support the comparisons in our study, they do not cover the full range of RCA tools within each abstraction level. We also compare tool abstraction levels and their combinations within a common agent harness, allowing the agent to select individual interfaces during diagnosis. The results therefore characterize the overall effects of the evaluated tool configurations, while broader tool coverage and finer-grained attribution to specific interfaces within each level remain directions for further investigation. 

External validity. We evaluate all 375 RE1 cases across three microservice systems and five injected failure types, providing coverage across different benchmark environments. This coverage supports comparisons within the benchmark, but production incidents and diagnosis incorporating logs and traces remain outside our experimental scope. In addition, our model comparison covers four models from the Qwen lineage, allowing us to examine capability differences within a common family. However, the applicability of these findings beyond the Qwen family has not yet been assessed. Extending this comparison to other model families therefore remains a direction for future study. 

# 6 Related Work 

Agentic RCA for microservice systems. Agentic RCA systems adopt different strategies for providing analytical support and organizing tool use. Preprocessing-based approaches encapsulate operations such as telemetry filtering, anomaly detection, and candidate scoring in predefined pipelines, allowing agents to reason over the resulting evidence (Luo et al., 2025; Sun et al., 2025; Tang et al., 2025). Code-based approaches provide a general execution interface through which agents implement data retrieval and analysis, as exemplified by OpenRCA’s RCA-agent and reflected in our L0 setting (Xu et al., 2025). Workflow-guided approaches use SOPs and structured operational knowledge to organize tool invocation and code generation (Pei et al., 2025; Gao et al., 2026). Reasoning-oriented approaches employ agent collaboration, search, explicit states, or memory to guide evidence acquisition and the interpretation of tool results (Zhang et al., 2024; Naakka et al., 2026; Luo et al., 2026a; Zhang et al., 2026; Sun et al., 2026; Luo et al., 2026b). However, these studies primarily evaluate tool support within specific diagnostic frameworks, providing limited guidance on how tool abstraction and composition affect diagnosis. 

Empirical studies of RCA and tool use. RCA benchmarks provide the experimental basis for comparing diagnostic methods across microservice systems, telemetry sources, and fault propagation scenarios (Pham et al., 2025; Xu et al., 15 2025; Fang et al., 2026). Beyond RCA, tool-use benchmarks assess whether models can retrieve appropriate tools, invoke APIs correctly, and complete multi-step interactions (Li et al., 2023; Qin et al., 2024; Lu et al., 2025; Patil et al., 2025). Controlled studies address tool design more directly, comparing interface organization under similar capabilities in coding agents and examining tool complexity and composition in web agents (Xu et al., 2026; Lou et al., 2026). Extending these evaluations to the division of analytical work in RCA, our study compares the diagnostic value of tools that provide observations, analytical evidence, or root cause recommendations, individually and in combination. 

# 7 Conclusion 

We conducted a controlled empirical study of tool abstraction and composition for agentic RCA across different models and microservice systems. Our results show that tool configurations affect root cause localization and failure type identification differently. With the strongest evaluated model, L3 diagnostic tools offer a favorable balance between localization accuracy and cost. Adding tool levels improves overall failure type identification, but can reduce localization accuracy. These benefits also depend on the model: adding L3 to L1+L2 improves localization for three of the four models, but reduces it for the weakest model. Even with the same model, the relative performance of tool configurations changes across microservice systems. Together, these findings provide an empirical foundation for designing and using RCA tools, guiding practitioners to select tool abstraction and composition according to the diagnostic objective, model capability, and target system. 16 References
