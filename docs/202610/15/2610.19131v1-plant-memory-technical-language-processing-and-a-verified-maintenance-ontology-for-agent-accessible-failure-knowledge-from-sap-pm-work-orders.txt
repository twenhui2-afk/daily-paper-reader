# Plant Memory: Technical Language Processing and a Verified Maintenance Ontology for Agent-Accessible Failure Knowledge from SAP PM Work Orders 

Akash Raj

Abstract 

Maintenance work orders are the largest written record of how industrial equipment fails, yet in most plants they are close to unusable for analysis. Short texts are abbreviated and misspelt, asset identity is buried in free text, work-type labels contradict the work described, and the fields that matter most for reliability (symptom, root cause, action taken) are usually empty. As a result, diagnostic knowledge stays with senior technicians and leaves when they do. We present Plant Memory , a system that applies technical language processing (TLP) to SAP Plant Maintenance (PM) exports and builds an ISO 14224-aligned maintenance ontology in which every extracted statement is a reified fact carrying a confidence score, the evidence it was read from, and a verification state. Extraction is rule-first, with an optional large language model (LLM) acting as a second reader whose disagreements raise a fact’s review priority rather than overwrite it. Technicians verify facts through a review queue, answer targeted knowledge-gap questions where failures repeat without a recorded cause, and approve or reject ontology drift proposals when new terms appear. The resulting graph is served to people through a web application and to AI agents through a Model Context Protocol (MCP) server, so both query the same verified knowledge and every answer cites the work orders behind it. On a synthetic 12-month export of 400 work orders from a parboiled-rice plant, rule-based extraction reaches 96.2% component accuracy, 88.9% failure-mode accuracy and 100% root-cause precision at 62% coverage; on 28 diagnostic questions, ranked root causes from the ontology are correct at top-1 in 82.1% of cases against 53.6% for the raw SAP root-cause column. We also report that an LLM used as an independent extractor was less accurate than the rules on every field, and describe the merge policy this led to. We discuss why these numbers are optimistic and what a real-plant evaluation requires. 

# 1 Introduction 

A typical computerised maintenance management system (CMMS) export records which parts were issued to which order and what they cost. It rarely records why the equipment failed or what actually fixed it. Where that information exists, it is spread across a 40-character short text (“Parb.- Dryer elevator brg chng”), an optional remarks field written in a mix of English and Hindi (“grease nahi tha, brg jam”), and occasionally a root-cause column filled in for a fraction of breakdowns. Reliability engineers who want to know which failure modes drive downtime, or which spares to stock, must read these records by hand. Two developments make this worth revisiting. First, technical language processing has emerged as a discipline concerned with exactly this kind of text: short, domain-specific, abbreviation-heavy, and written for 1arXiv:2610.19131v1 [cs.AI] 13 Oct 2026 colleagues rather than for machines [3, 4]. Second, AI assistants are starting to be placed in front of planners and engineers. An assistant can only answer from data it can read, and a raw Excel export is a poor substrate: it invites confident answers built on misread abbreviations, with no way for the reader to check them. Plant Memory addresses both. Its contributions are: 1. A provenance-first maintenance ontology. Classes and relations are aligned with ISO 14224 [7] and extended for rice-processing equipment. Every extracted statement is reified as a fact with confidence, extraction method, evidence snippet, source field and a verification state (proposed, verified, rejected). 2. A TLP pipeline tuned for SAP PM exports. It merges material lines into events, expands plant abbreviations, resolves assets from functional locations or free-text aliases, and extracts component, symptom, failure mode, root cause and action under an explicit precedence order with calibrated confidences. 3. An LLM-as-second-reader merge policy , derived from a measured comparison in which the LLM underperformed the rules as an independent extractor but added value by filling gaps and flagging disagreements. 4. A human verification loop comprising a lowest-confidence-first review queue, automatically generated knowledge-gap questions for technicians, and ontology drift proposals that change the vocabulary only on approval. Verification decisions survive rebuilds. 5. One knowledge core behind three interfaces : a web application, a command-line interface and an MCP server [1]. The MCP server lets general-purpose AI agents query the verified graph and cite evidence, while its only write tool creates proposals. 6. An evaluation harness with a synthetic SAP PM generator that plants known patterns and hidden ground truth, scoring both extraction and end-to-end diagnosis. 

# 2 Background and related work 

Technical language processing. Brundage et al. [3] argue that general-purpose NLP pipelines fail on maintenance text because of its vocabulary, brevity and implicit context, and they propose TLP as a human-in-the-loop discipline that adapts NLP tools to technical domains. Dima et al. [4] discuss the adaptations this requires. Earlier work on cleaning work-order data for reliability analysis [6] and on hybrid human–machine tagging of maintenance logs [12] established that useful structure can be recovered with modest, carefully designed tooling and that expert review is central. MaintIE [2] provides a fine-grained annotation schema and benchmark for information extraction from maintenance short texts. Plant Memory follows the TLP view: rules encode plant-specific knowledge, and people remain responsible for what counts as true. 

Maintenance ontologies. ISO 14224 [7] standardises equipment taxonomies, failure modes and failure mechanisms for reliability data. Reference ontologies for industrial maintenance, such as ROMAIN [8] and the maintenance-activity ontology of Woods et al. [14], formalise these concepts with richer axiomatisation. Our schema is deliberately lighter (an OWL 2 [13] vocabulary with reified facts) because its purpose is operational: to carry provenance and verification state for every statement extracted from a specific plant’s records. 

LLMs, knowledge graphs and tool protocols. Retrieval-augmented generation [9] grounds model output in retrieved text; graph-based variants [5] and broader proposals for unifying LLMs with knowledge graphs [10] retrieve from structured knowledge instead. The Model Context Protocol [1] standardises how assistants 2call external tools and read resources. Plant Memory uses MCP to expose reasoning tools over a verified graph rather than raw documents, so that an assistant’s answer can be traced to specific work orders and verification states. 

# 3 Problem setting: what an SAP PM export looks like 

The input is an SAP PM export in Excel or CSV with one row per material issue. A month of a real export from a rice processing unit motivated the design and exhibits the following issues, which the synthetic data reproduces: • Repeat failures are not linked. One elevator accumulated three separate orders within a month (a bearing change, a sprocket change and “general maintenance”), and nothing connects them as one recurring problem. • Free text is not machine-readable. Descriptions mix abbreviations and typos (“Parb.”, “brg”, “Plmbr Blck”, “modificatn”, “ELevator”), and asset names (“Hodi Elevator”, “Elev1&2”) are embedded in text with no equipment identifier. • Work-type labels are unreliable. Bearing and belt replacements are tagged Preventive while compa-rable work is tagged Corrective , which skews any analysis built on the label. • Cause and fix are missing. Cost, quantity and material are present; symptom, root cause, downtime and action taken mostly are not. • Records are fragmented. One order may be posted on several dates, materials are split across lines, and reservation rows (SAP transaction MB21) carry a cost centre but no order number. 

# 4 System design 

4.1 Architecture 

Figure 1 shows the data flow. Uploaded files are immutable evidence: people never edit raw rows, only the knowledge derived from them. The graph is rebuilt from all registered source files; when an order appears in several files, the newest file wins. Rebuilds preserve verification decisions for any fact whose extracted value is unchanged, and technician-stated facts are carried over untouched.

4.3 Technical language processing pipeline 

Ingestion. Column names are matched to canonical fields by exact lookup, then fuzzy matching, and users can correct the mapping on screen; only order number, date and description are required. Date order (day-first or month-first) is inferred from the values. Rows are grouped by order: the modal description and work type are taken, header fields use the first non-empty value, and the earliest and latest posting dates are both kept. Rows without an order become consumption-only records. A data-quality flag is raised when a breakdown (from the breakdown column or from words such as “broken” in the text) carries the work type Preventive .

Normalisation and asset resolution. Text is lower-cased, letter–digit runs are split (“elev1” → “elev 1”), and a plant abbreviation table is applied (“parb” → parboiling, “brg” → bearing, “plmbr blck” → plummer block, “b/d” → breakdown). Assets are resolved in order of reliability: a functional location that matches the register (confidence 0.98); otherwise the longest alias match in the normalised text, disambiguated by process-area cues (0.85 with an area cue, 0.80 without, 0.50 if still ambiguous); otherwise a fuzzy alias match (0.45). An asset-discovery step proposes new register entries from unresolved functional locations and from residual noun phrases after component, action and symptom words are stripped, accounting for SAP’s 40-character truncation. 

Rule-based extraction. Sources are consulted in a fixed precedence: structured SAP columns, then technician remarks, then the short text, then the materials issued. Specific rules encode domain knowledge: • Values from structured columns that map to the vocabulary receive confidence 0.95; values that do not map become drift candidates. • The asset’s own name and aliases are removed before component matching, so “Hodi belt conv” is not read as a conveyor-belt component. • A component named in the text and confirmed by an issued material receives 0.92; named but unconfirmed, 0.75; read only from materials, 0.75, preferring the highest-cost line and ignoring consumables such as adapter sleeves when a primary part is present. • Root causes are read only from the root-cause column or technician remarks, never from the short text, where words such as “stone” usually name a component. 4Class Role and examples ProcessArea Top of the asset hierarchy: parboiling, paddy-to-rice milling, utilities, packing, warehouse Asset Maintainable item with a functional location, class and shop-floor aliases (e.g. Dryer elevator ,alias “LSU elev”) Component Part of an asset: bearing, V-belt, sprocket, plummer block, rubber roll, mechanical seal SparePart SAP material that realises a component type, with material code and unit cost Symptom Observation: abnormal noise, vibration, belt slip, tripping, reduced output FailureMode ISO 14224-aligned, with mechanism code: bearing wear (2.4 Wear), belt slippage (1.5 Looseness), seal leakage (1.1 Leakage) RootCause Misalignment, inadequate lubrication, dust ingress, overload, foreign material, cavitation; grouped into cause categories Action Replace, repair, weld repair, realign, lubricate, adjust, refurbish, modify MaintenanceEvent One work order: dates, work type, cost, downtime, breakdown flag Fact Reified statement (subject, predicate, object) with confidence, method, status, verifier and evidence Evidence A source row and field, or a technician statement

LLM as second reader. When enabled, events are sent in batches to any OpenAI-compatible endpoint (a hosted provider or a local model). The prompt constrains output to vocabulary identifiers, or other:<phrase> 

when the text clearly states something outside the vocabulary, and requires a per-field confidence and the exact evidence words. Responses are cached by a hash of the event payload, prompt version and model, so rebuilds do not repeat calls; malformed batches are split recursively, and any failure falls back to the rules for the affected events. The merge policy (Section 6.4) was set from measurement: 1. Structured columns always win; agreement raises confidence to 0.97. 2. On disagreement the rule value is kept, its confidence drops by 0.15 (floor 0.3), and a note records the LLM’s suggestion so the fact rises in the review queue. 3. On agreement, confidence becomes min (0.93 , max (cllm , crule ) + 0.07 ).4. The LLM fills empty fields for failure mode, root cause, action and symptom at confidence min (0.7, cllm ), but never components. 5. An other: answer counts as drift only where the rules found nothing. 6. The LLM cannot reclassify a failure as planned work when the rules found a component or symptom. 

Drift detection. Phrases that fail to map, from structured columns, incompatible failure-mode evidence or LLM other: answers, are grouped into drift proposals with the orders they occur in. An engineer can approve a proposal as a new term (with label, synonyms, applicable components or cause category), map it as 5a synonym of an existing term, or reject it. Approved changes are written to an extension file and applied on the next build; the built-in vocabulary is never modified. 

4.4 Human verification and knowledge capture 

The review queue presents proposed facts lowest-confidence first, each with its evidence snippet, source field and extraction method, and allows a reviewer to verify, correct (which verifies the corrected value) or reject. Bulk verification above a confidence threshold is available and logged. Every decision is written to an audit log with the reviewer’s name. Knowledge-gap questions are generated where an asset has at least two events with the same failure mode and fewer than half of them have a confident or verified root cause. Each question names the asset, the failure mode, the number of unexplained events and the date range, asks what usually causes the failure and what check would confirm it, and suggests the technician who most often worked those orders. An answer that maps to a known cause becomes a proposed asset-level technician fact; an answer that names an unknown cause becomes a drift proposal. 

4.5 Reasoning 

All reasoning functions return the orders behind each result, a confidence, and a sparse-evidence flag when fewer than θ = 3 events support the answer. 

Root-cause ranking. For an asset and an optional symptom or failure-mode filter, each matching failure event e with a root-cause fact fe contributes weight ω( fe) to that cause, where ω = 1 for verified facts, the extraction confidence for proposed facts, and 0 for rejected facts. Technician statements for the asset add 2.0 if verified and 1 .2 if proposed. If the asset has fewer than θ explained events, events from assets of the same class are added at half weight. Scores are normalised, sc = wc/ ∑c′ wc′ , and banded as high ( sc ≥ 0.5), medium ( ≥ 0.25) or low, or as low (sparse evidence) when support is below θ . The response also lists typical actions and parts and the number of unexplained events, pointing to the open knowledge-gap questions. 

Similar failures. Each failure event is indexed as a bag of tokens from its description, symptom, remarks, recorded root cause and extracted labels, after normalisation, and ranked against a free-text query with Okapi BM25 [11] ( k1 = 1.2, b = 0.75). 

Bad actors, recurrence and spares. Bad actors are a Pareto ranking of failure events by cost, downtime or frequency, grouped by asset, failure mode or both, reporting how many groups account for 80% of the total. Recurrence uses a sliding window to find the largest set of events with the same failure mode on the same asset within W days (default 60, at least three events). Minimum spare stock per material is S = ⌈μL + z σ √L⌉,with μ and σ the mean and standard deviation of monthly consumption, L the lead time in months and 

z = 1.65; parts are ranked by the breakdown downtime of the orders that consumed them.

# 5 Implementation 

Table 3 summarises the technology stack. The implementation is about 5,000 lines of Python; the web API, MCP server and CLI are thin layers over one core library. Storage is abstracted behind a repository interface with two implementations returning identical records: Neo4j, used when credentials are configured, and SQLite as an offline fallback and test reference. Graph queries use plain openCypher without plug-ins, so the same code is also exercised in tests on an embedded openCypher engine. Long builds run as background jobs with progress reporting. The system is packaged for pip and for Docker Compose with Neo4j. 

Privacy. Maintenance records contain supplier names, costs and staff identifiers. The plant chooses one of three modes: local only (rules, no data leaves the machine), LLM API (text is sent to a hosted provider), or local LLM (an OpenAI-compatible model on the plant’s own network). # 6 Evaluation 

6.1 Data 

Real exports cannot be published, so evaluation uses a synthetic generator that reproduces the structure and messiness of the motivating export. It simulates 18 assets across five process areas for 12 months (October 2023 to October 2024) with Poisson failure arrivals per asset class and weighted scenarios per class (component, failure mode, symptoms, cause distribution, actions, quantities, downtime). Text is generated from deliberately messy templates, including abbreviations, upper-case variants, 40-character truncation and Hinglish remarks. Structured fields are sparsely populated: the root-cause column is filled for about half of breakdowns and a fifth of other failures, and work types are mislabelled on purpose. The generator plants four patterns: the dryer elevator fails at 2.2 times the class rate with misalignment over-represented; one V-belt is consumed across several elevators; husker rubber rolls dominate milling spend; and from the tenth month the Hodi conveyor shows gearbox oil leaks caused by a choked breather, a failure mode and cause absent from the vocabulary (drift). With seed 7 the export has 590 lines and 400 work orders (357 failures, 34 lubrication rounds and 9 modifications), plus 37 reservation lines. Ground truth is written to a separate file used only for evaluation.

6.4 Rules versus LLM 

We ran openai/gpt-oss-120b with low reasoning effort on 399 of the 400 orders and compared it with the rules (Table 6). As an independent extractor the LLM was less accurate on every field, most markedly on failure mode (55.4% versus 88.9%). A recurring error was reading the Preventive work type literally and classifying genuine wear failures as planned work; in an initial merge that allowed the LLM to override the rules, this removed 99 failure events and reduced diagnosis top-1 accuracy from 82.1% to 75.0%. The LLM nevertheless added value where the rules were silent, correctly filling 8 actions and 5 symptoms (with 2 incorrect fills each), which motivated the second-reader policy described above. Under that policy, action accuracy rose from 93.0% to 95.0% and symptom accuracy from 59.7% to 61.1%, with component, failure-mode and diagnosis accuracy unchanged. 

# 7 Discussion and limitations 

The evaluation is favourable to the system for a structural reason: the ground truth comes from the same generator as the data, and the abbreviation table and synonyms were written alongside the generator’s vocabulary. Real exports will contain unseen abbreviations, other languages and plant-specific idioms, and accuracy will be lower. This is the case the review queue, drift proposals and vocabulary editor are designed for, but their effectiveness has not yet been measured. A credible evaluation requires 50 to 100 hand-labelled orders from a real plant, which would also show whether the rules-versus-LLM ranking holds once the rules face unfamiliar text. The comparison with an LLM is likewise specific to one model, one prompt and synthetic text. Other limitations follow from scope. # 8 Conclusion 

Plant Memory treats maintenance text as evidence and maintenance knowledge as a set of claims that people verify. Rule-first technical language processing, an ISO 14224-aligned ontology with reified provenance, and a verification loop with knowledge-gap questions and drift proposals together produce a graph that both planners and AI agents can query, with every answer traceable to the work orders behind it. On synthetic data the approach substantially outperforms the raw root-cause column for diagnosis, and a measured comparison suggests that, for this kind of text, an LLM is more useful as a second reader than as the primary extractor. The next step is evaluation on real plant data with real technicians.
